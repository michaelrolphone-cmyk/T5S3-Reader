# Agent instructions

## Architecture and specification authority

Repository: `michaelrolphone-cmyk/T5S3-Reader`. Platform name: **RiscRTE (RISC Runtime Environment)**.

**Read [docs/RISCRTE_PLATFORM_SPEC.md](docs/RISCRTE_PLATFORM_SPEC.md) first** before architectural, platform API, application, service, driver/provider, streams, devices, jobs, packages, resource or hardware work. It is the canonical specification index and defines precedence. Then read the applicable [docs/PLATFORM_CAPABILITY_ROADMAP.md](docs/PLATFORM_CAPABILITY_ROADMAP.md) section and referenced child specifications.

**Active execution milestone: [docs/NEXT_HARDWARE_TEST_MILESTONE.md](docs/NEXT_HARDWARE_TEST_MILESTONE.md) (U1).** Read it before *any* current USB, Serial Monitor, package-manager, catalog, signing-purge or provider-release work. Its exact workstreams, implementation/status correction, acceptance and **single owner hardware-test handoff** supersede outdated PR draft, unsigned-integration, provider-publication and optional-signing-experiment statements in historical documentation. U1 is **one completed software deliverable**: finish common four-kind online/offline package lifecycle; eliminate coupling to `usb-provider-catalog.json` and special driver catalogs; purge unwanted package-signing code/tooling/docs from the active repo while keeping ordinary integrity and independent loader authorization; remove all operational USB selection/session/discovery/stream/hardware code from normal firmware in favor of independently installed hardware-owning ELFs and generic `serial.port`. Do not stop at a partial vertical slice and tell the owner to test it; owner hardware validation is after the complete software milestone.

**Scope authorization before implementation.** The latest explicit user objective defines work; long-term roadmap features, adjacent specs, existing prototypes and agent preferences cannot become mandatory deliverables. Write a change contract in each active PR/spec: user objective, included deliverables, excluded/deferred features, acceptance and source of mandatory dependencies. Classify additions REQUIRED, OPTIONAL/nonblocking or DEFERRED. Do not invent new trust systems, persistent policy, incompatible package formats, hardware ownership layers, cross-PR dependencies or release gates without authorization. Fix necessary bounded correctness defects but never smuggle unrelated features into them. Audit each PR against the contract.

**Future SD deployment provisioning is DEFERRED.** [docs/DEPLOYMENT_PROVISIONING.md](docs/DEPLOYMENT_PROVISIONING.md) specifies an eventual versioned manifest on a new SD card declaring a device's compatible board/hardware profiles, initial driver/provider/app packages and configuration. A future first-run provisioner must reuse the ordinary package manager and driver platform. **Do not implement a provisioning parser, wizard, installer, persistent ledger, credential setup or extra release/CI gate during U1 or the current MVP**, or treat provisioning as a hidden dependency. Only preserve generic package/driver interfaces; request separate authorization for the future implementation.

**Current package scope:** [docs/PACKAGE_MANAGER_SCOPE_CONTRACT.md](docs/PACKAGE_MANAGER_SCOPE_CONTRACT.md) and [docs/RISC_PACKAGE_FORMAT.md](docs/RISC_PACKAGE_FORMAT.md). Merged PRs #76/#79 contain a usable ordinary package engine and App Store/Driver Manager integration; do not repeat delivered work based on stale docs. Package signing/P-256, signer keys/revocation, signed provenance and NVS cryptographic floors were unrequested scope creep; the owner now requires the **active repository to be purged of signing-specific implementation, build/test tooling and experimental signed-format docs** after a reference audit and extraction of reusable ordinary behavior. Do not just archive, disable or relabel it. Keep SHA-256 file-integrity checking, bounded parsing, path/ELF/import/ABI checks, recoverable transactions, mapped executable-byte lifetimes and runtime permission policy. SHA-256 is not publisher identity. Keep unrelated OS/network cryptography and TLS. Previously installed data must not be silently deleted.

**Hardware boundary:** read [docs/HARDWARE_AGNOSTIC_DRIVER_BOUNDARY.md](docs/HARDWARE_AGNOSTIC_DRIVER_BOUNDARY.md) before touching any firmware, transport, driver, device, registry or capability work. The core treats `usb`, `serial.port` and any hardware identifiers as opaque data; no USB-specific discovery, controller, VID/PID/class/provider selection, physical stream/session, hardware power or fallback can remain in normal firmware. Functional hardware-owning ELFs implement actual behavior, potentially consuming other ELFs; descriptor/proxy ELFs forwarding into firmware do not satisfy the design. Runtime manages generic package/ELF loading, execution contexts, permissions, capability resolution, events/streams and lifecycle only. Real physical bus/controller/rail state is owned by providers. Keep boot-critical port/recovery primitives isolated and never silently expose them as normal capability fallbacks. Existing compiled USB/GNSS/Wi-Fi code is legacy/noncompliant, not precedent. A different ESP CPU/ABI may need a distinct minimal port; compatible new hardware on a given port must require no core recompile.

**U1 workflow and continuity:** Follow internal workstreams A–F in [U1](docs/NEXT_HARDWARE_TEST_MILESTONE.md) on **one PR targeting `master`**. Commit coherent internal checkpoints but do not label them owner-testable milestones or require intermediate board tests. The user reports most package management already hardware-tested and USB/Serial Monitor not yet tested; do not make earlier USB results a dependency of further implementation. Run local/host/build checks, push and observe CI opportunistically while coding the next independent workstream. **Never freeze a prompt waiting for CI**; handle failures as results arrive, carry an exact remaining-work ledger and continue next prompt on the same PR. Do not claim a pending/failed test passed. At the final software handoff, record exact commit, all relevant build/host/static results, coherent firmware/app/driver revisions and one end-to-end physical test procedure; mark physical results PENDING until owner tests. Do not auto-merge, tag, release, flash, or introduce workflows requiring repeated owner approval.

When target specs and legacy implementation differ, place target architecture first, followed by truthful current/legacy status and migration requirements. Spec edits alone never mean code is migrated. Update authoritative specs whenever APIs/architecture change, and do not introduce more legacy hardware-specific framework services in the interim.

Use **RiscRTE** for firmware, runtime, releases, packages and overall platform naming. **CrossPoint** refers only to ebook-reader subsystem/capabilities and existing compatibility symbols like `CrossPointSettings`, `.crosspoint/` or `CROSSPOINT_*`. `T5S3`/`EPD47` describe boards; existing `T5*` and `native_*` are historical ABI identifiers. New platform facilities should be generic capabilities, services/providers, streams, devices, jobs, intents, packages, contexts or core primitives, not private app substitutes. Prefer execution-context-owned opaque handles and semantic capability APIs.

## Pull request workflow — mandatory

**Never stack PRs.** Every PR targets `master` directly. If changes depend on an open PR, put them on that PR and its branch; do not create a second dependent PR or duplicate its unmerged commits. Genuinely independent changes may branch from master. Backmerge master into the active PR if necessary. Preserve unique work before closing any accidentally redundant PR; do not discard code simply to remove a dependency. Do not turn on auto-merge without explicit user instruction. During U1, use one cohesive working branch/PR and do not force the owner to merge incomplete portions just to continue.

## Tagged firmware releases

When the owner explicitly requests a release, read `docs/RELEASING.md` and `.github/workflows/release.yml` and inspect master, tag, versions, CI and required assets. Existing release request mechanism: update `[riscrte] version` in `platformio.ini`, commit `.github/release-request.json` on master with enabled=true, corresponding v-prefixed tag and commit_firmware=true unless directed otherwise. GitHub Actions builds `gh_release`, apps and drivers, stamps/version-checks, creates assets and publishes. Monitor and verify an explicitly requested release; existing tags cannot be reused. Avoid moving master while a commit_firmware=true release is active. Unrelated commits do not trigger publication just because an old request remains enabled. Do **not** use publishing as a build/test shortcut for U1.

**Before any release or app-update handoff**, audit every changed application against [docs/APP_VERSION_POLICY.md](docs/APP_VERSION_POLICY.md): its own `Apps/<name>.json` `version` MUST be strictly higher than the prior distributed/baseline version, and matching ELF, sidecar, generic package and catalogs must report the identical app version. Reject different shipped bytes under the same app identity/version; do not advance only the firmware version or `min_firmware_version`. Record every affected app's old -> new version in PR/release notes. Do not claim an automatic version guard passed unless it actually ran and passed.

`firmware-t5s3-pro.bin` remains OTA/SD compatibility filename; versioned `riscrte_...-app.bin` is OTA/SD at 0x10000, whereas the merged versioned `.bin` is USB-flash image at 0x0 and MUST NOT be used for OTA/SD. Versioned `.elf` may be for backtraces rather than flashing. Preserve firmware outputs outside mutable `.pio` before app/ELF builders and checksum them before release staging; U1 corrects source-discovery/release catalog so no USB-only index is needed.

## Adding or extending apps

**Mandatory first step for every app edit:** read [docs/APP_VERSION_POLICY.md](docs/APP_VERSION_POLICY.md), inspect that app's sibling `Apps/<name>.json` and its previous/published version. Every distributable change to app source, UI, behavior, resources, relevant build inputs or distributed manifest **MUST include a strictly increased `version` in that same app's source manifest within the same PR before declaring completion**. For multiple changed apps, bump each affected app independently. One bump per cumulative unreleased change set suffices; bump again for the next independently released update. A firmware version or `min_firmware_version` increase does NOT count as an app version increase; adjust minimum firmware only when compatibility genuinely requires it. Preserve matching version in emitted manifest, package, catalog, inventory and release assets. Explicitly report `old -> new` for every affected app, check against already published versions and run applicable app builds; do not leave the bump to the owner or the release workflow. Docs-only/non-distributable edits do not cause unrelated app bumps. Until a tested automated validator exists, perform this check manually and do not claim version enforcement is automatic.

For every first-class app or app-facing API read master, roadmap, `docs/APPLICATION_EXECUTION_CONTEXT_ARCHITECTURE.md` and `docs/NATIVE_APPS.md`. For U1 Serial Monitor/App Store/Driver Manager/Package Manager also read the U1 milestone and package/hardware contracts.

Trusted system UI mediation and package-private storage are high-priority for **new app work within explicit scope**: do not invent unrestricted file/resource browsers, credential/device/Wi-Fi pickers or permission prompts when the platform can mediate them; request platform pickers/intents and use scoped results. Put app-private persistent state in a private namespace, not arbitrary shared `/sd`; obtain shared files through trusted picker/intent/share/scoped handles. If a primitive is missing, use existing authorized facilities or identify a separately justified minimal prerequisite rather than silently expanding the task. Bind acquired resources to execution contexts with generation-safe handles, make use accountable/quota-capable where feasible, and derive/validate manifest requirements from SDK usage when practical.

Native app sources in `Apps/` have adjacent manifests; use `scripts/build_all_apps.py` for release-equivalent validation and append-only `struct_size` checks for new ABI members. `docs/ADDING_APPS.md` documents the legacy in-firmware C++ Activity path, only for genuinely firmware-internal functionality; do not choose it for a new first-class ELF app or to conceal a hardware driver.
