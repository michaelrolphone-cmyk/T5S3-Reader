**Hardware boundary:** read [docs/HARDWARE_AGNOSTIC_DRIVER_BOUNDARY.md](docs/HARDWARE_AGNOSTIC_DRIVER_BOUNDARY.md) before touching any firmware, transport, driver, device, registry or capability work. The core treats `usb`, `serial.port` and any hardware identifiers as opaque data; no USB-specific discovery, controller, VID/PID/class/provider selection, physical stream/session, hardware power or fallback can remain in normal firmware. Functional hardware-owning ELFs implement actual behavior, potentially consuming other ELFs; descriptor/proxy ELFs forwarding into firmware do not satisfy the design. Runtime manages generic package/ELF loading, execution contexts, permissions, capability resolution, events/streams and lifecycle only. Real physical bus/controller/rail state is owned by providers. Keep boot-critical port/recovery primitives isolated and never silently expose them as normal capability fallbacks. Existing compiled USB/GNSS/Wi-Fi code is legacy/noncompliant, not precedent. A different ESP CPU/ABI may need a distinct minimal port; compatible new hardware on a given port must require no core recompile.

## Package identity and versioning — mandatory for all agents

Read [docs/PACKAGE_IDENTITY_VERSION_POLICY.md](docs/PACKAGE_IDENTITY_VERSION_POLICY.md) before editing, packaging, cataloging, installing or releasing **any** app, driver, provider or service. Stable `id` is the update lineage; numeric `version` is the distributable release; `driver_abi`, architecture and capability API versions are separate compatibility declarations. Every changed distributable package MUST advance its own manifest `version` in the same PR relative to its merge-base and latest published version. Never rename `foo` to `foo-v2` merely because its ABI, code or architecture changed, or publish changed bytes under the same stable ID/version. Multiple changed packages require independent increments; unchanged packages do not. Release tag and firmware version are not package versions. Validate manifest, ordinary package, provider declarations, catalog, assets, installed inventory and UI all agree. Record each affected ID's `old -> new` version and perform actual build/CI guard checks; do not claim an unimplemented guard passed.

**U1 blocking defect:** legacy `usb-cdc-acm@0.1.0` ABI 1 is a firmware proxy; `usb-cdc-acm-v2@0.1.0` ABI 2 is its functional replacement, not a distinct CDC hardware family. The current forked identity and hard-coded `0.1.0` in `scripts/build_installed_usb_stack.py` MUST be repaired end to end in the SAME U1 PR: canonical `usb-cdc-acm` ID, version strictly greater than published lineage, correct independent ABI/dependencies, old proxy excluded from current builds/releases, explicit safe legacy-install migration/rollback, no duplicate catalog rows or firmware fallback, and automated ID/version regression gates. Follow [Drivers/AGENTS.md](Drivers/AGENTS.md). Never merely rename a source directory or delete installed data. Do not mark U1 software complete with this unresolved.

**Before any release or app-update handoff**, audit every changed application against [docs/APP_VERSION_POLICY.md](docs/APP_VERSION_POLICY.md): its own `Apps/<name>.json` `version` MUST be strictly higher than the prior distributed/baseline version, and matching ELF, sidecar, generic package and catalogs must report the identical app version. Reject different shipped bytes under the same app identity/version; do not advance only the firmware version or `min_firmware_version`. Record every affected app's old -> new version in PR/release notes. Do not claim an automatic version guard passed unless it actually ran and passed. Apply the same independent manifest ID/version and published-artifact checks to drivers, providers and services under [Package Identity and Version Policy](docs/PACKAGE_IDENTITY_VERSION_POLICY.md). **U1 release output is one ZIP archive per package and generic index, not individually downloaded ELFs/manifests; verify archive payload digests, identities and per-kind directory install paths.**

`firmware-t5s3-pro.bin` remains OTA/SD compatibility filename; versioned `riscrte_...-app.bin` is OTA/SD at 0x10000, whereas the merged versioned `.bin` is USB-flash image at 0x0 and MUST NOT be used for OTA/SD. Versioned `.elf` may be for backtraces rather than flashing. Preserve firmware outputs outside mutable `.pio` before app/ELF builders and checksum them before release staging; U1 corrects source-discovery/release catalog so no USB-only index is needed.

## Adding or extending apps

**Mandatory first step for every app edit:** read [docs/APP_VERSION_POLICY.md](docs/APP_VERSION_POLICY.md), inspect that app's sibling `Apps/<name>.json` and its previous/published version. Every distributable change to app source, UI, behavior, resources, relevant build inputs or distributed manifest **MUST include a strictly increased `version` in that same app's source manifest within the same PR before declaring completion**. For multiple changed apps, bump each affected app independently. One bump per cumulative unreleased change set suffices; bump again for the next independently released update. A firmware version or `min_firmware_version` increase does NOT count as an app version increase; adjust minimum firmware only when compatibility genuinely requires it. Preserve matching version in emitted manifest, package, catalog, inventory and release assets. Explicitly report `old -> new` for every affected app, check against already published versions and run applicable app builds; do not leave the bump to the owner or the release workflow. Docs-only/non-distributable edits do not cause unrelated app bumps. Until a tested automated validator exists, perform this check manually and do not claim version enforcement is automatic.

For every first-class app or app-facing API read master, roadmap, `docs/APPLICATION_EXECUTION_CONTEXT_ARCHITECTURE.md` and `docs/NATIVE_APPS.md`. For U1 Serial Monitor/App Store/Driver Manager/Package Manager also read the U1 milestone and package/hardware contracts. Build app resources inside its ZIP bundle and load them from its manager-owned package root, not the root `/Apps` folder or a stray sibling manifest.

Trusted system UI mediation and package-private storage are high-priority for **new app work within explicit scope**: do not invent unrestricted file/resource browsers, credential/device/Wi-Fi pickers or permission prompts when the platform can mediate them; request platform pickers/intents and use scoped results. Put app-private persistent state in a private namespace, not arbitrary shared `/sd`; obtain shared files through trusted picker/intent/share/scoped handles. If a primitive is missing, use existing authorized facilities or identify a separately justified minimal prerequisite rather than silently expanding the task. Bind acquired resources to execution contexts with generation-safe handles, make use accountable/quota-capable where feasible, and derive/validate manifest requirements from SDK use when practical.

Native app sources in `Apps/` have adjacent manifests; use `scripts/build_all_apps.py` for release-equivalent validation and append-only `struct_size` checks for new ABI members. `docs/ADDING_APPS.md` documents the legacy in-firmware C++ Activity path, only for genuinely firmware-internal functionality; do not choose it for a new first-class ELF app or to conceal a hardware driver.
