# RiscRTE typed record streams: version-2 ABI

## Authority and scope

[RiscRTE Platform Specification](RISCRTE_PLATFORM_SPEC.md) → [Platform Capability Roadmap](PLATFORM_CAPABILITY_ROADMAP.md), Part III → [Stream/Pipe Architecture](STREAM_PIPE_ARCHITECTURE.md) govern this interface. [Application Execution Context Architecture](APPLICATION_EXECUTION_CONTEXT_ARCHITECTURE.md) governs ownership. This document fixes the initial versioned binary contract and clearly distinguishes current implementation from the remaining architecture.

## Canonical contract

A record represents one indivisible message carrying a versioned schema identity. The runtime copies schema identifiers and record payloads into bounded framework storage, never retains pointers supplied by an ELF, and rejects byte↔record or incompatible-schema pipes before acquiring an endpoint lease. Exact matching is required until an explicitly typed transform is installed. A producer's declared maximum message size must fit the receiving endpoint's maximum record size, regardless of whether the records currently buffered happen to fit. Otherwise a pipe could irreversibly dequeue a record that its destination can never accept.

Every record stream and pipe belongs to the current execution context and uses the same generation-safe opaque stream/pipe handles, scheduler, endpoint leases, EOF/error/cancellation and cleanup model as byte streams. A consumer gets either an entire record or nothing. A short receive buffer returns `T5_STREAM_LIMIT` without consuming the record; zero-byte records return `T5_STREAM_OK` with size zero. A full destination returns `T5_STREAM_AGAIN`, preserving the record and applying backpressure. Queued records drain before EOF or other terminal errors. `finish` of a pipe-leased destination is forbidden until the connection is released. Record schemas are not implicitly converted and byte read/write functions reject record handles.

## Current ABI on PR #65

The historical exported symbol `t5_stream_get_api(version)` remains the sole loader entry point. The existing `t5_stream_get_api(1)` returns the unchanged `t5_stream_api_v1` structure, unchanged size, `api_version=1`, and unchanged function members. Requesting `t5_stream_get_api(2)` returns the `riscrte_stream_api_v2` table as a pointer to its `v1` prefix; that prefix has `api_version=2`, `struct_size=sizeof(riscrte_stream_api_v2)`, and the same v1 functions. The C SDK's `riscrte_stream_get_api_v2()` checks the version and complete size before casting. Neither function table may be cached across invocation unload/reload. Apps must set their minimum firmware version to the first released build that actually contains v2; a merged PR alone does not establish that floor.

The append-only v2 functions are `open_record_buffer(schema, max_record, capacity_records, flags, out)`, `record_read(handle, buffer, capacity, actual_size)`, `record_write(handle, payload, length)` and `record_info(handle, out)`. Existing v1 `pipe_connect`, `pipe_info`, `pipe_pause`, `pipe_cancel`, `pipe_close`, `finish`, `close`, and `info` work on both kinds, subject to type validation. `record_info` copies a NUL-terminated schema and counters into a caller-provided `riscrte_record_info_v1` whose `struct_size` must fit; no borrowed schema pointer or provider vtable crosses the ELF boundary. All functions use the existing invocation gate, registry mutex, owner and stream scheduler. V2 buffer flags are exactly READ, WRITE or both; SEEK is invalid for record streams.

The initial bounds are one of 12 shared registry slots per record stream, a total of four shared pipes, 1–8 records per stream, 1–512 bytes maximum per record, and `max_record × capacity_records ≤ 4096` payload bytes per stream. The schema is a copied, validated ASCII type ending in `.vN` (for example `location.fix.v1`); v1 and v2 schemas are incompatible. Record pipe staging is one complete record (including distinct zero-length pending state), with one record moved per scheduler turn. `BLOCK_PRODUCER` is the only enabled pipe policy. These bounds are current implementation limits, not promises about all later providers or memory tiers.

## Safety and verification

All v2 entry points validate an active application invocation before accessing registry state. The common mutex serializes record APIs and the pipe scheduler; the application receives only owned generation-safe handles, not provider callbacks or pointers. `record_info` checks `struct_size` before writing any caller output. Failed opens clear the resulting handle, and invalid/stale/foreign handles are rejected. Record-size compatibility must be checked at `pipe_connect` even when v1's inherited pipe API is used on records.

Host verification runs the actual `StreamRuntime::Registry` record and pipe tests, the native ELF bridge tests for v1/v2 table layout, metadata, atomicity, incompatible-schema/kind/max-size rejection, leases and revoked handles, and all legacy byte/serial/App Store regressions through `test/run_stream_test.sh`. Firmware builds for both supported boards and packaged ELF/driver checks are required on the exact PR head. This documentation does not claim physical hardware testing or release status.

## Remaining architecture work

The v2 API permits ELF code to create invocation-private record queues. It does **not** yet provide installable driver-owned typed record producers, semantic discovery, a shared subscription grant, or cross-context producer/consumer ownership. Those require a provider adapter and capability resolver with explicit rights and connection policy. A GNSS/location decoder or another real producer is the next meaningful consumer of this contract. Transforms, tee/merge, alternate loss/drop policies with counters, readiness events, global quotas/accounting, zero-copy and replay/range support are later architecture phases. Do not mistake a user-created record buffer for a resolved sensor/device capability.
