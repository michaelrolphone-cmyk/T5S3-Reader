# Xteink X4 Pro drivers

Board packages for the Xteink X4 Pro. They publish the existing RiscRTE capability ABI (`risc_driver_v2`, export `t5_driver_get` only) and do not reuse the T5S3 panel, touch axis, or I2C pin ownership.

Pin and protocol facts are derived from pinned CrossPoint/FreeInk firmware and driver sources. On the physical X4 Pro, the UC8279 full refresh completed and the owner confirmed visible blocks and later visible text. The owner manually installed the CI-built full merged image from PR commit `94c14bf6` and reported the on-screen message `SD card found; files unavailable`. That image probes FAT32 boot/root metadata but intentionally keeps file access unavailable, so the observation supports that limited path and does not establish a mounted filesystem. The owner then installed the exact CI-built full merged `5e1f8343` image. Its 6,068,576 bytes were verified at offset `0x0` by esptool, and a post-reset/reconnect serial capture independently recorded `diagnostic entered`, `storage.volume mounted=1`, `home present=1`, and repeated `heartbeat ready=1`. The owner reports that this Home frame is malformed: menu items appear too large and rotated 90 degrees relative to the on-screen controls. A reset looked like a non-boot visually, while the reconnected serial capture proves firmware boot and Home present occurred; an unchanged e-paper frame can hide a successful reboot. Buttons and TXT browsing remain physically untested. No camera images are in the repository.

Load order: `platform-clock-v1`, `x4pro-i2c`, `x4pro-panel`, `x4pro-gt911`, `x4pro-buttons`, `x4pro-frontlight`, `x4pro-battery`, `x4pro-sd`.

## First diagnostic boot

`env:xteink-x4-pro` does not call `HalSystem::begin()`, so the legacy T5S3 peripherals cannot be started on this path. It loads embedded `platform-clock-v1`, `x4pro-panel`, `x4pro-buttons`, `x4pro-frontlight`, `x4pro-sd`, `x4pro-i2c` and `x4pro-gt911` through `ProviderModuleV2::loadVerifiedBytes`. `ProviderDisplaySurface` validates the provider geometry, translates Reader MONO1 polarity, and makes bounded `display.output` presents. The global Reader `HalDisplay` and `GfxRenderer` forward through this provider. The X4 branch schedules the real shared `HomeActivity` first frame after provider and font initialization; it skips uninitialized T5S3 power and startup-screen services in its render worker.

The verified buttons ELF is borrowed by the existing `NativeNavigationInput` consumer. Its module remains owned by the X4 boot controller. Power currently maps to Confirm. The X4 bootstrap now calls `MappedInputManager`'s provider-only update and the ordinary `ActivityManager::loop`; the shared `HomeActivity` and `ButtonNavigator` handle focus, touch menu taps and selection. The Home rows retain the T5S3 labels and layout: Recent books, Apps, Settings. On X4, Recent books currently opens only the bounded read-only TXT subset; Apps and Settings display unavailable feedback until their device services are qualified. The X4 TXT view also uses the ordinary activity loop. The provider still logs actual `input.navigation event=...` edges for diagnosis; physical button movement on this new software path remains untested. Frontlight stays off.

The `x4pro-gt911` 0.1.1 driver asserts master peripheral enable GPIO1 high and active-low touch power GPIO2 low, performs the GT911 INT/RESET address-select sequence on GPIO10/4, then probes the claimed I2C bus at 0x5D or 0x14. It publishes bounded single-contact portrait 480×800 DOWN/MOVE/UP and capacitive Home-key events to the existing independent Reader touch capture task. Multi-contact reports invalidate the gesture stream; touch power returns off on driver stop. This is source and host-model behavior, not yet a physical touch qualification. `x4pro-sd` alone controls the active-low SD power gate GPIO5 and native one-bit SD CMD42/CLK41/DAT0 40; its power cycle uses the pinned board source's 80 ms high and 120 ms low intervals. Pinned FreeInk commit `111fdcc7f0176c3ee38391a160ee296bf492dbd8` supplies the SSD1677 full refresh sequence and the UC8279 X4 Pro 800×480 visible / 800×600 addressed, 120 gate offset, full GC waveform sequence. The provider confirms a UC8279 `VER[2]=0x68` identity with a second read and idle BUSY before issuing UC commands. Other UC81xx variants remain unsupported. SSD and UC use their respective BUSY polarities and bounded waits.

## Storage prerequisite for Home

The `x4pro-sd` 0.1.8 provider sends bounded native SD initialization commands, selects the card, reads CRC16-checked sectors over DAT0, and locates a FAT32 boot sector either at LBA0 or through one MBR FAT32 partition. It validates FAT32 geometry and root chain, then exposes read-only directory listing and short-name file reads through `storage.volume`. Absolute paths may contain up to four ASCII case-insensitive 8.3 components; dot traversal and long names are rejected. One directory and one file cursor are supported; directory scans are capped at 128 sector reads or 3 seconds, file chains at 1024 hops, and each file-read call copies at most one sector. Partial reads reuse the already CRC-checked sector. Writes and remove remain unsupported. CRC or invalid chain during file access invalidates the mount until `refresh()` succeeds. A host card model exercises nested listing, a two-cluster 600-byte file, partial reads and sector reuse, EOF, invalid clusters/chains, write rejection, CRC failure, recovery, stale-handle invalidation, both volume layouts, invalid metadata, missing data token and pin ownership. The enlarged provider builds with `-O2 -Wl,--no-relax`, verified by Linux CI run `37048644826` after the pinned Xtensa linker aborted under smaller optimization layouts. The owner's `94c14bf6` screen report supports successful FAT/root sector probing on that earlier image; physical file access in 0.1.8 remains untested. The X4 bootstrap looks for the first short-name `.TXT` file in `/Books`, then in `/`, and exercises Reader's existing `Txt::load` and `Txt::readContent` through a read-only `HalStorage`/`HalFile` binding before scheduling Home. File contents stay off serial logs. The binding implements read-only existence, file listing/open/read and bounded seek; mutations still fail closed, and it never initializes SdFat/SPI on the X4 SDMMC pins. The one-file provider and 128 KiB bounded seek limit still prevent general book support.

Partition layout in this tree is app0 at `0x10000` size `0x640000` and app1 at `0x650000`. The build emits both an app-only image for offset `0x10000` and a merged image for offset `0x0`. The merged image includes bootloader, partition table, OTA initializer and app0. Flashing it replaces the partition table and erases the NVS range because its NVS bytes are `0xff`. The exact `5e1f8343` image was physically installed and read back successfully on the identified X4; the private prewrite 16 MiB backup remains verified. Other stock variants remain unqualified.

The X4 first Home frame selects the built-in Classic theme, omits the T5S3 battery icon, and uses a monochrome Home card. The first physical Home report on `5e1f8343` exposed a landscape-versus-portrait mismatch: Home was laid out in 800×480 while shared button hints were drawn in portrait, leaving a negative Classic menu height. Current source selects 480×800 portrait, rejects undersized Home menu geometry, and shows one bounded clean startup frame before Home so a reset has a visible transition. The startup present state is cleared before scheduling Home; `home present=1` is logged only for the later successful Home present. The delivered `afebe686` full merged image has this first frame; the later delivered `dea3484e` image adds focus movement but no file destination. Current source adds a bounded read-only TXT destination after the first successful Home present. It scans at most 32 entries in each of `/Books` and `/`, retains at most 12 safe short-name `.TXT` paths, and opens only files of at most 128 KiB. Each 160-byte page is read through provider-backed `HalStorage`, sanitized for on-screen display, and never logged or written. Missing media, missing files and read/close errors return to a safe list status. A provider close failure retains the file-ownership gate rather than admitting a second handle. Apps, Settings, general recents, EPUB, writing, sleep/wake and optional services remain outside the supported X4 destination set. The malformed `5e1f8343` Home frame was physically observed; the portrait correction and TXT browse are still untested on device.

The owner later reported that the portrait Home is improving but buttons and touch do not navigate, and that the X4 Home rows should match T5S3. Source inspection found the X4 path bypassed the normal Reader activity loop, did not initialize `ButtonNavigator`, did not embed or start GT911, and changed Recent books to TXT Files. The software changes above address those causes; they have not been flashed or physically qualified. X4 automatic hardware tests are paused after a later cloud-artifact app write lost its USB port mid-write. Its exact prewrite app was restored with readback, protected-region hashes, Home boot and ready heartbeats verified. A separate one-shot USB stability diagnosis is needed before resuming unattended writes. Deferred: general Reader book operation and Home destinations beyond the TXT subset, charge-status polarity and sleep/wake policy.
