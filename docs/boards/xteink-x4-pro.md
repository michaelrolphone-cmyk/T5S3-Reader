# Xteink X4 Pro drivers

Board packages for the Xteink X4 Pro. They publish the existing RiscRTE capability ABI (`risc_driver_v2`, export `t5_driver_get` only) and do not reuse the T5S3 panel, touch axis, or I2C pin ownership.

Pin and protocol facts are derived from pinned CrossPoint/FreeInk firmware and driver sources. On the physical X4 Pro, the UC8279 full refresh completed and the owner confirmed visible blocks and later visible text. The owner manually installed the CI-built full merged image from PR commit `94c14bf6` and reported the on-screen message `SD card found; files unavailable`. That image probes FAT32 boot/root metadata but intentionally keeps file access unavailable, so the observation supports that limited path and does not establish a mounted filesystem. Later PR changes have CI evidence only. No camera images are in the repository.

Load order: `platform-clock-v1`, `x4pro-i2c`, `x4pro-panel`, `x4pro-gt911`, `x4pro-buttons`, `x4pro-frontlight`, `x4pro-battery`, `x4pro-sd`.

## First diagnostic boot

`env:xteink-x4-pro` does not call `HalSystem::begin()`, so the legacy T5S3 peripherals cannot be started on this path. It loads embedded `platform-clock-v1`, `x4pro-panel`, `x4pro-buttons`, `x4pro-frontlight`, and `x4pro-sd` through `ProviderModuleV2::loadVerifiedBytes`. `ProviderDisplaySurface` validates the provider geometry, translates Reader MONO1 polarity, and makes bounded `display.output` presents. The global Reader `HalDisplay` and `GfxRenderer` now forward through this provider instead of using physical panel code in firmware. The unmounted-storage path enters the existing Reader `FullScreenMessageActivity` synchronously; it does not start the normal render worker before its power and storage dependencies are ready.

The verified buttons ELF is borrowed by the existing `NativeNavigationInput` consumer. Its module remains owned by the X4 boot controller; the consumer refuses a handoff while installed-provider grants are live and refuses to claim sleep quiescence for that borrowed module. Power maps to Confirm. The `x4pro-buttons` 0.1.3 provider requires a neutral button state after startup or a UI focus reset before emitting new edges. The hardware button path has not yet been confirmed by a user press on the current image. Frontlight stays off.

GPIO1 is the recovered peripheral-enable name from the pinned FreeInk X4 Pro notes. This diagnostic does not drive it, and it does not assert what that rail powers. Touch power GPIO2 stays untouched. `x4pro-sd` alone controls the active-low SD power gate GPIO5 and native one-bit SD CMD42/CLK41/DAT0 40; its power cycle uses the pinned board source's 80 ms high and 120 ms low intervals. Pinned FreeInk commit `111fdcc7f0176c3ee38391a160ee296bf492dbd8` supplies the SSD1677 full refresh sequence and the UC8279 X4 Pro 800×480 visible / 800×600 addressed, 120 gate offset, full GC waveform sequence. The provider confirms a UC8279 `VER[2]=0x68` identity with a second read and idle BUSY before issuing UC commands. Other UC81xx variants remain unsupported. SSD and UC use their respective BUSY polarities and bounded waits. The provider version is `x4pro-panel 0.1.12`; the UC power-on wait gives BUSY_N one tick to assert before rewriting PSR. Failure logs include the version, probe bytes, elapsed time, budget, and a specific reason.

## Storage prerequisite for Home

The `x4pro-sd` 0.1.7 provider sends bounded native SD initialization commands, selects the card, reads CRC16-checked sectors over DAT0, and locates a FAT32 boot sector either at LBA0 or through one MBR FAT32 partition. It validates FAT32 geometry and root chain, then exposes read-only root directory listing and short-name file reads through `storage.volume`. One directory and one file cursor are supported; root scans are capped at 128 sector reads or 3 seconds, file chains at 1024 hops, and each file-read call copies at most one sector. Long names, subdirectories, writes and remove remain unsupported. CRC or invalid chain during file access invalidates the mount until `refresh()` succeeds. A host card model exercises listing, a two-cluster 600-byte file, partial reads, EOF, invalid clusters/chains, write rejection, CRC failure, recovery, stale-handle invalidation, both volume layouts, invalid metadata, missing data token and pin ownership. The enlarged provider builds with `-O2 -Wl,--no-relax`, verified by Linux CI run `37048644826` after the pinned Xtensa linker aborted under smaller optimization layouts. The owner's `94c14bf6` screen report supports successful FAT/root sector probing on that earlier image; physical file access in 0.1.7 remains untested. The X4 bootstrap passes the first root `.TXT` short-name file through this API and shows sanitized 48-byte chunks in the existing Reader message activity; Right advances to the next chunk and EOF closes the handle. If no matching file exists, it says so. This is a limited forward-only read workflow, not the normal Home or book reader. File contents stay off serial logs. All legacy `HalStorage` calls still refuse SdFat access on X4, whose slot is SDMMC; normal book reading requires a Reader storage adapter and remaining power/input lifecycle cutover.

Partition layout in this tree is app0 at `0x10000` size `0x640000` and app1 at `0x650000`. The build emits both an app-only image for offset `0x10000` and a merged image for offset `0x0`. The merged image includes bootloader, partition table, OTA initializer and app0. Flashing it replaces the partition table and erases the NVS range because its NVS bytes are `0xff`. Stock layout compatibility and current hardware behavior remain unverified.

Deferred: full Reader storage binding and normal Home/activity loop, GT911 sequencing, charge-status polarity, I2C 39/38 after the high-bank GPIO fix, and sleep/wake policy.
