# Unified Package Manager — MVP, actual implementation and remaining acceptance

**Status: merged foundation, incomplete full management experience, September 18, 2026.** This document is the normative package-manager branch under [RISCRTE_PLATFORM_SPEC.md](RISCRTE_PLATFORM_SPEC.md), [RISC_PACKAGE_FORMAT.md](RISC_PACKAGE_FORMAT.md) and [PACKAGE_MANAGER_SCOPE_CONTRACT.md](PACKAGE_MANAGER_SCOPE_CONTRACT.md). The **next implementation milestone**, task order, source audit and one hardware-test handoff are [NEXT_HARDWARE_TEST_MILESTONE.md](NEXT_HARDWARE_TEST_MILESTONE.md). Historical references to PR #76 as a draft or to an App Store/Driver Manager that has not been migrated are superseded; do not reimplement delivered work simply because old text says it is absent.

## Authorized goal

One ordinary source-independent package model and manager for four distribution kinds, `application`, `driver`, `service`, `provider`. They are package manifest classifications, not four separate transaction engines or an instruction to invent new runtime services. A driver can be a capability provider; the taxonomy does not make the runtime hardware-aware. Both SD and online delivery use one bounded manifest/preflight, compatibility/dependency plan, file verification, stage/commit/recovery, installed inventory, update/uninstall and use-gate. The App Store, Driver Manager and Package Manager are UI views/adapters over this engine; installation does not activate hardware or grant privileged imports. The same requirements apply regardless of download source.

**No signing ecosystem is authorized.** No mandatory P-256, signature verification, signer provisioning, keys, trust roots, allowlists, revocation, signed provenance, cryptographic security floors, secure boot or anti-rollback. The owner now explicitly requires the signing-specific experiment to be **purged from the active repository**, not archived or kept as an optional implementation. Preserve useful non-authentication validation, SHA-256 content-integrity checks, safe paths, ELF/architecture/ABI checks, independent loader import/relocation authorization, executable-byte ownership, mapping pins and crash-consistent replacement. A checksum is neither trusted-publisher identity nor permission to execute privileged code. Preserve TLS and generic cryptography unrelated to package signing.

## What exists and must be preserved

Merged PR #76 supplied a four-kind ordinary engine alongside an unnecessary signed-format experiment. Merged PR #78 supplied the real driver/privileged-loader/provider foundation; #79 connected App Store and Driver Manager and installed physical USB providers to the ordinary pathway. #80/#81 addressed installer/runtime watchdog and stack/download-recovery problems. The user reports having successfully tested most package-management paths; retain existing app/driver behavior and separately log the precise cases still untested.

Concrete useful components include `PackageIdentity.h`, `PackageJsonGuard.h`, `PackagePreflight.h`, `PackageOrdinaryManifest.h`, `PackageOrdinarySdAdapter.h`, `PackageOrdinaryTransaction.h`, `PackageOrdinaryStageRecovery.h`, `PackageUseGate.h`, `InstalledCapabilityResolver.*`, `NativePackageManagerBridge.cpp`, `NativeOnlineAppInstall.h`, `NativeOnlineDriverInstall.h`, `AppPackageRecoveryInventory.cpp`, `DriverStageActions.cpp`, and `InstalledProviderGraph`/`DeviceProviderExecutorV2`. This list is an inventory guide, **not** an assertion that every function and code path is complete. Existing app legacy ELF/JSON source conversion, driver four-file online conversion and offline inbox work are real. The Driver Manager already exposes an offline recovery screen; do not erase those features while unifying the surrounding API.

Current limitations requiring completion: `Apps/package_manager.c` is primarily an SD inbox view; `T5PackageManagerApi.h` exposes preview/install/uninstall but not a full common installed/online discovery, update/inventory interface. Driver Manager uses a special hard-coded USB canonical index plus a separate legacy driver catalog, and hard-codes a four-file download. App Store has an app-specific online source adapter; four-kind online catalog and UI lifecycle parity is not complete. The ordinary engine handles four kinds internally, but exposing an enum does not demonstrate online/offline UI and fault/recovery acceptance for all four. Existing manifest/capability policies still identify the architecture as Xtensa ESP32-S3. These facts are **not** reasons to refactor the validated normal transaction from scratch.

## Canonical package and source contracts

The normal on-disk form is a bounded ordinary `.package.json` declaring kind, ID, version, executable/resource file inventory with lengths and integrity digests, architecture/ABI and dependencies. Legacy loose app/driver assets may be converted by bounded compatibility *input adapters* into this model. The same ordinary engine verifies all bytes and uses manager-owned exclusive staging, installed-generation verification, preservation of previous generation, restart recovery, active mapped-ELF replacement refusal, in-use uninstall controls, explicit diagnostic result and separation of installation from activation. Only the provider executor/runtime grants independently allow privileged imports and capabilities; a manifest cannot self-authorize.

The **generic online catalog** is only a discovery/locator index generated from the package manifests and real release outputs. It exposes all four kinds and their versioned asset sets; it is not a package's sole inventory, loader authorization, special USB profile or prerequisite for offline work. Pin index and downloads to one immutable release; revalidate downloaded source metadata, size/hash, manifest/dependencies and staged content via the ordinary engine. No independent latest-release URL per component. Online catalog absence/corruption must not hide installed packages, prevent local uninstall, stop driver activation or block SD install. A new supported driver or package must join the index without editing a firmware driver enumeration or seven-entry build list. Publication must reject stale/missing/conflicting assets. See [U1 B](NEXT_HARDWARE_TEST_MILESTONE.md#workstream-b--finish-the-generic-manager-and-remove-usb-catalog-coupling) for the removal of `usb-provider-catalog.json`, fixed driver file/count assumptions, legacy importer disposition, and production-source regression gates.

### Shared management API and UI

Extend the existing generic SDK append-only with bounded `catalog_refresh/count/get`, `installed_refresh/count/get` and explicit preview, install/update, uninstall, and recovery inspection/retry/discard functions as needed. Version/`struct_size` guard newly appended entries; avoid breaking existing apps. Keep package kinds and state machine in common manager, with App Store filtering applications and Driver Manager filtering drivers, while Package Manager exposes all four and both installed/online/SD source views. Show dependency plan and precise failure, version, in-use/pin and previous-generation states. No UI owns an alternate transaction. Compatible manifest-driven dependencies may be installed in plan order only after explicit installation request; installation alone never starts the driver. Test fixtures for service/provider classification do not require building unrelated production services.

## Acceptance and stop rule

The manager is complete for this milestone only if **all** kinds can be inspected, inventoried, installed, updated and uninstalled through a common engine from appropriate offline/online routes; recovery and in-use protection work, prior installs survive bad inputs, catalog independence is demonstrated, and the UI/APIs expose those operations. The package-signing experiment is gone from production and repository source without losing content integrity or independent loader policy. Provider dependency installation is generic, and the entire USB stack can be installed without a special catalog. CI/host success does not imply physical USB success. The owner decides when to merge/publish/flash/test; incomplete U1 work continues in the same branch/PR. [U1 definition of done](NEXT_HARDWARE_TEST_MILESTONE.md#4-definition-of-done--milestone-stop-rule) is the single software handoff gate.
