# U1 glanceable progress reporting

**Mandatory; September 18, 2026.** Read with [Three-Step Implementation-First Workflow](IMPLEMENTATION_FIRST_QUALIFICATION_WORKFLOW.md), [U1 Continuation Protocol](U1_CONTINUATION_AND_COMPLETION_PROTOCOL.md) and [AGENTS.md](../AGENTS.md). The owner glances at the screen briefly. Keep updates to a few factual sentences: substantive code changed (commit/PR when confirmed), relevant actual check/failure, and next action or genuine blocker. Put logs and longer inventory in a concise implementation ledger. Do not constantly rehearse eventual physical testing, report imagined PASS, idle for CI or substitute documentation for source implementation.

**Absolute final line:** Every U1 response ends with ONE standalone Markdown-bold **2–5 word** current-state label, with NO text after it. Use these labels to convey the owner's EXACT THREE WORKFLOW STEPS:

1. **Work Complete** — exact initial announcement at the moment all requested IMPLEMENTATION code is actually finished and connected with no known blocking defect. It is an implementation-completion signal, **not** a claim of hardware testing, release qualification, all-green CI or publication. The message above it names the implementation PR/commit and honestly states what was checked/not checked. This exact phrase is the final line, not followed by a redundant fourth-state label.
2. **Improving Code** — on EVERY subsequent owner `continue` after Work Complete while the owner has NOT explicitly initiated Release Qualification. Actually audit code, add focused durable tests, improve diagnostics/performance or fix discovered defects; do not ask for hardware testing or simply repeat status. If a newly found blocker invalidates Work Complete, temporarily revert to **Implementation In Progress** while repairing it, then re-announce Work Complete when repaired.
3. **Release Qualification** — ONLY after the owner explicitly advances to joint testing/qualification. Test and patch together, establish release assets/revision here, report honest evidence and await owner acceptance. A qualified release is an outcome of this third step, **not** a fourth workflow state. Do not claim qualification before it is accepted or merge/tag/flash/publish without instruction.

During initial implementation BEFORE the Work Complete signal, use **Implementation In Progress**. That is a progress label before step one, not an additional milestone stage. Temporary truthful blockers may override the phase label: **Build Failure Under Repair**, **GitHub Quota Blocking Work** only on confirmed GitHub rate limiting, or **GitHub Access Unavailable** if failure cause is unconfirmed. Explain the evidence immediately above any blocker label, and never invent a quota reset. The final label must reflect the current actual state, not a finished subtask. No separate `Software Ready For Testing`, `Implementation Complete Awaiting Qualification`, `Post Completion Audit Active` or `Release Qualified Awaiting Authorization` statuses: these would fracture the owner's three-step workflow.
