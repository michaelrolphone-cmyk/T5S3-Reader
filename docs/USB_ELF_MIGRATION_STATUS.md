# USB ELF migration: implementation status and acceptance

**Authority:** [RiscRTE master specification](RISCRTE_PLATFORM_SPEC.md), [hardware-agnostic driver boundary](HARDWARE_AGNOSTIC_DRIVER_BOUNDARY.md), [runtime driver architecture](RUNTIME_DRIVER_ARCHITECTURE.md), and [USB architecture](USB_OTG_HOST_ARCHITECTURE.md). This document records implementation facts, not relaxed acceptance criteria. **The current shipping firmware still uses the legacy compiled USB path. Do not install experimental ELFs on a board.**

## Actual experimental provider stack

```text
CDC ACM ELF / CP210x ELF --requires usb.host@1---------> USB host ELF
USB host ELF -------------requires usb.controller@1----> ESP32-S3 controller ELF
ESP32-S3 controller ELF ---requires board.power.vbus@1-> independent board-power ELF (NOT IMPLEMENTED)
```

- `Drivers/usb_cdc_v2` implements CDC ACM descriptor matching including IAD/union and unambiguous nonzero alternates, control/data claims, line coding, DTR/RTS, bulk I/O, and stale session rejection. Multi-function selection is not supported by the existing `open(device)` entry point; ambiguous configurations reject.
- `Drivers/usb_cp210x_v2` implements CP210x UART enable/disable, baud, format, modem controls, vendor matching, bounded sessions, and bulk I/O. VID-only matching is experimental; precise PID/profile and physical hardware validation remain outstanding. Both class ELFs independently provide `serial.port@1` and consume `usb.host@1`.
- `Drivers/usb_host_v2` is an actual independent provider of `usb.host@1` requiring `usb.controller@1` from a DIFFERENT ELF. It implements provider-originated discovery, generation-qualified device/claim tokens, exclusive interface claims, selected alternate and endpoint descriptor checks, endpoint-direction gating, stale-device transfer rejection, and fail-closed release/quiescence. Its provider-level `poll()` and `devices()` do not yet feed the transport-neutral Unified Device Registry; a serialized provider executor is not yet integrated.
- **`Drivers/usb_controller_esp32s3/driver.cpp` implements an experimental PHYSICAL `usb.controller@1` provider**, not a firmware USB proxy. It calls ESP-IDF USB host install, client/device events, descriptor queries, interface operations, real control/bulk transfers and DMA allocation, and attempts bounded hardware teardown. It requires a separate `board.power.vbus@1` dependency. `scripts/probe_usb_controller_esp32s3.py` rebuilds pinned ESP-IDF v4.4.7 USB host/PHY/HAL/SoC sources as PIC and links them *inside the ELF*. ESP32-S3 peripheral MMIO addresses are read from that pinned IDF's target linker file rather than fetched from firmware symbol tables. USB PHY-specific GPIO pad drive is implemented in the ELF (`phy_gpio.c`), restricted to the SoC's internal USB data pins. The normal firmware GPIO driver is not used as a USB forwarding shim. **This controller is not installable or hardware-validated.** Its remaining kernel import requirements, VBUS dependency, controller/host executor, teardown/recovery behavior and physical electrical safety block deployment.

Generic `RiscProviderV2.h`, `ProviderModuleV2`, and `ProviderGraphV2` validate preverified root identities, resolve exact versioned requirements, pin dependent providers, reject cycles and ambiguous providers, and quarantine failed quiescence/unload. They do not contain USB-specific control flow. They are **not yet connected to signed package verification, production manifest discovery, execution-context authorization, rights/consent policy, registry publication, or stream dispatch**; current tests serialize calls and require caller-owned validated manifest strings.

## Verified tests, and precisely what they prove

Host tests exercise CDC and CP210x control/bulk behavior, CDC composite descriptors, graph grant/dependency lifetime, host attach/detach generations, exclusive claims, authorization of endpoint transfers and fail-closed teardown. `test/run_usb_three_elf_stack_v2_test.sh` separately loads a TEST-ONLY simulated controller ELF plus the real host ELF and real CDC ELF through the generic graph; it cannot prove a physical controller works. The mock is never a release package.

The physical controller PIC build and link, along with CDC, CP210x and host cross-builds, passed experimental CI [run 35245810058](https://github.com/michaelrolphone-cmyk/T5S3-Reader/actions/runs/35245810058). `scripts/audit_usb_controller_elf.py` checks ELF architecture, actual firmware symbol exports, the structural validator's relocation types and mapped targets, text relocations, and unauthorized dynamic exports. Experimental CI [run 35246640672](https://github.com/michaelrolphone-cmyk/T5S3-Reader/actions/runs/35246640672) passed native structural validation: 590 relocations accepted, zero text relocations, no unexpected exports, but **43 undefined names absent from current firmware export tables**. SoC GPIO table and pinned MMIO linker changes reduced that to **37** in [run 35247079244](https://github.com/michaelrolphone-cmyk/T5S3-Reader/actions/runs/35247079244). Driver-owned PHY GPIO drive then reduced the count to **36**, confirmed with the full successful experimental [run 35247590112](https://github.com/michaelrolphone-cmyk/T5S3-Reader/actions/runs/35247590112). The audit writes `controller-loader-audit.json`, retains `loader-abi-blocked` until all imports are valid, and always labels the build non-installable. CI artifacts are inspection-only, not package-catalog or release artifacts. A successful firmware build or cross-link is never proof of safe on-device operation.

## Work still required before USB migration can ship

1. **Actual loader and generic OS/CPU ABI compatibility.** Resolve remaining unexported FreeRTOS task/queue/synchronization, interrupts, memory allocation, logging, ROM GPIO and assertion symbols via a narrow, versioned, *hardware-agnostic* kernel/SoC port or independently owned driver code as appropriate. Verify actual native loader resolves all imports and handles every relocation, then implement executor ownership and safe cross-thread/ISR callback lifetime. No USB-named resident forwarding exports. Keep strict install gating until these checks pass.
2. **Independent board-power provider and hardware ownership.** Implement actual T5S3 board electrical policy behind `board.power.vbus@1`: external VBUS detection, charger/boost/role conflicts, host source-current limits, VBUS rise and shutdown verification. Block activation when the legacy firmware still owns OTG/PHY or the power profile is unsafe. Implement genuine cancellation, finite transfer drain, hub state and lost-event recovery without resetting token generations incorrectly. A failed release must prevent ELF unmapping.
3. **Generic production integration.** Connect trusted/verified manifests, context-owned grants, generic provider graph, serialized executor, generic registry publishing, cancellation and bounded streams. Implement remaining CH34x and other chipset providers plus qualified device selection. Do not allow the experimental controller or class artifacts into a user-installable catalog until all gates pass.
4. **Physical board acceptance and cutover.** Verify T5S3 cold boot, charger/VBUS/USB role safety, hub and multiple devices, attach/replug, unplug mid-transfer, CDC/CP210x baud and DTR/RTS, sustained duplex, timeout/cancellation, callback/DMA teardown, install/remove capability disappearance and no firmware fallback. Only after parity is demonstrated switch Serial Monitor and remove `NativeUsbBridge`, compiled `UsbCdcDriverRuntime`, USB-specific registry projections and hardcoded firmware routing from the normal runtime. Recovery bootstrap, if retained, must remain isolated.

**Status:** Draft PR #78 has real experimental CDC, CP210x, host and ESP32-S3 hardware controller *source and linked ELF*, plus generic dependency machinery. The controller is **not loadable under the shipping firmware's export ABI, not paired with a physical VBUS provider, and not validated on hardware**. Normal firmware USB and Serial Monitor are unchanged; USB migration remains incomplete.
