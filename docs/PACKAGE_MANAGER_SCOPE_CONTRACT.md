## Explicit objective and authorized requirements

Provide **one common ordinary package manager** for `application`, `driver`, `service`, `provider`, with complete offline SD and online discovery/input, inspection, inventory, installation, update, recovery and uninstall. Four manifest kinds are not four engines or a mandate to add new services. Preserve the already delivered and mostly owner-tested package paths from merged PRs #76/#79. Complete the API/UI and source integration rather than replacing working code with a new format. Use a bounded ordinary `.package.json`/payload manifest or compatible legacy input adapter, checked ID/version, architecture/runtime ABI, resource paths, dependencies, ELF/import bounds, declared length and SHA-256 file-content integrity. A digest does **not** authenticate a publisher or grant privileges.

Use a common, source-independent preflight and transactional stage/publish/recover/uninstall engine, preserving prior installations on failure, refusing replacement of active/pinned modules and avoiding deletion of unmanaged data. Inventory and uninstall must work offline; installation must not activate hardware. Privileged imports, execution-context identity, capability grants and provider physical ownership are enforced independently by the loader/runtime. The normal core never hard-codes USB or other hardware to decide which provider/package to install or load.

One generic, manifest-derived online source index covers all kinds; it is only a locator and must be pinned with its assets to the same immutable release snapshot. It cannot authorize execution, select USB chipsets, or block offline operation. The old `usb-provider-catalog.json`, hard-coded seven-driver exporter, fixed latest-release URL/four-file installer and special canonical/legacy overlay are migration targets and must be removed from production source/build/release by U1 completion. Legacy loose app/driver compatibility is permitted only as a bounded input adapter to the ordinary engine, with explicit deprecation rather than a second manager.

**Current architecture objective:** full normal-firmware USB extraction, provider-originated generic registry publication and streams, and Serial Monitor via arbitrary `serial.port`. Its detailed ownership and source-removal acceptance are specified in U1 and the hardware boundary. An ELF descriptor proxy or a firmware-side USB compatibility bridge that still selects VID/PID, device classes, USB sessions or hard-coded ELF IDs is not completion.

## Cryptographic work: purge, not defer in the active tree

The owner explicitly requests removal of unwanted package cryptography. Delete package-specific P-256/signature code, signing/key/trust/revocation APIs, signed RISC-PKG archive, signed provenance/receipts, NVS cryptographic security floors, signed-only loader assumptions, signing scripts/fixtures/tests, special release gates and experimental signed-format docs from the active repository **after** a complete reference/reachability audit and extraction of any independently useful generic behavior. Do not merely move signing into an `experimental` directory, keep a disabled shipping path, make it optional-but-linked, or substitute another publisher-authentication system. The historical work remains recoverable from git history; no history rewriting or deletion of published historical release assets is required.

Preserve independently useful defensive validation, SHA-256 corruption detection, file/ELF/ABI/import checks, manifest preflight, safe paths, exact candidate bytes, generic permission checks, context ownership, stage/recovery transactions and module lifetime/quiescence protections. General OS/network cryptography, including existing TLS, is not package-signing scope creep. Do not silently erase prior user-installed signed-only data; validate read-only against ordinary format or return an explicit unsupported/migration-required error. A digest supplied by a package is never authority to load privileged symbols.

No new signer, trust key, anti-rollback security floor, alternate cryptographic identity system, new mandatory package format, unrelated hardware subsystem, new physical hardware in the core, or broadened release gate may be introduced without an explicit new user request. A broad long-term roadmap section or perceived best practice is not approval. Future signing is no longer an active repository proposal; if separately requested later, it needs a new scope, threat model, consent, implementation and compatibility plan.

## Completion and workflow

The next unit is **one completed software milestone U1**, not a series of owner hardware tests after small edits. Internal workstreams inventory, manager/catalog, crypto purge, USB extraction, integrated software tests and acceptance documentation may be committed incrementally on the same branch/PR. They are not independently shippable completion claims. The owner has tested most package-manager paths but not the USB driver/Serial Monitor chain; do not require those USB results to plan or develop the rest. Only after the integrated work is software complete and build/test/source-link evidence is recorded should the owner receive **one** hardware test procedure and exact coherent firmware/app/driver revisions. Record physical validation as PENDING until performed; no CI result is a hardware test.

Never wait idly for CI to finish before moving to an independent next workstream; inspect CI opportunistically, correct failures as evidence becomes available and preserve a precise in-PR progress ledger across prompts. At handoff, do not misreport pending or failed jobs as passed. Do not auto-merge, tag, publish, flash or create unnecessary approval-triggering workflows. One PR targets `master`; do not stack dependent PRs. A genuine error requiring unsafe hardware experimentation is explicitly documented rather than bypassed.

## Change-control gate for each subsequent task

Record (a) explicit user objective, (b) required deliverables, (c) excluded/deferred features, (d) acceptance criteria, and (e) basis of mandatory dependencies. Classify additions as REQUIRED (directly necessary), OPTIONAL (separable and nonblocking) or DEFERRED (not authorized now). On mismatch, stop extending unrelated scope; audit concrete references and retain independently useful working code while deleting unwanted package-authentication implementation. Correct source, specs, tests, build and release together, and never claim a specification update is already an implementation change. Prove USB absence by production-source and link/reachability inspection and driver-removal behavior, not a renamed facade or a successful ELF build alone.
