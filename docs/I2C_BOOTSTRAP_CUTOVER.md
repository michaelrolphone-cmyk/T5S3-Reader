# Temporary firmware I²C bootstrap and dependency-safe ELF cutover

**Normative, September 18, 2026; specification only.** Owner-authorized exception to [hardware-agnostic boundary](HARDWARE_AGNOSTIC_DRIVER_BOUNDARY.md) during U1–U3. This document overrides earlier absolute language requiring an I²C controller ELF before USB/power driver conversion, or forbidding any firmware I²C calls during that transition. The final platform remains hardware-agnostic; this exception must not become a permanent core I²C driver. No code, hardware verification or completed cutover is implied by this specification.

## Dependency problem and milestone allocation

On the T5 Pro, power/expander peripherals may be reached over I²C, and their driver ELFs can be prerequisites for enabling other buses and devices. Requiring an installed I²C ELF to be fully initialized before the power/expander drivers that may themselves enable that I²C bus risks a bootstrap cycle. Do not block extraction of USB or every dependent driver on a fully converted I²C controller. Verify the actual board power tree, which rails enable which pins/controllers and which components are genuinely fitted before declaring any dependency cycle. Use the existing USB migration's temporary I²C implementation as the starting point where compatible; inspect its actual source and ABI rather than assuming implementation completeness.

- **U1:** Build the generic provider/stream/capability foundations first. Permit a deliberately small, clearly identified **transitional platform I²C API** so the power/expander ELFs and USB driver stack can perform their actual device work during cutover. USB host, class, enumeration, chipset logic and protocol state still belong entirely to ELFs. An independently packaged I²C ELF may be built and exercised in U1, but full I²C ownership transfer is **not a U1 Work Complete gate**. The U1 cross-family witness may consume this temporary bus API without being described as a completely extracted bus.
- **U2:** Package, release, and version providers without hard-coded firmware device or source selection; carry the transitional API only as an explicit versioned dependency while still required. No I²C cutover prerequisite for independent package publishing.
- **U3:** Migrate actual T5 Pro I²C clients (power, expander, touch, RTC, charger/gauge and other verified parts) into functional ELFs; dissolve the verified bus/power bootstrap cycle, then transfer runtime I²C bus ownership to one installable I²C controller/provider ELF. Convert those consumers to its capability without changing the generic runtime. Remove the transitional firmware API and its normal runtime call sites **before U3 Work Complete**. Keep only genuinely isolated, documented minimal recovery/bootstrap support if board-specific boot facts prove it unavoidable; it must never publish a normal I²C capability, service installed drivers, or become a fallback.
- **U4:** Headless provisioning and CAM drivers must use installed providers or the independently specified minimal boot/ROM port; they must not silently rely on the T5 Pro's transitional I²C API. No extra camera/I²C features beyond the one-image proof.

## Strict scope of transitional firmware API

Place it in an explicitly named platform/port compatibility module **outside generic resolver, registry, streams, package manager and UI logic**. Expose a minimal versioned I²C primitive to authorized installed driver ELFs: bounded bus acquisition/release and combined transfer (address, write/read lengths, timeout/result) plus minimal necessary pin/clock setup where verified. It must have fixed bounds, finite timeouts, proper ownership and reentrancy, error propagation, and a single bus controller owner. A neutral generic resource lease may enforce exclusive controller access; a firmware adapter may serialize its own physical transfers while transitional. Do not expose arbitrary firmware objects/pointers, unbounded transactions, global `Wire` access to applications, persistent callbacks into unloaded ELFs, or implicit bus reinitialization on every driver call.

The adapter may initialize and transfer on the bus **only** for this cutover; it may not interpret device addresses as semantics, perform register-level device behavior, choose USB/GPS/charger/touch models, manage device power policy, enumerate devices into the registry, publish `i2c.*` as a permanent firmware provider, or grant permissions merely because a caller has an ELF. Driver ELFs own individual device matching/probe, register sequences, actual peripheral behavior, interrupts, power-state policy, error recovery and teardown. Limit allowed callers to the installed packages explicitly migrating; make dependencies, active platform and temporary status visible in manifest/docs/implementation ledger. This is a temporary bus primitive, **not** the thin-proxy-driver pattern that previously kept actual device implementations in firmware.

## Non-cyclic transition and handoff

Inventory the *real* dependencies and draw the minimal directed graph: immutable CPU/port/boot-module storage → transitional I²C bus (when needed) → early power/expander ELF → downstream USB/peripheral ELFs. Power/expander drivers must never depend on the very controller/rail that requires their own startup unless an independent safe bootstrap path exists. Keep GPIO and rail defaults safe before all probes; no speculative enables.

For cutover, ensure the installable I²C provider can start with a noncyclic set of CPU/port primitives and verified power prerequisites. Stop admissions, quiesce all transitional clients, drain/revoke outstanding bus operations and leases, set a safe pin/rail state, release/deinitialize the firmware controller, then let the ELF claim and initialize it. Never run both controllers on the same bus concurrently; no silent runtime switching back after ELF removal/failure. Restart clients through the ELF capability and its generation-safe handles; failed takeover must fail closed or enter an isolated safe recovery mode. A bootstrap implementation may exist only where real module-store access or recovery requires it, never as a normal installed-device provider.

**U1 acceptance:** USB and its power/expander devices are operationally implemented in ELFs using only the explicitly scoped temporary I²C primitive as needed; no firmware USB logic or other device-specific proxies; missing I²C/driver dependency produces a clear failure without circular startup, race or unsafe rail state. Document remaining firmware I²C API callers and the U3 removal action rather than claiming complete I²C extraction.

**U3 acceptance:** installed I²C ELF exclusively controls normal bus transfers, T5 peripheral ELFs consume its capability, no transitional firmware I²C calls remain in the normal driver path, and unload/absence cannot invoke a hidden fallback. Check boot and driverless headless CAM independently. Hardware success is owner qualification only; implementation and source/build results must be reported accurately.
