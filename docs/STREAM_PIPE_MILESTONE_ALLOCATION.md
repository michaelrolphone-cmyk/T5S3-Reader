## 2. U1 — mandatory stream foundation BEFORE generic USB/packages are declared complete

U1 already requires provider-owned USB, generic `serial.port`, all-kind package lifecycle and one `.rte.zip` distribution. The following are the **minimum necessary stream integrations** to implement those same outcomes without forcing U2–U4 to rewrite the data plane:

1. **Installed-ELF producer/consumer attachment.** Extend the existing, single stream registry/API append-only with a transport-neutral provider endpoint contract for byte and typed-record producers/sinks. Bind an endpoint to an installed provider instance, capability/API version, generation, actual execution-context owner and required rights. Define safe dispatch/borrowed buffer lifetime and module pins; never store raw ELF callbacks past quiescence or route data through an old `firmware-owned USB provider` vtable. A provider can publish one or several independent endpoint instances. A non-USB witness should use the SAME mechanism where it produces sustained data. Do not instantiate a new USB, GNSS, LoRa or camera stream registry.
2. **Cross-context connection and authorization.** Distinguish provider-owned endpoint lifetime from consumer/job-owned pipe lifetime; current same-owner-only lookup cannot serve independently resident provider ELFs and apps/services. Define a generic authorized endpoint-open/connect/close operation through capability resolution, grant validation, endpoint direction/schema/limits and generation checks. On disconnect, revocation, stop/unload or unsafe quiescence, stop scheduling, cancel/drain according to explicit policy, revoke downstream handles, release leases and pin code until in-flight I/O is safely stopped. Protected data cannot be copied into an unprotected sink: implement the required generic downstream permission/retention/purge policy for a protected record pipe or explicitly reject that flow until the policy exists. Eliminate reliance on an unguarded record buffer as an authorization token. Keep byte v1 and record v2 ABI binary-compatible and add only versioned/size-guarded extensions.
3. **Complete the U1 serial/programmer data path.** Replace `NativeStreamBridge` USB read/write/open and `NativeSerialPortBridge` USB projection, hard-coded USB selection and stream pair with streams supplied by actual installed CDC/CP210x/etc `serial.port` ELFs. Preserve separate versioned baud/framing/DTR/RTS control plane. Serial Monitor and ESP ROM programming must consume the same semantic serial RX/TX, generation-safe revocation, and bounded firmware source stream. A fallback inside compiled normal firmware does not count. Existing Serial Monitor and Flasher ELFs should be adapted, not rebuilt as unrelated applications.
4. **Use shared streaming for every U1 package ingress.** Online catalog/ZIP download and offline SD package input enter the *same* bounded byte-stream reader, validation, SHA-256, safe ZIP extraction, stage/journal and commit engine; no whole-archive allocation or separate four-file driver downloader. Archive service reuses the bootstrap primitive. Preserve already-good App Store HTTP transfer and adapt the generic four-kind online source rather than silently keeping a parallel legacy download implementation. Pin release/asset snapshot, exact length/hash, and retain last-good installed generation on failures. Local inventory and SD install must remain independent of online streams/catalogs.
5. **Scheduler and failure contract.** Each operation specifies byte/record/queue/memory, I/O timeout, retry and per-turn wall-time bounds; bytes/items **and elapsed time** checkpoints; actual FreeRTOS scheduler cooperation; finite cancellation with owned `.part`/transaction recovery; transition-throttled progress, backpressure and stalled diagnostics. `esp_task_wdt_reset()` is not a scheduler yield. Audit `pump`/bridge mutex coupling: do not hold a global stream lock across potentially blocking filesystem, network or physical provider I/O. Protect endpoint generations and staged bytes across asynchronous I/O without invoking an unmapped ELF. Use focused real-invariant tests, not a new heavyweight E2E bureaucracy.
6. **Make the future family contracts usable without implementing those families.** A new ELF/profile/capability/stream schema must be registerable without changing generic firmware, the packer, a named driver catalog or app transport branches. Preserve typed-record atomicity/schema checks, generic error/EOF/backpressure, metadata and resource quotas. A large frame is **not** forced into the v2 512-byte record queue; the generic endpoint protocol must permit future bounded chunked byte or separately owned frame-buffer transport with clear lifetime. No full camera/display implementation in U1.

**U1 acceptance:** demonstrate the production `serial.port` path from physical USB driver ELF to Serial Monitor and programmer with zero firmware USB data plane; U1 package ZIP download/extraction using bounded shared streams; an independent provider lifecycle/stream attachment including loss/revocation; compatibility of v1/v2 existing callers; no unsafe blocked mutex/callback after unload and no hidden parallel manager. Physical tests remain owner-controlled Release Qualification. GNSS-specific sensor consumer rewrite and full GNSS rail/UART physical migration belong to U3, but U1's generic provider stream contract must not prevent them.

## 3. U2 — reuse streams for independently hosted packages, not a second stream runtime

Require generic, source-independent HTTP/file/package streams for the owner's separate GitHub package repository, catalogs, update discovery, immutable archive download, source disappearance and cancellation; source records, hashes and permissions remain control-plane metadata. Pipe progress feeds one transfer UI with bounded memory, deadlines, backpressure and recovery. Moving an archive between GitHub accounts cannot require new firmware transport code, a per-source downloader or app-specific stream helpers. If U1's generic source/ZIP stream path is complete, this is primarily consumer integration and regression checks, **not a fresh Stream v3 architecture milestone**. Network hardware extraction itself is separately scoped; do not put ESP Wi-Fi or a GitHub-specific protocol inside the generic stream runtime.

## 4. U3 — convert actual T5 Pro peripheral data planes onto the U1 contract

The fitted, board-specific ELF drivers publish generic streams/events according to semantics and demand: touch motion/gesture samples as typed bounded records or low-volume actions/events; SX1262 LoRa TX/RX as atomic packet records with bounded payload and RSSI/SNR/timestamp schema plus separate RF configuration/control; GNSS receiver byte source -> verified `location.fix.v1` records (reuse merged codec/source logic, remove firmware-specific polling/rail adapter); battery/charger/RTC telemetry as typed observations where continuous, event bus for rare changes; SD runtime media through generic file/storage bytes distinct from bootstrap. For the e-paper display, use a versioned display/frame/surface capability and bounded chunked or owned frame transfer appropriate to timing/PSRAM/DMA, not fake 512-byte frames or firmware-owned panel scans. Provider ELF owns actual hardware and buffers/IRQ lifecycle. Each pipeline must propagate backpressure, disconnect/revocation, resource ownership and sleep/unload safely. Add a narrowly scoped transform, fan-out, drop policy or performance optimization **only if a required U3 product path actually needs it**, preserving append-only ABI; do not require all optional stream architecture extensions before ordinary driver conversion.

**U3 acceptance:** actual display, touch, LoRa and all confirmed fitted Pro hardware produce/consume through generic capability/stream/event interfaces without transport-specific core code; T5 Pro regression; driver-absent ESP32-S3-CAM boots stably headless with no display/touch/LoRa stream startup prerequisite. The existing GNSS firmware-specific bridge must be retired if GNSS is fitted/used.

## 5. U4 — provision and demonstrate a CAM frame pipeline

U4 provisioning must reuse the U1/U2 bounded file/ZIP/source stream mechanism from an available bootstrap medium; never require an installed storage/network driver to fetch itself. A verified ESP32-S3-CAM driver exposes semantic camera capture/configuration and a **bounded high-throughput frame data path**, with frame length/format/dimensions/timestamp metadata, PSRAM/DMA-safe ownership, explicit buffer release, drop/backpressure policy, cancellation and revocation across contexts. Use chunked byte streams or a versioned owned-frame handle/record descriptor referring to manager-validated frame bytes; do not increase all v2 records to raw full-frame size or retain camera-ELF pointers in generic core. Demonstrate one headless frame-to-existing file/stream consumer and actual two-board capability separation. This is a U4 camera implementation on the U1 endpoint model, not a new per-camera stream engine or mandatory full recorder/tee network service.

## 6. Intentionally deferred full-architecture features

The full `STREAM_PIPE_ARCHITECTURE.md` also describes declarative general transform chains, coupled/independent tee, ordered fan-in merge, multiple alternate drop policies, watermarks/readiness APIs, generalized persistent/replay/range topology, zero-copy pools, global topology visualizers and broad diagnostics. None is independently authorized as a blanket U1/U2/U3/U4 gate. Implement a *specific* feature in the first milestone whose required functional consumer truly needs it (e.g., CAM frame ownership in U4), with a documented small append-only API; otherwise defer. Basic error/ownership, safe buffering, cancellation, scheduler cooperation and diagnostics needed by mandatory paths are **not** optional. Do not preserve a hardware-specific callback/transport path today merely by calling its proper generic conversion a future enhancement.

**Change-control:** This document is binding stream-related scope for the four milestones but does not expand U1 into full sensor/LoRa/display/camera feature development, advance milestones, alter the three-step implementation workflow or claim any source/build/hardware result. At each milestone kickoff use this allocation and inspect current production source to turn the stated gaps into actual implementation work; mark a feature complete only after source changes, not after this document merges.
