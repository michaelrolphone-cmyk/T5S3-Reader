# RiscRTE Runtime Provider/Driver Implementation State

**Current state as of September 18, 2026; not a completion claim.** Read normative [RISCRTE_PLATFORM_SPEC.md](RISCRTE_PLATFORM_SPEC.md), [HARDWARE_AGNOSTIC_DRIVER_BOUNDARY.md](HARDWARE_AGNOSTIC_DRIVER_BOUNDARY.md), [RUNTIME_DRIVER_ARCHITECTURE.md](RUNTIME_DRIVER_ARCHITECTURE.md) and the current integrated [U1 milestone](NEXT_HARDWARE_TEST_MILESTONE.md) before interpreting code below. The generic framework must see hardware names as opaque capability identifiers and own no physical device or transport. This file preserves accurate implementation/legacy evidence. See [USB migration status](USB_ELF_MIGRATION_STATUS.md) for current source-by-source USB extraction requirements, and [package scope](PACKAGE_MANAGER_SCOPE_CONTRACT.md) for signed-code purge.

## IMPLEMENTED FOUNDATION — ordinary manager, graph and physical-provider ELFs

Merged #76/#78/#79 supplied an ordinary four-kind package transaction path with SD/online app and driver adapters, a generic privileged OS/CPU ABI (46 symbols), private checked ELF/import/relocation path, installed provider graph/executor and functioning *source-code implementations* for a seven-package physical USB/I2C/power chain. The published v1.2.19 release includes canonical hardware-owning provider assets. These are meaningful implementation advances over thin proxy ELFs. The owner reports most package-management systems have checked out on hardware, while USB and Serial Monitor are not yet owner-tested. Neither CI, release publication nor code inspection proves USB enumeration, real duplex I/O, IRQ/DMA draining or electrical safety.

The remaining manager source/distribution gap is a special, generated `usb-provider-catalog.json`: a seven-driver build list, exactly-seven exporter, release asset, fixed `latest` fetch in Driver Manager and fixed four-file online installer. The generic package engine exists, but complete four-kind online/catalog/UI/inventory/update/uninstall parity does not. The catalog may locate online files but must never become mandatory for installed inventory, offline installs, module activation or class selection. U1 removes this coupling, completes the manager and purges out-of-scope signing code.

## CURRENT/LEGACY, NONCOMPLIANT — USB despite real ELFs

`Drivers/usb_controller_esp32s3`, `usb_host_v2`, `usb_cdc_v2`, `usb_cp210x_v2`, `i2c_esp32s3_v2`, `board_power_t5s3_v2`, `platform_clock_v1` contain actual corresponding hardware/class implementations and use the generic privileged ABI. `NativeUsbBridge.cpp` no longer implements ESP-IDF physical host/PHY itself, **but it still implements USB-specific provider selection and runtime behavior:** fixed `usb-host-v2` package choice, VID `0x10c4` CP210x selection, fixed class IDs, descriptor/host polling, USB session and line-coding state, physical read/write dispatch and a `BOARD_T5S3_PRO` guard. `NativeSerialPortBridge.cpp`, `UsbSerialProjection`, `NativeUsbDeviceRegistry`, firmware `nativeDeviceDiscoveryTick`/`ActivityManager::loop`, USB portions of `NativeStreamBridge`, the old `UsbCdcDriverRuntime` and `T5UsbApi` adapter must be audited for compiled/live reachability, migrated or deleted. Do not assume a file is dead just because new ELF modules exist.

The transport-neutral `src/runtime/capabilities/DeviceRegistry.h`, generic event/subscription journal, software execution-context leases and owned module pins are independently useful and stay. Current firmware-side USB snapshot projection, device-specific reservations and physical session ownership are not target behavior. Host/class ELFs must publish bounded generic device records and own actual USB tokens, matching, transfers, power and reset; Serial Monitor resolves `serial.port` and uses a generic stream plus provider-declared controls. Remove all normal firmware USB class/VID/device selection and special-case loader paths, with no compiled USB fallback. Quarantine and pin on unsafe shutdown; never unload ISR/DMA/callback owners optimistically. Distinguish isolated debug/ROM/boot functions from normal host functionality rather than deleting required bootstrap indiscriminately.

USB/I2C hardware acceptance remains **PENDING**: cold boot, true CDC/CP210x enumeration and sustained serial data, long-lived VBUS/current and power-role/backfeed safety, I2C exclusivity with `Wire`, disconnect/reconnect, failed activation, quiesce and removal/reinstall without firmware USB fallback. All U1 source/build/host integration work precedes one owner hardware test sheet. No repeated owner test requests are needed during implementation.

## CURRENT/LEGACY, NONCOMPLIANT — fixed network provider

Hardware radio functionality moved out of activities but remains compiled into `src/providers/network/Esp32NetworkProvider.cpp` and fixed through `src/runtime/network/NetworkService.cpp`. The internal contracts separate common network state/address/shutdown from Wi-Fi scan/connect/MAC/SSID/signal but still bind the provider for firmware lifetime, not by installed capability resolution. Migrated callers include Wi-Fi selection, file transfer, Calibre, OPDS, KOReader sync, firmware updater and native networking. Existing `test/run_runtime_network_test.sh` only validates current extraction. Actual Wi-Fi/link and hardware-dependent network logic must ultimately become ELFs, with generic services consuming them. This is a subsequent hardware-family milestone, **not a reason to expand U1 to a Wi-Fi rewrite**.

## PARTIALLY MODULAR — GNSS and UART/rail

`GPS_DRIVER.md` describes `gps-nmea` ELF and `position.gnss`; receiver/NMEA parsing resides inside the ELF and firmware has no parser fallback. Firmware still has GPS-specific adapter/facade, provider lifecycle and physical UART/rail management: a compatibility startup obtains a generic location lease and then firmware claims UART/power/ELF. The adapter can synthesize a location/UART registry record. Target is ELF-owned GNSS physical session, independently provided UART/rail capabilities, provider-originated publication and no fixed firmware GNSS path. This is later work, not full-portability evidence for U1.

## GENERIC REGISTRY — useful mechanism with legacy transport inputs

`DeviceRegistry.h` stores bounded, copied producer identity and capabilities, generations, shared/exclusive **software** leases and owner-checked invocation identity. Owner teardown releases grants. A bounded 24-entry lifecycle journal with 64-bit sequence and GAP behavior, eight invocation-owned subscriptions, read-only `T5DeviceApi.h`/`NativeDeviceBridge.cpp` inventory/snapshot/poll APIs and owner-task marshalling protect identities and resource lifetimes. They do not themselves control physical USB/UART. Tests include `device_registry_test`, `device_event_test`, `device_subscription_test`, `usb_serial_projection_test`, `usb_discovery_tick_test`, `usb_device_api_test` and `usb_direct_ownership_test`. The USB-specific suites currently describe legacy behavior and must be replaced with actual provider-publication/stream tests, not mistaken for architectural compliance.

## Migration order and acceptance

1. Complete U1 generic source/catalog and normal engine parity, remove signing-only code and integrate ordinary checked metadata/bytes with independent loader policy. No mandatory publisher identity or signing gate.
2. Complete **entire USB functional vertical** in provider ELFs, including provider-originated generic registry publication, Serial Monitor semantic stream, class probing and hardware quiescence; remove compiled normal firmware USB host/class/session/projection/selection/stream and catalog coupling. Avoid `Wire`/charger physical ownership races and isolate boot-only ports.
3. Run production-source **and linked-firmware** checks, host fault/lifecycle tests, release-equivalent images/modules and one hardware-test procedure. Mark USB software READY only after all workstreams pass; owner supplies physical results afterward. Do not wait idle for CI to write independent next code. This is [U1's single stop rule](NEXT_HARDWARE_TEST_MILESTONE.md#4-definition-of-done--milestone-stop-rule).
4. After U1, apply the same standard to GNSS/UART/power, network/Wi-Fi, SPI/GPIO/display/storage and other still-compiled physical families through separately authorized milestones. A different ESP ISA/ABI still requires a distinct minimal port; U1 makes new compatible USB devices installable without a core rebuild, **not** all ESP platforms magically binary compatible.

**Never label USB complete because hardware code moved only to a controller ELF, a package shipped, or CI passed.** Remove the driver and demonstrate that the capability/physical functionality disappears with no firmware substitute; install a compatible new device through ELF/profile alone. Do not put more hardware logic back into firmware to make a short-term test pass.
