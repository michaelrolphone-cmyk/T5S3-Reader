# Bounded, cooperative long-running operations — code-completion rule

**Binding for U1 and subsequent RiscRTE implementation work.** Read root [AGENTS.md](../AGENTS.md) and the [implementation-first workflow](IMPLEMENTATION_FIRST_QUALIFICATION_WORKFLOW.md). This rule is about **writing complete code**, not imposing a separate release-qualification stage, blanket CI gate or comprehensive end-to-end test suite. Build the safeguards into an operation while implementing it; do not defer predictable watchdog starvation, unbounded memory, unresponsive UI or data loss until the owner performs hardware testing.

## Requirement for every potentially long-running operation

Every loop or iterative state machine that performs filesystem, SD, network, cryptographic, package, dependency, recovery, device or other potentially blocking work **MUST declare and implement all five**:

1. **Resource and termination bounds:** maximum live memory/chunk size, pending items/queue depth, item count or total bytes where relevant, elapsed-operation deadline, per-I/O timeout where supported, and bounded unsuccessful retries/backoff. Never allocate in proportion to an untrusted archive, response or directory without a validated cap; refuse exhaustion safely.
2. **Bounded work and one-pass state:** no unbounded recursion; use iterative state machines and bounded work queues. Process each item once per operation whenever possible. Preserve cursors, hashes and resolved dependency state; avoid rescanning directories, rehashing unchanged bytes or reevaluating the entire dependency graph on each UI tick. If reprocessing is needed for correctness, document its finite bound and trigger.
3. **Dual checkpoint and actual scheduler cooperation:** checkpoint on **both bytes/items processed and elapsed wall/monotonic time**, including during low-throughput or empty progress. Choose realistic thresholds for the task; neither byte count nor `esp_task_wdt_reset()` alone guarantees CPU is shared. At checkpoints, service the task watchdog when appropriate **and explicitly yield with `vTaskDelay(...)`, a blocking queue wait or another demonstrable scheduler-cooperative mechanism**. A task that continually resets its own watchdog can still starve idle/other tasks. Blocking SD/network/filesystem calls must themselves have bounded timeouts or a recoverable cancellation/error path where APIs permit; yielding only *after* an indefinitely blocked call is insufficient.
4. **Observable progress:** report bounded-rate progress at checkpoints and state transitions (e.g. items/bytes, stage, last-progress time and error/retry state). UI/clients must distinguish ongoing slow work, waiting/retrying and a stalled/failed operation; do not emit unbounded UI updates on every byte.
5. **Failure, cancellation and recovery:** terminate or enter an explicit recoverable state when size/count/memory/deadline/retry bounds are hit, I/O stalls, cancellation occurs or storage disappears. Report the actual failure. Preserve previously installed files, verified generations, user data and transaction journals; roll back or retain a diagnosable resumable stage instead of exposing partial or mixed package contents. Never force-unload an active physical driver merely to escape a limit.

Review question: **For every relevant loop/state machine, where are its bounds, checkpoint, real scheduler yield, progress report and failure/recovery behavior? Missing any one means the implementation of that operation is incomplete.** Put short constants/comments near the code or in the operation contract; do not require a separate formal review dossier.

### Example: SHA-256 file verification

Read a bounded fixed-size chunk; feed its bytes to the incremental hash once; update total bytes and the monotonic checkpoint clock; enforce overall length/deadline and I/O result; at a byte **or** elapsed-time checkpoint publish throttled progress, service the watchdog if needed and genuinely yield to the scheduler. Finish with expected length and digest comparison. On timeout, short read, SD removal or digest mismatch report error and preserve the preexisting installed generation. Apply the same pattern to directory enumeration, download, ZIP streaming/extraction, dependency resolution, transactional install/recovery comparison and device polling.

**Development trade-off:** Implement these direct correctness requirements during coding with small targeted checks where useful. Do not respond by creating broad short-lived integration suites, blocking further coding on unrelated CI, asking the owner to test each operation or expanding U1 into a separate scheduling-framework redesign. An existing bounded cooperative primitive may be reused instead of duplicating machinery.
