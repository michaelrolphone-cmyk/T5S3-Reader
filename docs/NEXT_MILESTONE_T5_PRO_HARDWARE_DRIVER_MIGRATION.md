# U3 — T5 Pro hardware driver migration, bus cutover and UI-optional boot

**THIRD MILESTONE; SPECIFICATION ONLY.** Begins after accepted U2 and explicit owner direction, on one new implementation PR. Owner controls merge, release, flash and physical qualification. Governing documents: [four-milestone order](FOUR_MILESTONE_STREAM_FIRST_EXECUTION_ORDER.md), **[shared chip and rail ownership](SHARED_CHIP_AND_RAIL_OWNERSHIP.md)**, [I²C bus ELF cutover](I2C_BOOTSTRAP_CUTOVER.md), [SPI/UART ELF cutover](SPI_UART_ELF_BOOTSTRAP_CUTOVER.md), [UI-optional boundary](HEADLESS_RUNTIME_AND_CAMERA_SERVICE_BOUNDARY.md), [hardware boundary](HARDWARE_AGNOSTIC_DRIVER_BOUNDARY.md), [streams](STREAM_PIPE_MILESTONE_ALLOCATION.md), [driver architecture](RUNTIME_DRIVER_ARCHITECTURE.md), [U1](NEXT_HARDWARE_TEST_MILESTONE.md), [U2](NEXT_MILESTONE_INDEPENDENT_PACKAGE_ECOSYSTEM.md) and [U4](NEXT_MILESTONE_PROVISIONING_AND_ESP32_S3_CAM.md). Inspect real accepted firmware, Pro board revision/BOM/schematic, linked code and CAM flash/PSRAM/boot facts before determining fitted parts. Pin definitions alone are not hardware inventory. **Chip/rail ownership in the shared ownership contract supersedes any older table assigning one physical chip to two independent owners.**

## Required outcomes and exclusions

U3 must (1) migrate verified T5 Pro board-added peripherals into functional installed ELFs and both GPS apps off GPS-specific firmware bridges, with **single physical register/rail owners for all shared parts**; (2) switch the existing U1 I²C bus ELF's private backend to exclusive native controller ownership, install stable SPI and physical UART bus ELFs before their consumers, then switch them to native backends and retire normal firmware I²C/SPI/UART APIs without a second consumer rewrite; (3) keep compiled-in GUI optional while generic boot, scheduler, manager and services operate headlessly; (4) provide a CAM-compatible firmware booting driverless into observable, recoverable idle. Camera provisioning/image capture are U4. One-way headless serial is diagnostics, not a required interactive shell.

CPU, integrated Wi-Fi/BLE, flash/PSRAM, ROM and minimal on-chip boot/port primitives are excluded from board-added conversion. USB extraction is U1. Verified boot module-store/ROM/recovery paths may remain isolated, never publish a normal bus capability, become firmware fallback or contend with ELF-owned controllers. No new hardware families, GUI ELF, provisioning or CAM sensor drivers.

## Shared-chip, power and rail graph — a completion requirement

Follow [shared ownership](SHARED_CHIP_AND_RAIL_OWNERSHIP.md) for concrete interfaces and failure semantics. The PCA owner claims `0x20` once and exclusively manages both port registers, shadow state, configuration, interrupt fan-out and **atomic masked output changes**. Its public interface grants disjoint output pin masks and read/event rights, never shared raw register addresses. EPD power may own only its required PCA pin grant; button consumer only subscribes/reads. Do not allow an EPD state change to overwrite IO00, change button direction, or drop another client's pin grant. Conflicts, unknown writes and owner unload fail safely. The BQ `0x6B` owner from U1 continues to arbitrate OTG/charger functions; a new charger UI/driver cannot open BQ independently.

A single TPS owner claims `0x68` and implements all chip registers, fault telemetry and HV/VCOM state. One EPD power sequencer owns **the sequence**, depending on both the TPS capability and PCA's allocated EPD/TPS control pins. Display obtains a power lease from the sequencer; it never directly assumes TPS or PCA register ownership. Explicit sequence, timings, fault/hot-unplug/shutdown and safe HV state come from verified board facts. The BQ VBUS branch and TPS EPD-HV branch share `i2c.bus` but do not depend on one another unless physical schematic proves it. **Do not drag TPS/EPD into U1 merely because USB's BQ shares the controller.**

GNSS and LoRa may share PCA IO00 radio/GPS enable. A separate shared-rail provider (or the PCA owner publishing a distinct explicitly leased rail capability) must hold the **sole** IO00 output grant; GNSS and LoRa never write it. First successful lease enables verified power, subsequent leases keep it up; one consumer release must not shut it down while the other is active. Last release may shut down only after consumers quiesce and safe state is known. On failed disable/unknown electrical state report fault and retain ownership/quarantine, not `OFF`; on owner loss revoke both drivers' grants. Test both activation orders, concurrent consumers, one crash, missing rail provider and fault recovery. One power acquisition is not permission for LoRa TX. Validate actual wiring and any separate resets or power domains before selecting policy.

Record directed **bus → chip owners → rail/EPD sequencers → GNSS/LoRa/display → apps** and **I²C → BQ VBUS → USB host** dependencies. If the bus needs a rail it can only enable through a downstream device, identify a genuine safe bootstrap; never create circular graph or silent firmware chip implementation. One physical controller owner, address claim, pin output owner and rail policy owner at a time. Prevent removal/update of PCA, TPS, BQ or rail owner while their consumers hold leases or quiescence is uncertain. Missing shared owner means all dependent capabilities disappear, not an alternate raw bus register route. Generic core manages only opaque exclusive resource claims, rights, generations and dependency pins; no board chip knowledge.

## Bus migration: stable interfaces, private backend replacement

Follow [I²C](I2C_BOOTSTRAP_CUTOVER.md) and [SPI/UART](SPI_UART_ELF_BOOTSTRAP_CUTOVER.md). Inventory controllers, consumers, bus boot power, SD bootstrap, pins, shared signals and UART/ROM diagnostics. U1 I²C ELF already publishes `i2c.bus`, alone imports firmware I²C and supplies BQ VBUS and any actual U1 expander prerequisites. **Do not migrate existing BQ/PCA consumers again**: additional clients bind the same chip-owner capabilities. Before moving display/LoRa/SD and GNSS to bus ELFs install separately managed versioned `spi.bus`/`uart.port` providers; their temporary firmware imports, when necessary, remain private to matching bus ELF. USB CDC `serial.port` differs from MCU UART.

Check dependency cycles; a bus ELF may not require its own downstream rail owner absent independent safe boot. Bus ELFs own admission, rights, arbitration, bounds and lifecycle. SPI mediates clock/mode/order/CS, pad mux and DMA; UART owns hardware port, RX/TX streams, baud/framing, error and close. ROM/boot diagnostics need exclusive controller or a verified release/handoff and cannot become production UART fallback. For **each** physical controller, block admissions, quiesce clients, drain/cancel I/O, revoke generations, safe-state pins/rails, release firmware backend and then initialize native backend inside the **same bus ELF**. Rebind clients through unchanged public ABI; no simultaneous controller or firmware fallback. Delete normal-runtime firmware I²C/SPI/UART imports after cutover; isolate strictly necessary boot/recovery separately. U3 Work Complete requires native controllers for all actually used normal bus families, earlier-client compatibility and correct multi-client chip/rail arbitration.

Consumers use U1 bounded paths: atomic LoRa packet records, GNSS byte/position records, touch events, telemetry, SD bytes, display owned frames/chunks (not a full EPD frame in a 512-byte record). No retained DMA or ELF pointers past ownership; finite timeout/retry/queue/memory, real yields and recovery per [bounded operations](COOPERATIVE_BOUNDED_OPERATIONS.md). Preserve ZIP, package identity, U2 sources and profile roles; Pro system-core not universal on CAM.

## GNSS: complete driver-to-app conversion

**Verified master baseline at September 18, 2026:** `Drivers/gps_nmea/driver.c` implements NMEA/fix/baud but imports `t5_kernel_io_v1` UART/power; its manifest requires `kernel.serial`, `kernel.power`, `kernel.clock` and provides `position.gnss`. `GpsKernelIo.cpp` directly controls T5 board-specific GPS UART/pins/`RadioPower`; `GpsDriverRuntime.cpp` names `gps-nmea`, starts/polls and publishes `location.fix.v1` through native GNSS bridges; `NativeGpsBridge.cpp` exposes `T5GpsApi`, `NativeLocationBridge.cpp` calls the runtime. `Apps/gps.c` uses `t5_gps_get_api()`/start/read/stop; `Apps/gnss_stream_diagnostic.c` reads location records but hard-codes `gps-nmea`/UART and `location->poll`. These are migration targets, not evidence ELF/streams are absent.

Move GNSS receiver protocol, UART/configuration, pins and **shared rail access through `board.power.radio`**, never direct `RadioPower`, into installed ELFs. GNSS provider publishes `location.position` and versioned `location.fix.v1` via generic registry/streams on resident bounded driver work, independent of app polling. Both GPS and diagnostic apps resolve semantic capability, authorize/subscribe/read, render fixes/diagnostics, retain denial/revocation/backpressure and bump versions. No `T5GpsApi`, `gps-nmea` hard-code or `location->poll` to drive source. Remove/reduce `GpsKernelIo.cpp`, `GpsDriverRuntime.cpp`, `NativeGpsBridge.cpp`, `NativeLocationBridge.cpp` and GNSS-specific stream bridge to generic/strict legacy compatibility, no firmware receiver power/UART/start/poll/fix publication. Test driver absence, multiple contexts, alternative location provider, permission loss, backpressure, update/unload and safe **shared-rail release while LoRa is still active**. Physical evidence remains owner qualification. **GNSS acceptance:** both apps consume real installed-ELF semantic streams without provider-ID, firmware GPS or app-poll coupling.

## UI optional and driverless CAM

Boot port/minimal recovery → inventory/profile → scheduler/providers/services → optional firmware GUI **only** if profile requests and `display.*` exists. Missing display/touch/fonts/UI cannot prevent boot, services, recovery, idle or diagnostics; headless allocates no EPD framebuffer/fonts and does not poll render/ActivityManager. Pro retains GUI. No new interactive console or GUI ELF. Actual CAM boots compatible firmware with zero Pro/CAM packages, optional SD/display/touch/radio/RTC/gauge/GUI/camera/provisioning absent, stable idle and recovery. Minimal one-way serial where supported; no normal UART fallback. Validate bootloader/flash/PSRAM/pins; prefer same binary where feasible or minimal port distinction and same hardware-blind runtime. Do not initialize retired T5 bus adapters or treat T5 shared-chip packages as universal core dependencies.
