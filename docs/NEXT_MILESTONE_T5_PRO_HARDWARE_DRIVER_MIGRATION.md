This document does not authorize work on U3 during either earlier milestone, expand U1/U2 acceptance, create an implementation branch, or request intermediate owner hardware tests. At U3 kickoff inspect the actual merged code, relevant board revision(s), fitted component inventory, U1 driver-gap ledger, U2 package repository/builds, and currently used driver/capability APIs; revise the factual migration inventory without weakening the architectural requirements below.

**Authorities:** [Platform specification](RISCRTE_PLATFORM_SPEC.md), [hardware-agnostic driver boundary](HARDWARE_AGNOSTIC_DRIVER_BOUNDARY.md), [runtime driver architecture](RUNTIME_DRIVER_ARCHITECTURE.md), [driver-platform reuse acceptance](DRIVER_PLATFORM_REUSE_ACCEPTANCE.md), [platform abstraction](PLATFORM_ABSTRACTION_ARCHITECTURE.md), [cooperative bounded operations](COOPERATIVE_BOUNDED_OPERATIONS.md), [U1](NEXT_HARDWARE_TEST_MILESTONE.md), [U2](NEXT_MILESTONE_INDEPENDENT_PACKAGE_ECOSYSTEM.md), and [implementation-first workflow](IMPLEMENTATION_FIRST_QUALIFICATION_WORKFLOW.md). Existing code and vendor pin definitions are evidence of intended hardware wiring, **not proof that every peripheral is populated or works on every Pro/Lite revision**.

## 1. Objective and precise scope boundary

Migrate **the physical peripheral hardware added by the LilyGO T5S3 4.7-inch e-paper Pro board around its ESP32-S3 module** into real, separately buildable/installable hardware-owning driver/provider ELFs. Include the display and touch screen, LoRa, and every other fitted board-specific peripheral and its control/power circuitry. Consume the generic package manager, capability resolver, port primitives, manifests, board profiles, lifecycle, streams/events and independent package-publishing path delivered by U1/U2. **Do not implement another package manager or embed a second hardware framework in firmware.**

**Explicitly outside the U3 conversion inventory:** capabilities intrinsic to ordinary ESP32-S3 modules/SoCs, such as the CPU, flash/PSRAM substrate, integrated Wi-Fi/BLE radios, generic native GPIO/I2C/SPI/UART controller hardware, ROM/boot facilities and generic memory/FreeRTOS/ELF-port mechanics. They may be consumed through existing generic OS/CPU primitives or reusable bus providers; U3 is not a mandate to finish an independent migration of all on-chip ESP32-S3 hardware or Wi-Fi/BLE. The normal RiscRTE core nevertheless remains hardware-blind; this exclusion is not permission to add a panel/LoRa/touch implementation or a named hardware bridge to the core. Already-completed U1 USB extraction is not reimplemented in U3. If a missing **generic** bus or interrupt primitive is indispensable to operate an included board peripheral, repair/reuse that generic facility once rather than create a board-specific firmware exception.

A component belongs to U3 when it is a **board-added physical device, transceiver, connector/media interface, power circuit, input, output, or fitted peripheral** beyond the module itself. Scope is based on verified board hardware and actual ownership, not solely on whether a function is displayed in the UI. Existing board-specific physical functionality must not silently disappear because a driver is optional or the migration is inconvenient. Do not invent support for unpopulated components from names or pin constants alone; record fitted/not-fitted/variant-dependent status. Do not drag arbitrary external plug-in sensors or every other ESP32 board into U3.

The source pin header documents I2C addresses for GT911 (`0x5D`), PCF85063 (`0x51`), TPS65185 (`0x68`), PCA9535 (`0x20`), BQ25896 (`0x6B`) and BQ27220 (`0x55`), plus LoRa SX1262, GNSS UART, SD and panel pins. ## 3. Required architecture and dependency graph

Build each physical vertical slice as a true ELF hardware implementation. It may depend on installed reusable bus/controller, GPIO, power, IRQ, clock and board-profile capabilities; it must not forward panel scans, touch I2C transactions, radio commands, charger registers or board power sequencing to compiled firmware. Composites are allowed when a chip needs several lower providers. Keep ordinary package `kind` and independently versioned U2 source/role/publisher metadata separate: a display driver is a driver, although a selected board profile may classify it as a necessary **system component**. Nothing is universal or auto-installed merely for being called core.

Illustrative manifest-driven paths (capability spellings and interface versions finalized from real U1/U2 APIs at kickoff):

```text
system UI / screen clients -> display.frame / display.refresh
                              ^
                          e-paper ELF -> panel pins / timing + EPD power provider

launcher/input clients -> input.touch <- GT911 ELF -> I2C / IRQ / power provider
radio consumers -> radio.lora <- SX1262 ELF -> SPI / IRQ / GPIO / RF power
location consumers -> location.* <- GNSS ELF -> UART / shared rail provider
battery/settings/power policy -> battery.* / power.* <- charger + gauge ELFs
clock/alarm clients -> time.rtc <- RTC ELF -> I2C / IRQ provider
package manager / storage clients -> storage.* <- SD runtime ELF, distinct from bootstrap
```

The core knows only manifests, opaque capability names, authorization, dependency order, generic events/streams and module lifetime. Board profiles carry revision, fitted devices, safe pin maps, bus/address/chip-select bindings, shared-resource conflicts, power dependencies and default capability choices; **no hard-coded `T5 Pro` device switch in generic firmware**. Consumers resolve semantic capabilities rather than `BoardT5S3` functions or specific ELF filenames. New compatible panel, digitizer or radio driver/package must not require a new firmware branch.

## 4. Shared board resources and electrical safety

- **Bus/pin arbitration:** inventory every overlapping pin, bus, CS, DMA channel, IRQ and expander output. SD and SX1262 share an SPI wiring definition; the EPD parallel mapping reuses several of those GPIO numbers. Establish explicit exclusive/serialized modes, pad-mux handoff, CS idle states and dependency-order policies in the owning provider/profile. An SPI mutex alone is insufficient for GPIO pad conflicts. No simultaneous operations are promised unless electrically safe.
- **Power:** centralize GNSS/LoRa shared rail, EPD HV/VCOM, charger and board shutdown through suitable power-provider ownership and reference/lease policy. No separate ELF may directly toggle another provider's rail or disable power while a dependent transfer, display refresh or receiver session is active. Respect battery/USB source constraints, fault inputs, safe wake and power-down order; preserve hardware safety even when software components are missing or fail.
- **IRQ, tasks and DMA:** driver ELFs register and unregister their real interrupts, callbacks and tasks, use DMA-compatible allocations/cache maintenance for panel/radio where applicable, and drain/quarantine uncertain work before unmapping. Generic execution contexts and software leases do not substitute for physical quiescence. Missing/corrupt driver yields an unavailable capability and diagnostics, not a compiled fallback.
- **Bounded cooperative operations:** follow [Cooperative Bounded Operations](COOPERATIVE_BOUNDED_OPERATIONS.md) for display refresh/painting, touch event processing, packet TX/RX, SD transfers, battery polling and driver recovery: fixed memory/queues, bounded work and retries, elapsed-time and byte/item checkpoints, **real scheduler yields** (a watchdog reset is not one), throttled progress and safe cancellation/recovery. For timing-critical transfers use bounded device-owned asynchronous chunks/interrupts while other tasks remain schedulable; do not yield mid-waveform if that would violate hardware timing.

## 5. Display and touch conversion must preserve the product

The generic scene/UI host remains presentation, composition, layout, navigation and UI state; the **panel hardware implementation, waveform/timing, pins, controller reset, refresh and physical power** belong in installed ELFs. Define a versioned capability for surfaces/frames, dimensions, orientation, pixel formats, partial/full update requests, completion/failure and the buffer ownership contract. Adapt every compiled display consumer, status/sleep clock, file/image reader and app host to that capability without requiring a particular panel. Bound PSRAM buffers, copies and DMA mappings. Never keep a callback into an unmapped display ELF.

The touch driver publishes bounded, calibrated input events through a generic input interface; transforms from physical orientation to logical screen coordinates are profile/UI policy over neutral metadata, not a GT911 branch in the core. Missing touch must permit other input/diagnostic routes. Display and touch may be installed/updated/disabled independently where their real electrical dependencies permit. A device profile lacking display/touch must boot, manage packages through a supported non-display channel and run headless services without installing Settings or other display-only system apps.

**Bootstrap visibility:** e-paper is slow/nonvolatile and may be blank or stale if its ordinary ELF is missing; define one minimal, clearly isolated recovery/diagnostic channel that does not depend on the missing normal display driver. If recovery absolutely needs a separate emergency panel path, document its small scope, entry condition and inability to register as a production `display.*` provider; prefer serial/logging or other existing board-independent recovery. Do not justify keeping normal panel scans in firmware as an invisible fallback.

## 6. Radio, GNSS, storage and board-management conversion

The SX1262 ELF owns initialization, register/protocol operations, radio mode/configuration, IRQ/BUSY handling, TX/RX buffers, timeouts, errors and safe shutdown. Provide explicit regional/frequency/configuration inputs and report unsupported hardware/profile states; no unconditional TX at boot, no unbounded radio retry loop and no radio-specific framework queue. Higher-level messaging/LoRa application protocols remain separate services/apps, not hard-coded driver policy.

Preserve useful existing GNSS ELF parsing and driver packaging, but eliminate any remaining firmware GPS UART claiming, board rail manipulation, parser calls or GPS-specific compatibility selection. Share the GNSS/LoRa enable safely with the radio provider. If the particular Pro revision has only an optional GPS connector or no receiver, document that and expose capability absence rather than fabricate a built-in GPS. Reuse the existing U1 GNSS gap ledger.

Migrate external RTC, charger/gauge, expander, board buttons/illumination and other confirmed board peripherals using the same general capability path. Keep safe basic battery power behavior even if the manager or user interface is absent; characterize unavoidable immutable power-on/boot-critical circuitry separately rather than registering it as an ordinary driver. Avoid creating one all-knowing `BoardT5S3` ELF that merely repeats the board monolith: factor owners by actual hardware/resource/lifecycle boundaries, allowing composite board-profile packages where useful.

The SD interface is an explicit special case because installed driver ELFs and packages may be stored on SD itself. Document the smallest immutable module-store/bootstrap route needed to read/install drivers; isolate it from the normal runtime SD provider and ensure an orderly handoff or separately protected ownership without double initialization and without losing mounted executable mappings. Uninstalling the runtime SD provider must not strand boot/recovery or corrupt installed packages. Do not generalize the boot path into a full firmware SD driver fallback.

## 7. Source migration, packaging and independent publishing

At U3 kickoff create one concise **board-hardware migration ledger** mapping verified component/revision -> exact compiled owners/callers -> provider dependency/profile -> required capability ABI -> driver package/source -> removal edits -> known safety constraints. Include `lib/Board_T5S3/BoardT5S3.cpp/.h`, `pin.hpp`, EPD/touch libraries, firmware UI/display/audio/light paths if actually present, LoRa/GPS paths, battery/power/RTC/expander/SD and sleep logic; audit the build and linked firmware rather than only filename scans. Do not automatically delete `BoardT5S3` compatibility code before consumers migrate; physically remove device operations from normal builds after migration and retain only justified bootstrap facts.

Use the **U2 independent package repository/build/release mechanism** for these packages: one U1 `.rte.zip` per versioned identity/target, coherent metadata, source author, board revision/architecture/ABI and firmware floor, per-kind/ID installed directories, generic catalog, safe version increments/update/rollback and offline SD availability. Firmware releases need no rebuild for a compatible driver/profile update. Package activation remains distinct from installation, and removal of a required system driver must show dependency/profile impact and safely refuse if necessary. Keep historical package identities/installed data unless an explicit bounded migration is implemented. No signed-package experiment, special board-specific installer or manual hard-coded release asset list.

## 8. Work Complete boundary and owner-led qualification

**During implementation** complete the entire board-added hardware inventory and working production migration as one milestone branch/PR. A component confirmed present is not done merely because its ELF compiles: move the real hardware code, integrate consumers and dependencies, remove operational firmware owner/fallback, implement bounded/cooperative loops and safe lifecycle, and publish correct package/profile manifests/build paths. Resolve concrete build/integration defects as they arise without stopping independent work for all-green CI or building a giant temporary E2E suite. Record targeted checks honestly; do not ask for per-driver hardware tests.

**Work Complete** can be announced when all verified in-scope Pro-specific peripherals have a defensible owner/disposition, required functional ELFs and generic consumers are wired, no board-specific production hardware implementation or hidden fallback remains in core, bootstrap boundaries are documented, package/build sources work with U2 separation and no known blocking source/build defect remains. Variant-dependent/unfitted parts require explicit documented disposition rather than invented test claims. Physical functionality is not qualified by this signal. Following owner `continue`, enter **Improving Code** and perform useful independent audits/fixes on the same PR; enter **Release Qualification** only at the owner's explicit request and then test real board combinations, display/touch, LoRa, shared buses/rails, SD/bootstrap, sleep/wake, battery and recovery together. Qualify only observed results and owner acceptance; never automatically merge, publish, flash or advance milestones.

**Explicit exclusions:** U1 USB/package completion or redo; U2 release decoupling or third-party developer onboarding; migration of Wi-Fi/BLE and other ESP32-S3-intrinsic hardware as standalone projects; arbitrary external add-on boards; new trust/signature marketplace; complete first-run SD provisioning; rearchitecting the entire renderer or operating system beyond the minimal generic capability adaptation needed to remove physical display ownership. This U3 document remains future scope until the owner starts it.
