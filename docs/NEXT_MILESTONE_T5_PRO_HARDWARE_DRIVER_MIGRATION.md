## 1. Objective and boundary

**Two inseparable U3 outcomes:** (A) migrate the physical peripherals added by the LilyGO T5S3 4.7-inch e-paper Pro board around its ESP32-S3 module to real, separately buildable/installable hardware-owning ELFs; and (B) make the resulting generic RiscRTE firmware **flashable and stably bootable on the owner's ESP32-S3-CAM when NONE of that board's camera-specific drivers or the T5 Pro packages are installed**. In this second configuration, the runtime deliberately runs headless and may become idle for lack of available apps/capabilities. Idle is success; crash/reboot loops, watchdog starvation, mandatory display initialization, blocking forever on missing SD, and implicit T5-only peripheral fallback are failures. The bare CAM must not need to capture images, mount an optional board SD slot, or perform first-run provisioning until U4.

For outcome A, include the real fitted T5 display and touch, LoRa, and every other board-added physical peripheral and its control/power circuitry. Consume U1's common package manager, resolver, ABI, lifecycle, board profiles and bootstrap and U2's independent package publication. Do not create a second package manager or hide devices in firmware. Outcome B is a **cross-board core portability and absence proof**, not authorization to move CAM camera hardware into U3.

**Excluded from the U3 peripheral-conversion inventory:** capabilities intrinsic to ordinary ESP32-S3 SoCs/modules: CPU, flash/PSRAM substrate, integrated Wi-Fi/BLE radios, generic on-chip GPIO/I2C/SPI/UART controllers, ROM/boot and generic memory/RTOS/ELF-port machinery. Use existing generic primitives/reusable bus ELFs where applicable. Do not start independent Wi-Fi/BLE or all-on-chip hardware migrations. This exclusion does not excuse hardware-specific code inside generic core; where a required primitive is missing, add one transport-neutral, versioned CPU/OS port contract rather than named device behavior. USB extraction is U1, not repeated here. Scope other fitted Pro peripherals from reliable board evidence; do not invent devices or broaden to arbitrary external sensors.

## 3. Driver architecture and dependencies

A physical driver ELF owns probe/init, actual register/protocol transactions, transfers, hardware state, callbacks/IRQ/DMA, power and failure recovery and physical teardown. It may consume lower bus/controller, expander, power and clock providers; no ELF may simply proxy a firmware panel/touch/radio/charger implementation. Consumer apps/services request semantic capabilities, not `BoardT5S3` functions, physical pin maps or ELF filenames. The core sees only opaque manifest requirements, policy, grants, generic registry/events/streams and lifetimes. Board profiles supply fitted-device/revision data, pin/bus/CS/address/IRQ/rail mappings and shared-resource constraints; no `BOARD_T5S3` special-case route in generic code.

```text
UI/scene -> display.frame/refresh -> EPD ELF -> panel control + EPD power provider
input consumer -> input.touch -> GT911 ELF -> I2C/IRQ/expander dependencies
radio consumer -> radio.lora -> SX1262 ELF -> SPI/GPIO/IRQ/shared power
location consumer -> location.* -> GNSS ELF -> UART/shared power
battery/clock consumers -> battery.*/time.rtc -> gauge, charger, RTC ELFs
storage client -> storage.* -> runtime SD ELF; bootstrap reader is separately isolated
```

Keep the existing four package kinds and U2 independent version/source/publisher/role metadata. Pro driver may be `system-core` **for an applicable Pro profile**, but remains an installable package; its role is never a universal installation requirement or privilege grant. Adding a compatible panel, radio or future board must not introduce firmware device branches.

## 4. Resource and safety rules

Inventory shared SPI/I2C wiring, pin mux, CS, DMA, IRQ and expander outputs. SD/LoRa SPI and EPD parallel pins may overlap; provider/profile defines safe exclusive modes, handoff, idle CS and dependency order instead of assuming concurrency. Shared GNSS/LoRa rail, EPD HV, VCOM, charger/USB power and board shutdown have single coherent provider ownership. A dependent driver must not power off a shared resource in use. Preserve safe default electrical behavior during absence, failures, unload, power loss and sleep.

ELF driver callbacks/tasks/IRQ/DMA are registered and fully drained before unmapping; uncertain physical quiescence pins/quarantines dependencies and revokes consumers safely. For refresh, packet transfers, touch, SD and polling, follow [bounded cooperative work](COOPERATIVE_BOUNDED_OPERATIONS.md): limited buffers/work queues/retries, time+byte/item checkpoints, **real scheduler cooperation rather than watchdog reset alone**, throttled progress and recovery. Timing-critical signal trains can use bounded asynchronous chunks and interrupts; do not yield in the middle of a waveform if it violates electrical timing. Missing/corrupt drivers yield ordinary capability absence and diagnostics, never compiled production fallback.

## 5. Display, touch and board functions

The generic UI/scene host retains layout/composition/navigation and routes frames to a versioned `display.*` surface/capability. The installed EPD driver owns all scan/waveform/panel pin/refresh/power operations. Define frame dimensions, format, orientation, partial/full refresh, completion/error and owned-buffer lifetime; adapt status/sleep clock, file/image reader and app/UI consumers. Bound PSRAM/DMA ownership and forbid stale pointers/callbacks after ELF unload. Touch events are bounded/calibrated through generic input; transform screen orientation from metadata and profile, not a GT911 switch. Display and touch can be absent or independently installed where safe.

SX1262 ELF owns initialization, radio commands/registers, RX/TX mode, IRQ/BUSY, timeout/recovery and shutdown; unsupported frequency/profile states fail explicitly, with no TX on boot. LoRa messaging policy stays in separate services/apps. GNSS retains real `gps-nmea` logic but moves any firmware UART/rail/parser/selection residue into ELFs; do not pretend a connector guarantees a populated receiver. Move RTC, charger/gauge, expander, buttons, illumination and sleep hardware behavior into correct physically owning packages; do not merely rename the old board monolith one all-purpose ELF.

Runtime SD requires particular care because a module might be stored on the medium it would normally operate. Preserve a **minimal explicitly bounded module-store/bootstrap/recovery route** and independent normal runtime SD provider with safe ownership handoff. A removed driver must not strand boot/recovery or invalidate mapped executable bytes. This bootstrap exception cannot advertise a production `storage.*` fallback. Preserve safe charger/power-on hardware defaults and document truly immutable boot-critical operations separately from installable provider functions.

## 6. Mandatory CAM headless boot at U3 completion

**The owner must be able to flash an applicable U3 RiscRTE firmware build onto their actual ESP32-S3-CAM, with no CAM-specific driver, no T5 Pro peripheral driver or UI package installed, and reach a healthy stable headless idle state. This is U3's release-boundary software objective and subsequent owner qualification scenario, NOT deferred to U4.** U4 installs camera-board drivers/provisions packages only AFTER this basic hardware-independent boot has been established.

- **No T5-only startup dependencies:** generic startup, service discovery, scheduler, resource accounting, installer/inventory and recovery cannot require an EPD, touchscreen, GT911, SX1262, T5 power IC, external RTC, board expander, SD slot, battery gauge, T5 pin map or T5 device profile. Absence of these or all optional packages results in unavailable capabilities/skipped dependent apps, not a fatal assert, reboot, null invocation or auto-install of the wrong profile. No fake display or fake camera capability is published.
- **Storage bootstrap without board SD:** boot the runtime and enter a durable empty/inert installed-package state from an actually supported minimal internal module-store/recovery location (or another explicitly verified board-independent bootstrap path). Optional SD mount failure is nonfatal; avoid repeated probing/recovery loops that starve scheduler. The package manager must not require a UI to perform its ordinary background inventory/recovery; do not claim online/SD installation is available without an actual transport.
- **Minimum physical/port portability:** inspect chip/architecture, flash voltage/size, partitions/bootloader, PSRAM presence/configuration, boot pins and generic CPU/OS port needs for BOTH actual boards. Target **one identical flashable firmware image** on both when those constraints permit. Where bootloader/flash layouts/port bootstrap require different output images, allow only a documented smallest necessary board/port build artifact difference while retaining one generic runtime code path and ABI; do not declare that two different binary layouts are byte-identical or smuggle in a T5/CAM device switch. Gracefully handle unavailable or smaller PSRAM: essential runtime/idle boot must not allocate a T5 display frame buffer or crash because PSRAM is absent. If a common image is feasible, demonstrate identical-image flashing, not just source equivalence.
- **Observable, recoverable idle:** enter and maintain scheduler-cooperative idle with bounded memory/tasks, normal watchdog behavior, stable uptime and no boot/recovery thrash. Expose a minimal diagnostic/owner recovery channel that does NOT need missing display/camera/storage peripheral drivers; use a documented safe port/ROM/USB-console/recovery path only if actually supported by this board. It may report boot, firmware/port version, memory and capability absence. No camera application, graphical Settings, Wi-Fi enrollment or provisioning wizard is required to be functional in U3. A healthy idle device is not a failed boot merely because it has nothing to run.
- **Truthful verification boundary:** during implementation inspect/link-test absence paths and build the actual compatible firmware image(s), fix known boot-architecture blockers; do not declare software complete with a known T5 startup dependency. At owner-initiated Release Qualification, flash the real CAM, observe stable boot/idle/recovery without installed board drivers, then separately confirm T5 Pro still boots with its packages. CI or emulated boot is not physical CAM PASS. Record exact boards, flash artifact identity, actual memory layouts and installed package inventory; a CAM capture success is U4, not U3.

## 7. Migration ledger, builds and sequencing

Maintain a concise component/revision -> current compiled owner/caller -> ELF/package/board profile -> generic ABI/dependency -> removed core source -> recovery/absence treatment -> verification ledger. Inspect actual linked images, not just filename grep. Move real hardware code and all consumers; delete board-specific operational firmware ownership/fallback only after migration. Keep compatibility interfaces only when truly generic or explicitly isolated bootstrap. Driver sources/manifests are packaged by U2's independent repo/workflow: one U1 `.rte.zip` per version/target, coherent author/source/compatibility info, valid catalog, SD availability, safe versioning/upgrade/rollback and no firmware rebuild for compatible driver updates. Preserve historical installs and data; no board-specific installer, old signed-package framework or fixed package list.

Implement complete functional slices and CAM bare-boot architecture on ONE U3 implementation PR; targeted builds/invariant/smoke checks as useful, no repeated owner board tests, giant brittle milestone-only E2E suite or idle all-green CI wait. Separate the boot-only module-store path from normal runtime storage before treating driverless CAM as a supported deployment. If the bare CAM has no installation media, its inability to access camera packages until U4 provisioning is expected, not an excuse to crash or demand the CAM driver now.

## 8. Work Complete and qualification

**Work Complete** requires BOTH (A) verified fitted Pro-specific peripherals have an explicit owner/disposition, real functional ELFs and migrated generic consumers, no normal board-specific firmware hardware implementation/fallback, safe lifecycle, independent packaging and no known blocking build defects; AND (B) an applicable generic image, headless absence paths and minimal bootstrap/recovery have been implemented so the driver's absence does not block boot on the owner's actual ESP32-S3-CAM. Inspect actual firmware link, builds and bounded absence/recovery behavior; report checks honestly. Physical CAM flash/idle and Pro hardware behavior remain pending until owner-initiated qualification and must not be claimed passed merely from compiling. On later `continue`, **Improving Code** means independent source audit/fixes; **Release Qualification** starts only on explicit owner direction for joint CAM flash/idle and full Pro device testing. Do not auto-merge/tag/release/flash or advance U4.

**U4 handoff:** [U4](NEXT_MILESTONE_PROVISIONING_AND_ESP32_S3_CAM.md) implements the deferred declarative first-run manifest, headless installation/activation and actual CAM-specific drivers. It must reuse U3's already-portable runtime rather than repairing a T5-only boot path by compiling camera implementations into firmware.

**Excluded from U3:** U1 USB/package redo; U2 publishing/third-party onboarding; independent migrations of ESP32-S3-integrated Wi-Fi/BLE and other on-chip hardware; arbitrary external add-ons; new signing marketplace; full first-run provisioning; actual CAM sensor, illumination or CAM storage drivers; major renderer/OS redesign beyond generic display capability migration. This is future scope until the owner starts U3.
