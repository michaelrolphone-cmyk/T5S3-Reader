# U3 — T5 Pro board-peripheral drivers and UI-optional headless-port proof

**Status: THIRD MILESTONE, SPECIFICATION ONLY; follows U1 and U2, precedes [U4 provisioning and ESP32-S3-CAM streaming](NEXT_MILESTONE_PROVISIONING_AND_ESP32_S3_CAM.md).** September 18, 2026. U3 does not begin during earlier milestones, and this specification is not authorization to implement, merge, release or flash. Begin on owner direction from the accepted U2 baseline; inspect actual code, T5 Pro revision/fitted parts, actual CAM flash/PSRAM/boot configuration, U1 gap ledger and U2 packages. Do not infer board contents from vendor pin definitions.

Hardware inventory starting points: `lib/Board_T5S3/pin.hpp`, `BoardT5S3.h/.cpp`, active EPD, touch, LoRa, GNSS, battery, power, RTC, SD, expander, app startup, UI/ActivityManager and boot/recovery source. These paths describe candidates, not verified fitted parts on every revision.

## 1. Objective and hardware boundary

**Three coordinated U3 outcomes:** (A) migrate all verified physical peripherals added around the ESP32-S3 on the LilyGO T5S3 4.7-inch Pro board into separately buildable/installable *hardware-owning* driver ELFs; (B) make the **existing firmware UI optional at runtime**, with generic boot/scheduler/service/installer/recovery independent of display, touch and UI loops while retaining the working T5 Pro graphical firmware code; (C) make that runtime flashable and stably bootable on the owner's ESP32-S3-CAM with **neither CAM-specific nor T5 Pro peripheral drivers installed**, reaching a healthy headless idle. It may have nothing to run: that is success. Crash/reset loops, watchdog starvation, mandatory display init, indefinite missing-SD waits or built-in T5 hardware fallback fail.

Outcome C is a cross-board absence/portability proof, **not** CAM capture, actual board-driver provisioning or a requirement for any interactive headless shell; those are U4 or later. Reuse U1's common package manager, generic installed-ELF stream endpoint/capability resolver/ABI/lifecycle/bootstrap and U2 independent package publication/profile policy; do not add parallel managers, new device-specific stream engines or firmware device branches.

**Excluded from the peripheral-conversion inventory:** ESP32-S3 SoC/module-intrinsic CPU, flash/PSRAM substrate, integrated Wi-Fi/BLE radios, on-chip GPIO/I2C/SPI/UART controller primitives, ROM boot and generic memory/RTOS/ELF port. Existing generic OS/CPU primitives and reusable bus ELFs may be dependencies, not excuses for core hardware-specific logic. Independent migration of integrated Wi-Fi/BLE is out of scope. USB extraction belongs to U1. A missing required CPU primitive is added as a generic versioned port facility, not a T5 driver in core. Never invent arbitrary attached sensors or variants.

## 2. Verified Pro peripheral inventory and disposition

At kickoff cross-check schematic/BOM/revision, actual linked firmware and consumers. Mark each `PRESENT`, `VARIANT-DEPENDENT`, `ABSENT` or `UNCONFIRMED`; only confirmed parts are implementation requirements. Each inventory item gets package identity, physical ownership, lower provider dependencies, board-profile metadata, consumer, electrical safety, absent-driver state and migration/verification evidence.

| Board-added hardware / candidate | Driver/semantic target | Principal constraint |
| --- | --- | --- |
| ED047TC1 4.7-inch e-paper panel and signals | EPD controller/panel ELF -> versioned `display.*`; firmware UI becomes optional consumer | Full/partial refresh, PSRAM/DMA/cache, HV, sleep/wake, no-display path |
| TPS65185 EPD power / PCA9535 EPD outputs | EPD power and shared expander provider | HV/VCOM, power-good, temperature, rail/output exclusivity |

## 3. Ownership, generic data plane and profile

Every physical ELF owns probe/identification, register/protocol I/O, controller transfers, hardware state, IRQ/DMA/callbacks, real power sequencing, fault recovery and physical teardown. Driver ELFs may depend on generic controller/bus, expander, power and clock ELFs. A proxy ELF forwarding to compiled panel/touch/LoRa/charger operations is noncompliant. Applications and services request semantic capabilities rather than `BoardT5S3` methods, T5 pins or ELF filenames. Core handles only opaque manifests, grants, generic device registry, streams/events, policy and module lifetime. Profiles identify actual fitted hardware, shared pin/bus/CS/IRQ/power constraints and suitable drivers without any `BOARD_T5S3` decision path in generic core.

```text
optional firmware UI/scene -> display.frame/refresh -> EPD ELF -> EPD power
input consumer -> input.touch -> GT911 ELF -> I2C/IRQ/expander
radio consumer -> radio.lora -> SX1262 ELF -> SPI/GPIO/IRQ/power
location consumer -> location.* -> GNSS ELF -> UART/power
battery/clock consumers -> battery.*/time.rtc -> charger/gauge/RTC ELFs
storage clients -> storage.* -> SD ELF; separate bounded bootstrap/recovery
```

Keep the four package kinds and U2 independent versions, origin and roles. `system-core` applies only to a selected Pro profile, does not grant privilege and never forces installation on CAM/headless profiles. Each sustained data path uses **U1's generic installed-ELF stream endpoint**: touch data as bounded records/events, LoRa RX/TX packets as atomic typed records with metadata, GNSS byte source and `location.fix.v1`, continuous telemetry as typed observations, SD as bounded file bytes. Use event bus for low-volume change notifications. E-paper surface/frame writes need bounded chunks or explicit owned/pinned buffers with length, format, refresh completion and PSRAM/DMA-safe lifetime; never stuff full images into the v2 512-byte record queue. Avoid new device-specific firmware streams and only add a narrowly needed transform/tee/drop policy if a required functional path truly needs it.

## 4. Shared resources, lifecycle and safety

Inventory actual SPI/I2C, pad mux, CS, DMA, IRQ, expander outputs and dependency order. SD/LoRa/EPD may share incompatible resources: providers/profile enforce exclusive modes, idle CS and handoff rather than assuming simultaneous use. Shared GNSS/LoRa rail, EPD HV/VCOM and charger/USB power require single coherent ownership; a child never powers down a live sibling. Honor safe boot, failure, unload and sleep states. Drain IRQ/DMA/callbacks/tasks before unmapping; failed quiescence conservatively pins/quarantines code/dependencies, revokes clients and reports error rather than secretly activating a compiled fallback.

Refresh, radio transfers, SD and polling obey [bounded cooperative operations](COOPERATIVE_BOUNDED_OPERATIONS.md): maximum buffers/iterations/retries/time, byte/item plus elapsed-time checkpoints, real scheduler yields, throttled progress and recovery. Timing-critical scan waveforms may use bounded IRQ/asynchronous sections, not unsafe yields in the middle of a required electrical pulse. Missing/corrupt drivers expose unavailable capabilities and usable diagnostics, not boot assertions.

## 5. Display/touch conversion **without a full UI-as-ELF migration**

Keep the graphical firmware's UI layout, scenes, navigation, Settings and rendering/composition code for T5 Pro. Migrate *only* actual panel/touch hardware ownership into ELFs and make the UI host a replaceable/conditional **consumer of** `display.*` and input capabilities. Installed EPD driver owns scan, waveform, panel pins, power, refresh and completion; framework UI emits generic surface/frame requests with format/dimensions/orientation, full/partial refresh, bounded PSRAM/DMA buffer lifetime and error state. Adapt status/sleep clock, image/file viewer and other present UI consumers to generic display interface. Touch presents calibrated orientation-aware bounded events; display and touch absence must be independently handled when safe. Do not rename the firmware UI itself as an installable driver, write a second headless renderer or move UI into an ELF merely to complete U3.

SX1262 owns radio registers/commands, RX/TX mode, RF constraints, BUSY/IRQ, timeouts and shutdown. Never transmit merely because a driver installed or booted; radio messaging remains an independently chosen service/app. GNSS reuses actual `gps-nmea` source/record logic while extracting firmware UART, parser, rail and selection residue. RTC, charger/gauge, expander, buttons, lighting, sleep and other verified board hardware move to actual owners, not a disguised one-piece board ELF. SD needs a minimal separate bounded module-store/bootstrap/recovery reader and normal-runtime installable SD provider, with explicit ownership handoff; never strand mapped ELF bytes by removing its backing driver. Boot-only access must not publish a fake normal `storage.*` capability. Preserve safe charger defaults and document immutable boot operations separately.

## 6. Mandatory UI-optional startup and driverless CAM boot

**Binding design:** [UI-optional runtime and camera service boundary](HEADLESS_RUNTIME_AND_CAMERA_SERVICE_BOUNDARY.md). U3's core **must no longer derive its lifetime or progress from a graphical UI event loop**, including `ActivityManager` navigation, button poll, screen refresh, status-bar ticks or a foreground app. A finite startup sequence initializes generic CPU/port, bounded minimal storage/recovery, package inventory, generic provider graph, scheduler/service runtime and profile resolution; only then conditionally instantiates graphical UI if the profile selects it **and a working display capability exists**. It must skip missing display, fonts, icons, touch setup, display frame allocations, scene/springboard creation and UI loops entirely for headless profiles. If an optional display goes away, UI teardown cannot stop generic runtime/services; a UI-required profile may report the dependency missing instead of inventing success. Do not make touch universally mandatory for display when other legitimate input paths exist.

The owner must be able to flash an applicable generic U3 firmware onto the **actual ESP32-S3-CAM**, with zero T5 Pro and zero CAM-specific peripheral drivers or UI package installed, and reach stable recoverable idle. No EPD, GT911, LoRa, T5 power IC, RTC, expander, SD, gauge, T5 pin map/profile, camera sensor or graphical Settings is a startup dependency. Missing packages/capabilities prevent dependent apps from launching, never boot/runtime itself. No display or camera capability may be faked. The package manager performs non-UI inventory and recovery; missing optional SD cannot force a blocking loop. Bootstrap uses verified minimal internal module-store/recovery or another genuinely supported board-independent path; do not claim ability to install online/SD packages without a functional source.

Check chip/architecture, flash voltage/size, bootloader/partitions, PSRAM configuration, boot pins and generic OS port needs for **both actual boards**. Prefer *one identical flashable firmware image* if compatible; otherwise document only minimal necessary port/flash-layout divergence with one runtime source/ABI, never a compiled CAM/T5 driver switch. Essential idle startup cannot depend on T5 framebuffer or PSRAM being present; absent/smaller PSRAM must fail optional buffers gracefully. Stable idle requires active scheduler and service infrastructure, bounded tasks/memory, watchdog cooperation, no repeated UI/storage probes, meaningful uptime and recoverable errors. A device with no eligible apps/services is legitimately idle, not frozen.

Provide an observable **noninteractive** diagnostic/recovery path through a verified generic serial/ROM/port console where supported; boot, firmware/port version, selected profile, absent capabilities, memory, error and recovery status suffice. Do NOT require or create interactive serial commands, shell, serial menu, configuration portal, live network connection, camera application or Wi-Fi enrollment to meet U3. The eventual headless human interface may be serial; U3 needs only one-way logging and physically viable recovery, not a complete UI. Isolated port console/ROM access must not become a compiled production USB/serial host driver or forbidden fallback.

**Software acceptance:** audit actual init and scheduler/ActivityManager reachability, default config and conditional allocations, no-screen/no-touch/no-SD paths and service-loop liveness, build compatible CAM image(s) and Pro firmware, and fix known blocking source defects; no physical PASS merely from compilation. During owner-initiated Release Qualification flash the real CAM and verify stable driverless idle, no UI dependency, watchdog/memory/recovery and serial diagnostic path if fitted; then check actual Pro display/touch/driver functionality. Exact board/revision, image/layout and installed package inventory must be recorded. Camera image capture or driver provisioning is U4, not a substitute for U3 bare boot.

## 7. Migration ledger, build integration and sequence

Maintain actual component/revision -> compiled owner/caller -> real ELF/package/profile -> generic ABI/stream/dependency -> deleted core operation -> missing-driver/recovery behavior -> checks. Review the linked firmware, not just filename grep; remove old board physical fallback only after migration. Generic ABI compatibility is retained; bootstrap exception is isolated, no parallel stream registry/manager. Driver sources/manifests publish through U2 separate package infrastructure, U1 `.rte.zip`, coherent provenance/compatibility, safe version/rollback and no firmware rebuild for compatible updates. Historical installed data is preserved.

Use one U3 implementation PR and substantive complete slices: peripheral conversion and generic UI-capability integration; separate UI startup/runtime loop; headless CAM absence/bootstrap; combined source/build tests. CI provides feedback but is not a stop-work gate. No repeated intermediate owner hardware tests, expansive brittle milestone E2E or autonomous merge/release/flash. U3 is not permission to implement U4 manifest or CAM camera drivers early.

## 8. Work Complete and owner qualification

**Work Complete** requires all verified fitted Pro-specific hardware accounted for and working real ELF migration paths, graphical firmware still functional when its display package exists, no compiled normal peripheral fallback, safe shared resource lifecycle and package releases, **UI independent boot/scheduler/service lifecycle**, and an applicable CAM driverless headless absence/recovery build with no known blocking source/build defect. State tested and untested precisely. Physical CAM idle flash, Pro functionality and user acceptance remain pending until explicit **Release Qualification**. After Work Complete subsequent `continue` means **Improving Code**; only owner initiates qualification, merge, tag, publish, flash or U4.

**U4 handoff:** [U4](NEXT_MILESTONE_PROVISIONING_AND_ESP32_S3_CAM.md) adds manifest-driven headless install/activation of verified CAM drivers **and an automatically started camera streaming service**. It must reuse the already functional U3 UI-free scheduler and cannot camouflage a T5-only startup issue by installing a camera or compiling UI/device-specific fallbacks.

**Excluded from U3:** redoing U1 package/USB and U2 publishing; migrating intrinsic ESP32-S3 Wi-Fi/BLE; arbitrary external peripherals; new signing/marketplace; full UI-as-ELF migration; replacement graphical or interactive serial UI; first-run provisioning; actual CAM sensor/illumination/storage drivers and streaming service; major renderer or OS redesign outside the minimal conditional UI/device separation required for correct headless boot.
