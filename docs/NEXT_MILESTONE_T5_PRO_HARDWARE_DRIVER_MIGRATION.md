# U3 — T5 Pro hardware driver migration and UI-optional headless boot

**THIRD MILESTONE; SPECIFICATION ONLY.** Begins only after accepted U2 and explicit owner direction, on a new milestone implementation PR. Not permission to merge, publish, flash or assert physical qualification. Governing docs: [four-milestone order](FOUR_MILESTONE_STREAM_FIRST_EXECUTION_ORDER.md), [I²C bus ELF cutover](I2C_BOOTSTRAP_CUTOVER.md), [UI-optional boundary](HEADLESS_RUNTIME_AND_CAMERA_SERVICE_BOUNDARY.md), [hardware boundary](HARDWARE_AGNOSTIC_DRIVER_BOUNDARY.md), [streams](STREAM_PIPE_MILESTONE_ALLOCATION.md), [driver architecture](RUNTIME_DRIVER_ARCHITECTURE.md), [U1](NEXT_HARDWARE_TEST_MILESTONE.md), [U2](NEXT_MILESTONE_INDEPENDENT_PACKAGE_ECOSYSTEM.md) and [U4](NEXT_MILESTONE_PROVISIONING_AND_ESP32_S3_CAM.md). Inspect actual accepted firmware, Pro board revision/BOM/schematic, linked code and CAM flash/PSRAM/boot data before finalizing scope. Pin definitions do not prove fitted hardware.

## Objective and boundary

U3 has four outcomes: **(1)** every verified Pro board-added peripheral moves into functional installed driver/provider ELFs, including the two GPS apps' migration off firmware-specific GPS bridges; **(2)** the **existing U1 I²C bus ELF** changes its private backend from temporary firmware bus primitives to exclusive ELF-owned physical controller implementation **without changing its public bus capability or requiring already-migrated client drivers to be rewritten**; the temporary normal firmware API/imports are removed; **(3)** GUI remains compiled into firmware but optional at runtime and core boot, scheduler, manager, providers/services operate without display/touch or foreground app; **(4)** compatible firmware boots the owner's ESP32-S3-CAM with no Pro or CAM peripheral packages and reaches stable, observable, recoverable headless idle. No provisioning/camera capture until U4. Headless serial is one-way diagnostics, not a required interactive console.

Intrinsic ESP32-S3 CPU, integrated Wi-Fi/BLE, flash/PSRAM substrate, on-chip port primitives and ROM/RTOS bootstrap are excluded from the *board-added peripheral* conversion. Reuse provider capabilities and generic port functions, not board-specific core code. U1 owns USB extraction and already requires the stable I²C ELF interface, with the restricted **bus ELF-only** firmware backend. No other new hardware families, full UI-to-ELF conversion, provisioning or CAM sensor drivers.

Candidate addresses from `lib/Board_T5S3/pin.hpp` include GT911 `0x5D`, PCF85063 `0x51`, TPS65185 `0x68`, PCA9535 `0x20`, BQ25896 `0x6B`, BQ27220 `0x55`. Validate board revision, SD/LoRa/EPD pad-mux conflicts, power chains and interrupts; a mutex does not resolve shared-pin configuration conflicts. Device ELFs own device-register I/O, probe, policies, faults and teardown; the **I²C bus ELF** owns all public bus mediation/transfers, temporarily delegating raw controller operations to firmware until U3 cutover. Other ELFs must never call the temporary firmware API. Quiesce and pin/quarantine uncertain modules instead of invoking unmapped code.

Use U1 generic bounded data paths: LoRa atomic typed packets, GNSS records, touch events, telemetry, SD byte streams, display chunk/owned-frame capability. A full EPD frame cannot fit a v2 512-byte record. Avoid retained DMA/ELF pointers beyond ownership; use [cooperative bounded operations](COOPERATIVE_BOUNDED_OPERATIONS.md), finite retries/timeouts, real scheduler yields and explicit progress/recovery. Add optional transforms only for demonstrated dependencies. Keep one `.rte.zip` per package and U2 version/source/role rules; T5 `system-core` does not imply CAM requires display/touch.

## I²C root-bus cutover: replace bus ELF internals, not its consumers

[I²C Bus ELF Bootstrap and Cutover](I2C_BOOTSTRAP_CUTOVER.md) is the controlling contract. U1 must already supply an independently installed I²C bus ELF publishing stable `i2c.bus`, and its *private* firmware I²C imports must have been exclusive to that ELF. Power/expander/USB consumers built in U1/U2 already require `i2c.bus`; inspect their manifests/imports and **do not migrate them a second time**. Move additional verified U3 clients (touch, RTC, charger/gauge, etc.) to that same capability with native device-register/policy code in their own ELFs. No peripheral ELF gets `kernel.i2c`, `Wire` or another temporary port bridge.

Inspect actual bootstrap/power prerequisites and ensure the bus ELF can initialize using boot-alive CPU/port resources without depending on a power ELF that requires its own bus. Keep pin/rail safety. Implement full controller initialization, arbitration, transfers, fault recovery, pin/clock and teardown *inside the existing bus ELF* using appropriate versioned privileged CPU/RTOS primitives; keep its public bus capability ABI and package identity/version lineage compatible, with a controlled additive ABI version only if fundamentally necessary. Do not compile a parallel new bus provider or rename the package to conceal a version change.

For takeover, prevent new admissions; quiesce bus consumers; drain/cancel transfers; revoke old-generation handles; safe-state rails/pins; release and deinitialize firmware controller **before** the bus ELF exclusively initializes/claims the physical controller. Restart/rebind consumers via the unchanged published capability and fresh handles. Never run both controllers together, leave latent `Wire` owners, or fall back to firmware after ELF failure/removal. Delete/disable the normal firmware I²C primitive export and its runtime call sites; only genuinely indispensable, separately proven and isolated boot/recovery functions may remain, and they cannot publish a runtime capability or serve ordinary driver requests. Audit linked firmware symbols, the I²C ELF imports and every upstream package; zero direct transient firmware imports in any ELF after takeover. **U3 Work Complete requires both exclusive native bus ownership and unchanged operation of earlier peripheral ELFs.**

## GNSS: migrate the complete driver-to-app path

**Verified master baseline at September 18, 2026:** `Drivers/gps_nmea/driver.c` performs NMEA parsing/fix/baud logic but imports `t5_kernel_io_v1` UART/power callbacks; its manifest requires `kernel.serial`, `kernel.power`, `kernel.clock` and provides `position.gnss`. `GpsKernelIo.cpp` compiles T5 board-specific GPS UART/pins/`RadioPower`; `GpsDriverRuntime.cpp` names `gps-nmea`, manages leases/start/poll and sends `location.fix.v1` via native GNSS bridges. `NativeGpsBridge.cpp` exposes the legacy app API, while `NativeLocationBridge.cpp` calls the runtime directly. `Apps/gps.c` uses `t5_gps_get_api()`/start/read/stop; `Apps/gnss_stream_diagnostic.c` reads location records but hard-codes `gps-nmea`/UART and calls `location->poll`. These are existing migration targets, not evidence that the ELF or record stream does not exist.

1. Move receiver protocol, physical UART/configuration, pins, GPS/LoRa power rail operation, startup/poll and fixes into functional ELFs through generic port/bus/power capabilities and verified profiles. Reuse NMEA parser and existing record schema; no generic firmware copy of `GpsKernelIo.cpp` or board-specific GPS route.
2. Independent GNSS provider publishes semantic `location.position` and versioned `location.fix.v1` via the common provider/registry/stream mechanism, advancing with bounded driver-owned task/event scheduling rather than a foreground app's poll loop. Generic grants, backpressure, ownership and revocation are transport-neutral and available only for live installed providers.
3. Convert **both** `Apps/gps.c` and `Apps/gnss_stream_diagnostic.c` to resolve location by semantic capability, authorize and read records via generic streams, display fixes and diagnostics. No `T5GpsApi`, hard-coded `gps-nmea` or forced `location->poll`. Preserve diagnostic denial/revocation/backpressure behavior; audit other consumers. Bump each modified app version, manifests, import requirements and package artifacts.
4. Remove/reduce `GpsKernelIo.cpp`, `GpsDriverRuntime.cpp`, `NativeGpsBridge.cpp`, `NativeLocationBridge.cpp` and GNSS-specific `NativeStreamBridge` to genuinely generic port/registry/ABI compatibility paths. No normal firmware GNSS UART/power/source startup/poll/fix publisher or hidden fallback. Strict versioned app compatibility adapter only if required for unrelated installed legacy apps, never as a hardware owner or route for updated apps.
5. Test absent/uninstalled GNSS driver, multiple consumer contexts, permission denied/revoked, stream loss/backpressure, update/unload, safe UART/rail release and compatible alternative provider; no fabricated fix. Hardware receiver/alternate-provider evidence remains owner-qualified, not inferred from host tests.

**GNSS acceptance:** both apps obtain actual GNSS observations from installed hardware-owning driver through generic authorized semantic streams, without provider-ID dependency, firmware GPS dispatch or app-driven device polling.

## Optional GUI without making it an ELF

Boot CPU/port and minimal recovery/module store → package inventory/profile → generic scheduler, providers and services → **optional** GUI initialization only if profile requests it and usable `display.*` exists. Existing scene/navigation/render/Settings may remain in firmware but must consume driver display/input capabilities, not own hardware. Missing display/touch/fonts/UI cannot prevent boot, service work, recovery, idle, sleep or one-way diagnostics. Headless profile does not allocate framebuffer/EPD/fonts or poll ActivityManager renders. UI failure safely skips graphical work. Pro retains working GUI; scheduler does not depend on app input polling. No new GUI, shell or interactive serial manager.

## Driverless ESP32-S3-CAM acceptance

Owner's actual CAM boots compatible firmware with zero Pro/CAM-specific packages, no screen/touch/Pro power/LoRa/RTC/gauge/optional SD/GUI/camera driver/provisioning manifest. Missing capabilities prevent dependents safely, never crashes, watchdog loops or endless SD/driver retries. Retain minimal boot/recovery even with no SD, without falsely publishing normal storage. Basic one-way serial/ROM diagnostics are sufficient where supported. Stable low-work idle and recoverability constitute success. CAM must not initialize the retired T5 temporary I²C runtime adapter. Validate bootloader/partition/flash/PSRAM/pin compatibility; prefer identical binary if feasible, otherwise minimal documented port difference with the same hardware-blind source/ABI and no CAM/T5 peripheral switch in core.

## Execution and handoff

Maintain a compact ledger mapping each verified part/legacy firmware owner to its ELF/package/profile, consumer, safe absence, fallback removal and checks. **Track I²C bus ELF public ABI, its sole temporary import, exclusive handoff, removal of firmware adapter and regression of every already-migrated client without interface changes.** Include both GNSS native bridges/runtime, both apps and optional GUI/headless boot. One U3 implementation PR; proportionate firmware/ELF/app builds, source/link/import checks and safe absence/recovery tests, no repeated intermediate owner hardware test or idle CI waits.

**Work Complete** requires functional fitted peripheral ELFs, native controller ownership by the preexisting I²C bus ELF with no normal firmware adapter/import/fallback and compatibility of prior bus clients, both GPS apps using generic driver-published location streams, functioning optional Pro GUI, headless-capable runtime and CAM boot candidate with no known blocking source/build defects. Physical CAM idle and Pro peripheral testing remain **Release Qualification** when owner requests it. Only owner approves merge/release/flash/U4 advance.

**U4:** [provisioning and CAM](NEXT_MILESTONE_PROVISIONING_AND_ESP32_S3_CAM.md) adds functional CAM-specific ELFs and proves one actual captured image to available output; continuous streaming, network client and autostart are not gates. Do not work around U3 deficiencies by compiling CAM hardware/headless UI into core.
