# RiscRTE Device Capability Access API — Authorization and Transient Consent

Authority: [RiscRTE Platform Specification](RISCRTE_PLATFORM_SPEC.md), [Application Execution Context Architecture](APPLICATION_EXECUTION_CONTEXT_ARCHITECTURE.md), [Security Architecture](SECURITY_ARCHITECTURE.md), [Device Observation API](DEVICE_OBSERVATION_API.md) and [Application Capability Requirements](APP_CAPABILITY_REQUIREMENTS.md).

## Versioned contract

`T5DeviceApi.h` retains the byte-for-byte original v1 observation table. `t5_device_get_api(2)` returns the v1 prefix of `t5_device_api_v2`, which appends `acquire(capability, device, rights, out)`, `validate(lease, rights, device_out)` and `release(lease)`. `t5_device_get_api(3)` returns the original v2 table as a prefix of `t5_device_api_v3` and adds `request(capability, device, rights, out)`. Clients check the returned `api_version` and `struct_size` before casting. The exported getter symbol is unchanged. `acquire` in both v2 and v3 is **noninteractive and default-deny**; only the explicit v3 `request` can prompt.

An access handle is a generation-checked registry lease for one semantic capability on one specific device, owned by a unique execution-context invocation. Rights are READ (1), WRITE (2), CONFIGURE (4), or subsets of their union. `validate` checks the original invocation, handle and device generation, exact capability, requested-rights subset, current grant and device usability. Output handles reset on failure. `release` and context termination reclaim handles. Device removal and firmware revocation invalidate access immediately; an identical peripheral that reconnects receives a different handle. A later expansion of a grant does not expand an already-issued handle.

## Firmware-owned, one-run consent

`request` first attempts a previously authorized acquisition. If the exact rights are already granted it returns a new handle without prompting. Otherwise the bridge validates the requested rights and capability against a copied, available registry device, then calls the **firmware-only** `nativeDeviceConsentPrompt()` while the requesting ELF is paused on its owner task. The prompt presents a firmware-controlled device label, semantic capability and rights; it identifies the requesting executable as an **unverified local app** because package signatures and stable package identity are not implemented. No untrusted app text is accepted as a device label. Back, Power, Home, explicit denial, absent UI and the 30-second timeout return no permission or handle; a button held at prompt entry cannot count as approval. No persistent approval, 'always allow', automatic grant from an SD manifest or background permission decision exists.

After a positive decision the bridge reconciles discovery again and verifies the same running invocation, identical generation-qualified device and capability, and an available state **before** calling `CapabilityAccess::grantTrusted` and acquiring the requested access handle. A detached or replaced device cannot inherit the approval. Grants are bounded, owned by the current execution context and reclaimed on termination. The firmware does not export `grantTrusted`, `revokeTrusted` or the prompt as ELF symbols. An application cannot grant itself hardware access by editing its manifest. The synchronous prompt does not unload and relaunch the application and therefore does not accidentally transfer consent into a new invocation.

## Distinct resource layers and incomplete boundaries

An app manifest's required/optional dependency is a compatibility claim, not a grant. A v3 access handle represents rights, not a physical UART/USB session. Providers must separately enforce both rights and an exclusive/shared physical session before any device I/O. The existing GNSS and USB/serial compatibility APIs **have not yet been converted to check v3 authorization handles** and retain their documented legacy access behavior; neither v2 nor v3 currently provides end-to-end hardware isolation. Native ELF code also runs in a shared address space: this mechanism is not a process sandbox, and a lookalike app screen is not cryptographically distinguishable from the current prompt without additional trusted UI protections. Physical button/touch, screen layout, USB/VBUS/replug and GNSS acceptance remain outstanding.

Future work: stable authenticated package identity, signed ELF/manifest verification with executable-byte TOCTOU protection, trusted installation and device selection, persistent scoped consent only under authenticated identity, provider-side rights checks and migration away from legacy broad-access paths. Do not auto-grant mandatory dependencies as a shortcut.

## Verification

`test/resources/capability_access_test.cpp` checks default denial, bounded rights, ownership, device scoping, revocation, generation reuse and cleanup. `test/resources/device_bridge_v2_test.cpp` tests the real bridge with a simulated firmware prompt: denial, approval, explicit rights escalation, no repeated prompt for already granted rights, device detach during approval, and invocation teardown. `test/resources/device_api_v2_abi_test.c` verifies C11 binary-prefix compatibility through v3. The host suite and both firmware builds are required before deployment; simulated prompt tests do not establish physical input behavior.
