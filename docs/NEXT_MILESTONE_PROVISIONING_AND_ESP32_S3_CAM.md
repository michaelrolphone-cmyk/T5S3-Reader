# U4 — Declarative headless provisioning and ESP32-S3-CAM streaming proof

**Status: FOURTH MILESTONE; SPECIFICATION ONLY.** Follows U3; no implementation, merge, publish, flash or intermediate owner testing is authorized by this document. Begin on a fresh milestone implementation branch/PR from the accepted U3 baseline when the owner explicitly advances. Read [Platform Specification](RISCRTE_PLATFORM_SPEC.md), [hardware-agnostic driver boundary](HARDWARE_AGNOSTIC_DRIVER_BOUNDARY.md), [U3 T5 Pro and UI-optional boot](NEXT_MILESTONE_T5_PRO_HARDWARE_DRIVER_MIGRATION.md), [binding headless runtime and camera service contract](HEADLESS_RUNTIME_AND_CAMERA_SERVICE_BOUNDARY.md), [four-milestone order](FOUR_MILESTONE_STREAM_FIRST_EXECUTION_ORDER.md), [U2 independent publishing](NEXT_MILESTONE_INDEPENDENT_PACKAGE_ECOSYSTEM.md), [deployment provisioning](DEPLOYMENT_PROVISIONING.md), [ordinary ZIP package format](RISC_PACKAGE_FORMAT.md), [stream allocation](STREAM_PIPE_MILESTONE_ALLOCATION.md), [cooperative bounded work](COOPERATIVE_BOUNDED_OPERATIONS.md) and [implementation-first workflow](IMPLEMENTATION_FIRST_QUALIFICATION_WORKFLOW.md).

## 1. Objective and actual board prerequisite

**Prove that a single hardware-blind RiscRTE runtime supports two different ESP32-S3 devices, each configured by profile and installable packages: graphical T5 Pro with its own hardware ELFs and a headless ESP32-S3-CAM that is provisioned to run an actual camera streaming service.** U3 must first produce the stable, observable and recoverable **driverless** CAM boot in which the compiled firmware UI is skipped and the generic scheduler, package manager and services operate without a screen or foreground app. U4 may not paper over a U3 boot fault with a CAM-specific compiled fallback or invented UI. Neither the UI itself nor a headless serial interactive interface needs migration/implementation; graphical UI code may remain compiled into firmware but inactive for CAM.

Identify the owner's **actual CAM vendor, model, board revision, image sensor, flash/PSRAM, bootloader/partitions, pin map, power circuitry, boot/storage medium and any physically available data transport** from the physical unit and reliable documentation before implementing device drivers or choosing streaming output. The label `ESP32-S3-CAM` does not establish OV2640/OV5640, an SD slot, illumination, Wi-Fi provisioning state, flash size or a suitable network endpoint. Record measured/verified assumptions and limitations. U4 requires a reachable streaming consumer, so choose one real supported output transport and simple protocol at kickoff, not an aspirational network service with no way to reach it.

## 2. Declarative headless provisioning — desired state, not a new installer

Implement [Deployment Provisioning Manifest](DEPLOYMENT_PROVISIONING.md) as a bounded, versioned declarative input to U1's **one** four-kind `.rte.zip` manager and U2's independently hosted sources, using U3 profile/capability and UI-free service execution. Finalize discovery paths, schema/limits, board identity validation, version constraints, source pinning, transaction/recovery ledger and authorization. Reuse ordinary preflight, shared dependency graph, verified stage/commit/rollback, install inventory, activation and permissions; **no second package manager, CAM-only loader, signed framework, per-camera kernel switch or display-driven installation path**. Preserve old installs and data.

Manifest expresses stable deployment ID/revision, verified CPU/port/ABI and actual board/profile binding; required/optional packages of all four kinds with identity/source/version pins; required capabilities/dependencies; eligible system-core role per profile; limited authorized per-package configuration; explicit service startup/autostart intent; output-transport/network requirements and permitted camera configuration; immutable boot prerequisites and reapply/rollback policy. A CAM headless profile **omits graphical Settings, springboard, display, touch and all GUI-only apps**. Select only its required drivers/providers and camera streaming service; provisioning cannot assume UI availability, UI-loop dispatch or a foreground app and must not activate an unnecessary T5 peripheral. The same core generic scheduler/service framework continues running after provisioning without a visible activity.

**Medium/bootstrap cycle:** verified supported SD or other initial medium may contain ordinary ZIPs and manifest; use a minimal isolated boot/recovery reader or preinstalled independent bootstrap route. Never require an SD driver from an inaccessible SD card to install itself; a board with no verified SD slot uses a genuinely supported authorized alternative such as a bundle staged through existing recovery/programming. Missing media/manifest on a bare CAM must be nonfatal and leave stable U3 idle. U2 independent GitHub package source is an optional online path, never required to bootstrap its own network driver, network configuration or credentials. Do not claim Wi-Fi connectivity, console transport or arbitrary storage unless actually established on the board and port.

**Consent and headless use:** plan/preview/authorization must be achievable via a deliberately supported, owner-approved deployment/recovery workflow or previously authorized policy, without relying on a graphical prompt or a newly implemented interactive serial console. A verified signed-off offline deployment can represent consent only through the documented runtime permission model and explicit owner action at preparation, not mere manifest presence or SHA-256. For sensitive camera capture/network exposure, obtain explicit applicable authorization and configure access controls; no automatic trust or privilege from `system-core`, manifest text, installed driver or repository identity. Serial/ROM/debug channel may report boot, package progress and errors **one-way only** if physically supported. U4 does not require serial commands, shell, menus or an interactive provisioning UI.

Provisioning sequence: first eligible run or explicit approved reapply -> verify authentic board/port facts -> bounded manifest parse -> compute source/dependency/profile/configuration/service plan -> inspect/authorize through the chosen supported non-GUI owner workflow -> stage/check/install through ordinary engine -> activate providers and camera driver with correct grants -> apply allowed configuration -> start authorized streaming service through generic service manager -> verify actual capability/service/output readiness and installed inventory -> persist atomic deployment ledger. For unchanged completed manifest, subsequent boot is a no-op for package installation but still restores approved service runtime state. Changed revision needs explicit reapply; wrong board/version/source, missing package/transport, corruption, power loss and interruption recover without erasing last good generations or blocking generic headless boot. No plaintext portable Wi-Fi/API credentials or secrets in serial/logs/ledger; use an explicitly permitted safe configuration mechanism. Installation is never implicit execution permission.

## 3. Functional ESP32-S3-CAM hardware-owning ELF drivers

Inventory **verified fitted board-added hardware** against schematic/BOM/revision and reached code: actual sensor/module, camera bus/control/interface, sensor clock/reset/power, optional SD/media, lighting, buttons, regulators and other actual peripherals. Track precise owner, pin/power/bus/profile configuration, dependencies and safe absence. On-chip CPU/flash/PSRAM and ESP32-S3-integrated controller primitives remain generic port resources or reusable controller/provider dependencies, not fictional board devices. If camera capture requires additional CPU/OS functionality such as DMA/interrupt/cache/MMU access, provide a constrained generic versioned port primitive usable by unrelated future drivers—not `kernel.cam`, camera model-specific I/O or hardcoded pins in core.

At minimum build an independent real camera sensor/controller ELF chain for the actual sensor. The physical ELF(s) own probe/identification, sensor registers and timing, actual capture/peripheral interface, clock/pin/power sequence, bounded DMA/PSRAM frame allocations, IRQ/timeouts, stop/recovery and hardware quiescence. Split lower shared clock/interface/I2C/power providers where genuine reusable ownership demands it. Camera hardware cannot be a thin proxy to compiled firmware `esp_camera`. Publish semantic versioned `camera.*` capture/configuration/frame capabilities through U1's **single** generic provider/stream registry and permission/lifetime API; no camera-specific stream or framework bridge. Other actually fitted CAM peripherals needed by the selected profile have functional packages; do not assume nonexistent SD, LEDs or buttons.

Frame transport publishes format, dimensions, length, timestamp/sequence, source/device generation and other required metadata with **bounded chunks or an opaque owned-frame descriptor and explicit release/pinning**, preserving DMA/PSRAM and ELF unload safety. A full camera frame is not squeezed into a 512-byte typed record. Permission applies at source and downstream sinks; output revocation stops copies, releases in-flight frame ownership and prevents replaying private buffers. Handle capture failure, backpressure, slow client, disconnect and driver removal without unbounded retained frames, invalidated pointers, blocked UI tasks or core panics. Keep the runtime hardware-blind.

## 4. Independently installed camera streaming **service**

Deliver an actual `service` package, independently built/released using U2, which resolves generic `camera.*` capture/frame capability and a separately provided reachable transport/network capability, consumes the U1 bounded stream/frame endpoint and publishes a continuous stream through one documented practical protocol. This is a **persistent headless service**, not a screen app, test-only file saver, firmware web handler or implicit permanently running kernel camera task. Its manifest declares minimum ABI, dependencies, capability grants, limits/configuration and startup policy. It must be installable/updatable/removable without rebuilding normal firmware; no application launch, Settings navigation, display/touch or foreground UI loop is necessary to start, run or recover it.

At kickoff pick and document one actually supported output transport and receiver procedure—e.g. a minimal reachable IP stream if an existing ESP32-S3 network port/capability and permitted connectivity are available, or another real transport capable of carrying sequential camera frames. A tiny purpose-built streaming endpoint/protocol is in scope, **not** a browser dashboard, multi-user cloud stack, generalized video marketplace or full recorder. If IP is chosen, U4 must deliver the minimal generic network readiness/configuration needed for an actual client connection rather than claiming imaginary saved Wi-Fi; no wholesale intrinsic ESP32-S3 Wi-Fi/BLE driver conversion is required. Do not silently open an unrestricted camera endpoint or put plaintext credentials in a package manifest.

Start service only after authorized provisioning verified dependencies and configured its camera/output settings. Ensure generic service supervisor can start it headlessly at provision completion and restore desired auto-start on reboot **without rerunning package installation**. Declare readiness only when camera and transport endpoints are functional; distinguish installed/activated/started/listening/streaming states. Preserve bounded queue/frame ownership, frame rate/throughput/memory limits, backpressure/drop decisions, connection timeouts, graceful client disconnect, restart after temporary loss under finite policy, explicit stop/disable/revoke and safe shutdown before provider removal or update. The output consumer must receive a **sequence of actual separate captured frames**; a successful one-off snapshot or frame-to-file is supplementary diagnostic evidence, not U4 completion.

Noninteractive serial status/logging where supported shows deployment revision, installed/active packages, camera capability, service startup/readiness, client and error transitions without dumping frame payloads or secrets. This logging is observational, not an interactive serial UI. Missing camera, transport, authorization or provisioning media reports failure and preserves U3 driverless idle/recovery instead of crashing/rebooting or launching a graphical error modal.

## 5. Two-board and streaming acceptance

Use the same generic runtime source/CPU-port ABI, capability resolver, manager, streams, service lifecycle and permissions on T5 Pro and CAM. Prefer the **identical flash image** where verified bootloader, partition, flash voltage/size and memory permit; otherwise record the smallest necessary port/layout artifact difference, not a compiled T5/CAM camera/display branch. T5 profile starts its actual board driver graph and retained firmware GUI; CAM profile starts its actual camera graph and headless service without GUI. No hard-coded `BOARD_T5S3`, `BOARD_ESP32_S3_CAM`, sensor or pin list in generic decisions.

**U4 functional cases:** (a) U3 CAM still boots stable headless without any board drivers; (b) approved provisioning installs correct CAM packages/service without core source edit or firmware rebuild and preserves last-good state; (c) actual sensor probes, captures and exposes correct bounded frames; (d) service auto-starts following successful provisioning, **remains configured across reboot and delivers multiple successive frames to a separate real client**; (e) no graphical UI, app launch or interactive serial command is involved; (f) actual Pro GUI/peripherals still work under Pro profile with no CAM driver activation; (g) removing/disable camera/provider/service removes capability and streaming without compiled fallback and revokes in-flight handles; (h) wrong profile/source/corrupt/missing ZIP/media, lost transport/client, interruption/reboot and rollback produce bounded diagnosable recovery; (i) package/service identities, port/image artifacts and actual status are recorded, with same-binary claims only when physically established. Test permission refusal and safe camera/network exposure as appropriate.

## 6. Implementation order, completion and exclusions

1. Inspect accepted U3 idle CAM image and actual UI-less service/scheduler/port health; inventory actual CAM sensor, memory, boot medium, possible output channels and supported network stack. Select verified streaming transport/protocol and provisioning/authorization medium.
2. Implement bounded generic provisioning, owner-authorized manifest/config, package plan/transaction, durable idempotent ledger and noninteractive headless progress/diagnostics, reusing [Deployment Provisioning](DEPLOYMENT_PROVISIONING.md).
3. Implement/test actual CAM hardware ELF chain, safe generic frame streaming endpoint and correct profile/source/version/ABI; install/package via U2 source.
4. Build the independent streaming service and generic headless startup/restart integration, prove client data path by source/host/integration tests and relevant build/smoke checks without demanding intermediate owner hardware tests. Address known blockers as one coherent U4 software block.

**Work Complete:** fully integrated U4 source implementing recoverable deployment, correct actual driver packages, a genuinely runnable auto-start camera streaming service, one supported client protocol, no known blocking source/build defect and honest evidence of checks. Subsequent owner `continue` is **Improving Code**. Enter **Release Qualification** only when owner explicitly requests it; jointly qualify actual first-run/reapply/reboot/rollback, real image frames to a separate client and both boards. Physical PASS cannot be inferred from compilation or simulation. No autonomous merge, tag, release or flash.

**Explicitly outside U4:** redo U1 packages/U2 publishing/U3 T5 extraction; fully converting graphical firmware UI to ELF; implementing interactive serial shell/provisioning console, dashboard or mandatory display; migrating all ESP32-S3-intrinsic Wi-Fi/BLE hardware; arbitrary other camera boards; public third-party onboarding, cloud accounts, generalized marketplace, new package-signing framework, automated provisioning firmware flash or a new OS.
