# U4 — Headless provisioning and ESP32-S3-CAM multi-device proof

**FOURTH MILESTONE; SPECIFICATION ONLY.** Starts only when the owner advances from U3, on a fresh implementation branch and PR. No merge, release, flash or hardware result is implied. Governing specifications: [UI-optional headless boundary](HEADLESS_RUNTIME_AND_CAMERA_SERVICE_BOUNDARY.md), [U3](NEXT_MILESTONE_T5_PRO_HARDWARE_DRIVER_MIGRATION.md), [deployment provisioning](DEPLOYMENT_PROVISIONING.md), [four-milestone order](FOUR_MILESTONE_STREAM_FIRST_EXECUTION_ORDER.md), [streams allocation](STREAM_PIPE_MILESTONE_ALLOCATION.md), [hardware ownership](HARDWARE_AGNOSTIC_DRIVER_BOUNDARY.md), [U2 packages](NEXT_MILESTONE_INDEPENDENT_PACKAGE_ECOSYSTEM.md) and [bounded operations](COOPERATIVE_BOUNDED_OPERATIONS.md).

## Objective

Prove one generic RiscRTE runtime works on two distinct ESP32-S3 devices through board profiles and installable hardware drivers. U3 already supplies a flashable, stable, recoverable **driverless** ESP32-S3-CAM boot with optional graphical UI suppressed; the firmware UI itself may stay compiled in and continue running normally on T5 Pro. U4 provisions the CAM with the actual board drivers and demonstrates that it does useful work headlessly by **capturing an actual camera frame and writing one test image to an available output**. This is enough. A continuous camera streaming service is a possible later consumer, **not** an U4 deliverable. No interactive serial interface or graphical UI is required.

Before implementing drivers establish the owner's **exact CAM vendor/model/revision, fitted sensor, flash/PSRAM/boot and partition configuration, camera pin map, power, available bootstrap media and a genuine way to write/retrieve the image** from actual hardware and documentation. `ESP32-S3-CAM` alone proves no particular sensor, SD slot or network availability. Prefer one identical firmware image where verified flash/boot/memory compatibility permits; otherwise only minimal documented port/layout differences with one runtime source/ABI. No board-specific hardware routing compiled into generic firmware.

## 1. Provision through the existing manager

Finalize and implement the bounded declarative [provisioning manifest](DEPLOYMENT_PROVISIONING.md): verified board/profile/port and ABI, versioned deployment ID/revision, required/optional packages across four existing kinds, immutable source/version pins, dependencies and required capabilities, safe allowlisted configuration and explicit authorization. Use U1's ONE stream/ZIP package and transaction engine, U2 independent package repository and U3 UI-free boot/scheduler. A headless profile does not require Settings, springboard, display or touch. No second installer, signed package system, UI wizard or speculative automated network onboarding.

Choose a real bootstrappable medium or independent recovery/staging route for this **actual** CAM; do not assume SD or require an SD driver located on the SD card to mount itself. Missing/corrupt media or manifest leaves stable generic idle. On first eligible deployment or explicitly owner-approved reapply: verify real board/port facts; parse and preflight bounded package/source/dependency plan; enforce existing permissions; stage/install/activate via normal manager; apply allowed settings; compare desired installed and available capabilities; persist idempotent, recoverable status. Same completed manifest is a no-op on subsequent boot. New revision or privileged camera activation needs documented owner approval; possession of manifest or SHA-256 is not itself authority. Preserve existing files/installed generations on failure and do not expose plaintext secrets. One-way serial/port logs may report progress where genuinely supported; no interactive console, remote dashboard or display requirement.

Provisioning need only install and activate the drivers needed by the selected profile and make a simple diagnostic callable/run under generic non-graphical execution. **No automatic always-on camera service, external client, network connection, continuous capture or reboot auto-start is required.** Future provisioning schema may support startup services without U4 implementing camera streaming.

## 2. Implement actual board-specific CAM drivers

Inventory verified fitted sensor/module, camera bus/control, sensor clock/reset/power, optional SD, lighting, buttons and other relevant peripherals. Create functional separately packaged physical ELFs for the actual camera and the dependencies needed for the selected proof. Sensor/provider ELFs own probe/register I/O, camera timing, actual image capture, DMA/IRQ, bounded PSRAM/buffers, power and safe stop/recovery—not thin delegates to firmware `esp_camera`. Generic firmware exposes only CPU/OS port primitives, opaque capabilities, permissions, streams and driver lifecycle. If new CPU primitives are required, provide constrained reusable versioned port functions, not a camera-specific kernel bridge. Intrinsic ESP32-S3 Wi-Fi/BLE and other SoC devices are not a U4 peripheral migration.

Publish semantic versioned `camera.*` capabilities and frame metadata (format, length, dimensions and source/time as needed) using U1's generic stream/endpoint mechanism. Use bounded byte chunks or explicit owned/released frame buffers; the 512-byte record queue is not a raw full-frame container. Capture cancellation, driver unload, source revocation and failed output must not leak DMA buffers or leave stale ELF callbacks. Apply actual granted permissions and appropriate capture controls. Package independently through U2 as ordinary `.rte.zip`, with safe update/remove and profile-only activation.

## 3. Minimal headless functional demonstration

Provide a minimal ordinary application, service or diagnostic using `camera.*` and a **verified available output** to capture one real image, write it successfully and permit the owner to inspect/retrieve or otherwise verify the saved content. Choose a format/path appropriate to the sensor and actual available storage/transport. A file on verified SD/internal accessible storage is sufficient. If there is no suitable output, establish a supported minimal route rather than asserting an imaginary SD or Wi-Fi endpoint. Do not add a dedicated network server, remote video protocol, viewer, credentials flow or continuous service solely to validate the driver. The diagnostic runs without a graphical app, touch, interactive serial menu or UI event loop; noninteractive logs can state result and destination. Camera may be disabled and the runtime returns to stable headless operation.

## 4. Acceptance and milestone handoff

**Work Complete (software):** generic first-run/reapply and rollback implemented; verified CAM packages and profile install via ordinary manager; actual sensor driver and one-image diagnostic/output wired and buildable without known blocking defects; UI-free scheduler continues and Pro GUI path remains supported. Run proportionate build and focused invariant tests; do not demand intermediate owner hardware checks, all-green CI as a stop-work gate or a huge E2E harness. Follow existing Work Complete → Improving Code → owner-initiated Release Qualification workflow.

**Physical qualification, only when owner initiates:** flash the actual CAM, confirm U3 driverless idle still works, provision the CAM, verify camera probe and **one real saved/retrievable image**, reboots and recoverability, missing/removed packages, bad/absent provisioning source, and T5 Pro GUI/drivers. Record actual board/flash image/package identities and test evidence; do not call compilation physical proof. Same image is claimed only when exact board compatibility is verified.

**Deferred:** continuous camera streaming, remotely connected client, network setup, streaming service auto-start/restart, full GUI-to-ELF conversion, interactive serial provisioning interface, unrelated boards, public third-party onboarding, cloud/dashboard, new cryptographic signing or provisioning-driven firmware flashing. U4's yield is a **provisioned, functioning headless CAM with a real image**, not a complete video product.
