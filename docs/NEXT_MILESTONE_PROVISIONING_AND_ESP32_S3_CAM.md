# U4 — Declarative provisioning and ESP32-S3-CAM multi-device proof

**Status: FOURTH MILESTONE; SPECIFICATION ONLY.** Follows U3. This is not an implementation request, a new U1–U3 completion gate, or authorization to merge, publish, flash, or ask the owner for intermediate tests. Start U4 on a fresh milestone branch/PR from the accepted U3 baseline when the owner explicitly advances. Read [Platform Specification](RISCRTE_PLATFORM_SPEC.md), [hardware-agnostic driver boundary](HARDWARE_AGNOSTIC_DRIVER_BOUNDARY.md), [U3 T5 Pro migration](NEXT_MILESTONE_T5_PRO_HARDWARE_DRIVER_MIGRATION.md), [U2 independent publishing](NEXT_MILESTONE_INDEPENDENT_PACKAGE_ECOSYSTEM.md), [deployment provisioning design](DEPLOYMENT_PROVISIONING.md), [ordinary ZIP package format](RISC_PACKAGE_FORMAT.md), [cooperative bounded operations](COOPERATIVE_BOUNDED_OPERATIONS.md) and [three-step workflow](IMPLEMENTATION_FIRST_QUALIFICATION_WORKFLOW.md).

## 1. Objective and prerequisite

**Prove one hardware-blind RiscRTE runtime can operate on at least two distinct ESP32-S3 boards through data-selected profiles and independently installed physical driver packages, not by compiling T5 Pro and ESP32-S3-CAM hardware logic into alternate core firmware.** U3 must already demonstrate that the applicable generic runtime can be flashed to the owner's ESP32-S3-CAM, boots with **zero camera-board peripheral drivers installed**, stays stable and observable headless, and treats missing T5 Pro drivers/display/SD as absent capabilities. U4 starts from that verified software boundary; it must not disguise a U3 boot defect with a board-specific compiled fallback.

U4 makes this previously idle bare system useful: implement the deferred declarative provisioning flow and functional, independently distributed drivers for the actual ESP32-S3-CAM hardware. The owner's **exact ESP32-S3-CAM vendor/model/revision, fitted camera sensor, flash/PSRAM configuration, pin map, power wiring and boot/storage media must be established from the physical unit and reliable source data at kickoff**. `ESP32-S3-CAM` is not a sufficient camera sensor, GPIO map, flash layout, PSRAM capability or microSD assertion. Do not invent an OV2640/OV5640, SD slot or LED on an unverified board.

## 2. Provisioning is desired state, not a second installer

Implement the [Deployment Provisioning Manifest](DEPLOYMENT_PROVISIONING.md) as a bounded, versioned, declarative input to U1's *same* four-kind ZIP package manager, U2's independently hosted sources and U3's generic profiles/capabilities. Choose and document the finalized discovery path(s), parser/schema, maximum fields/bytes/count, compatibility/identity rules, recovery journal and authorization. Reuse the ordinary dependency planner, preflight, transaction, installed inventory, activation and permission enforcement; **no separate package loader, camera installer, platform-specific firmware application switch, implicit privilege escalation or signed-package subsystem**.

A deployment manifest must express stable deployment ID/revision, target CPU/port/ABI and verified board/profile binding; required and optional board/peripheral profiles; desired `application`, `driver`, `service` and `provider` packages with source and version pins/constraints; required capabilities; permitted initial per-package/configuration values; desired startup/headless services; explicit user-approved reapply behavior and safe rollback. Distinguish boot-critical port resources from installable drivers and profile-select only relevant `system-core` packages. Headless CAM profile must not require Settings, springboard, display, touch or a graphical installer. Offline provisioning must work with all necessary packages on supported removable media; independently hosted U2 GitHub packages are an optional online source, never required to bring up their own network driver.

**Bootstrap and source-medium cycle:** document a minimal port/recovery reader for the provisioning medium, or use an already supported independent bootstrap source; never require a driver located on an inaccessible SD card to mount that same card. On a CAM board without an SD interface, absence of an SD manifest is nonfatal; use a deliberately implemented, owner-authorized compatible alternative such as an installable bundle staged through the existing recovery/programming pathway. Do not assume the U3 headless runtime already provides networking, user credentials, local UI or arbitrary storage hardware. Provisioning may use a small generic console/serial diagnostic interface if supported by the CPU port; this is not a camera driver or a replacement for provider-owned runtime UART/USB.

Provisioning flow: detect only on first run or explicit reapply; verify actual platform/board facts before electrical activation; parse with finite memory/time and real scheduler yields; compute one bounded dependency/source plan; present an inspectable preview on an available authorized headless channel and obtain required consent; stage/verify/commit via ordinary manager; activate through generic provider lifecycle; apply authorized configuration; compare actual final inventory/capabilities with desired state; persist an atomic deployment ledger and report complete only after validation. Explicit no-op for unchanged completed manifest, consent for changed revision; handle missing media, unavailable source, version collision, wrong board/profile, corruption, power loss and interruption without erasing prior files or leaving partially activated unsafe hardware. Credentials must not be stored in plaintext portable manifests/logs. Installation alone never grants privileged imports or device authority.

## 3. ESP32-S3-CAM hardware-driver packages

Inventory each **verified board-added component** by BOM/schematic/revision and source/linked-code references: fitted camera module and image sensor, clock/reset/power circuitry, DVP/parallel or other sensor interface and control bus, optional SD storage, illumination/flash LED, buttons, regulators and other actual peripheral devices. Group by true physical ownership and lifecycle. On-chip CPU, flash/PSRAM memory substrate and ESP32-S3-integrated controller primitives are port resources or existing reusable controller/provider dependencies, not newly invented camera-board driver classes. If the camera requires a new CPU/OS primitive (e.g. camera-capable peripheral access, DMA/cache or interrupt support), add one **generic, versioned port interface** with constrained imports that can support other compatible drivers; never add `kernel.cam`, camera register transfers or CAM pin maps to generic firmware.

At minimum, deliver a real camera-sensor/controller driver path for the **actually installed sensor** that owns identification/probe, sensor register configuration, pixel-clock/timing and pin/power sequencing, capture state, bounded frame buffers, DMA/IRQ/timeout/failure handling, start/stop and physical quiescence. Lower camera interface/clock/bus/power providers may be separate ELFs where shared; the sensor ELF consumes them using versioned capability contracts. Publish semantic, versioned `camera.*` capture/frame/configuration capabilities, copied or explicitly owned frame/stream buffers, availability/events and correct frame lifetime/backpressure; core merely routes opaque capability handles and generic streams. Camera support cannot be a thin ELF proxy to firmware `esp_camera` operations. Use independently versioned `.rte.zip` packages, U2 separate package publishing, compatible profile requirements and manager-controlled update/rollback.

Add functional ELFs for **other actually fitted CAM-specific peripherals** needed for the stated board profile (e.g. storage or illumination) with honest omissions for absent parts. Avoid requiring a display to view captures: demonstrate a supported headless camera consumer, such as a minimal generic frame-to-file/stream diagnostic using already available capabilities, chosen from actual supported storage/transport. Do not invent Wi-Fi capture streaming, an entire camera application suite or a new web server merely to show proof. If a physical output path is unavailable, make the headless feature/diagnostic plan explicit before implementation rather than claiming frames were observed.

## 4. Real multi-board proof and absence semantics

Use the **same generic RiscRTE core source, capability resolver, manager, SDK and versioned CPU/OS port contract** for Pro and CAM. Prefer the same flashable firmware image when actual ESP32-S3 memory, flash/partition, bootloader and PSRAM configurations are compatible. If the physical boards require distinct flash layout/port bootstrap images, document the minimal unavoidable difference and prove it is data/port configuration rather than different compiled hardware-specific runtime behavior; never assert binary interchangeability without verifying the exact artifacts. The Pro profile enables only its fitted T5 hardware packages, and the CAM profile enables only its real camera-board package graph. No hard-coded `BOARD_T5S3`, `BOARD_ESP32_S3_CAM`, camera sensor ID, pin map or producer list belongs in the generic runtime decision paths.

U4 acceptance cases: (a) preserve U3 bare CAM headless boot without installed CAM drivers, (b) use the approved manifest/profile to install CAM drivers through the ordinary manager with no core source edit/firmware rebuild, (c) actual camera probe and bounded capture/frame delivery through a generic consumer, (d) functional T5 Pro after CAM packages exist, with correct profile-based applicability, (e) remove/disable CAM driver: camera capability disappears, handles/frames revoke and device quiesces without a compiled fallback, (f) bad/missing CAM packages or provisioning media fail recoverably, and (g) recovery/reboot/interrupted-install remains functional on both profiles. Compare exact firmware core commit/port ABI and installed package identities in the result; distinguish same image from same source where a port-level difference is unavoidable.

## 5. Implementation order, scope guard and handoff

1. Reinspect accepted U3 image, headless CAM absence behavior, two boards' actual boot/flash/PSRAM/storage differences and U2 package source. Reconcile the factual inventory before choosing pin maps, capture implementation or provisioning medium.
2. Implement bounded generic provisioning parser, intent/preview/authorization, ordinary package-plan integration, durable journal/idempotence, bootstrap and headless status path. Build on [Deployment Provisioning Manifest](DEPLOYMENT_PROVISIONING.md), not a new package manager.
3. Implement/install verified CAM hardware ELFs and profile(s), adapt only necessary generic camera consumer, maintain source/manifest/ABI/version/asset agreement and safe resource ownership.
4. Complete code and relevant build/smoke checks as one block, including absence/recovery, compatibility and reuse; no intermediate owner hardware tests, mandatory expansive E2E suite or CI stop-work gate. Declare **Work Complete** only after production source is wired and there is no known blocking software defect. Subsequent `continue` means **Improving Code**. Enter **Release Qualification** only on owner's explicit request; jointly test physical capture, provision/reboot/rollback and both device profiles at that stage. Never claim physical PASS before the owner actually performs it or autonomously merge/tag/release/flash.

**Explicitly outside U4:** reimplementing U1 packages/U2 publishing/U3 T5 migration; migrating all ESP32-S3-intrinsic Wi-Fi/BLE controllers as independent drivers; support for unspecified other cameras/ESP boards; open third-party developer onboarding; cloud account systems, generalized marketplaces, new cryptographic package signing, a new OS, mandatory display UI or automatic firmware flashing by provisioning.
