# Configured default application entry

The optional SD selector `/RiscRTE/default-app.txt` contains exactly one native ELF **basename** followed by an optional line ending, for example `camera_utility.elf`. It cannot contain a path, whitespace, extra lines, or a second choice. The selector names no device and grants no capability. The installed-app resolver verifies the package, sidecar, compatibility and artifact identity; the normal native ELF loader performs import and execution checks. On paper targets an absent selector resolves the installed `default.elf` Reader entry; if it is missing, the existing embedded GUI remains available. An absent selector leaves the normal idle provider runtime on headless targets. An invalid or unavailable selector is reported once per boot, with no retry or boot loop. A returned custom app is not relaunched automatically. The Reader entry uses the supervised child handoff described below.

On paper, the existing display and input host starts first. `Apps/default.c` is the PaperSpace/Reader application entry, packaged as the ordinary `application/default` package. It exports `app_main` and calls the versioned `t5_reader_entry_get_api(1)->pump()` callback until a handoff or stop. The first pump enters the same existing Home or saved-book destination, and subsequent pumps run the existing Reader input/activity loop. Home, themes, pins, recents, reader code and saved data remain firmware-owned and unchanged. This is an ELF-owned control-flow entry with firmware callbacks, not a second GUI. The new app is `1.0.0` and requires firmware `1.3.90`. The ordinary app builder stages its ELF/sidecar/catalog and `.rte.zip`; install it through the existing package workflow. No boot-time installer or release publication is added.

The Reader entry uses the same Arduino owner task, loader serialization, execution-context identity and verified package admission as other apps, with no native drawing session or long-held RenderLock. Its manifest must have no provider requirements, and hardware takeover is refused. The callback is available only to the supervisor owner task during that invocation; it refuses recursive pumps and yields the scheduler every iteration. Other apps and tasks cannot use the Reader callback to enter this loop.

Before an existing activity consumes a launch flag, it records its exact firmware-owned pointer and generation and returns `HANDOFF`. `default.elf` returns and unloads before the supervisor runs that original activity loop once. This preserves synchronous child/parent results and nested keyboard, Wi-Fi, file-browser, image, Settings and installed-app workflows. The next fresh `default.elf` invocation resumes the same ActivityManager state; it does not send the user Home or replay input. Sleep and power-off also run after unload, including light-sleep return. Failed unload blocks further dispatch/load rather than executing a child over retained code.

A verified custom selector other than `default.elf` still enters through `runNativeApp` and returns to Home. Missing, invalid or failed Reader entry admission falls back once to the same existing Home/book boot choice. Display failure, recovery and panic destinations bypass the entry. No selector and no installed Reader entry preserve the established retained e-paper behavior. The CAM port has no display or touch host. It enters the same native ELF `app_main` loader with an owner-task execution context, the existing stream runtime, installed provider graph, and U1 managed-application snapshot admission. The headless build links U1's strong admission hook, captures the verified sidecar before the loader opens the ELF, and checks the operation-owned ELF bytes. Its minimal app API supplies only cooperative `poll` and `millis`; unsupported UI/hardware takeover imports are absent or fail closed. Manifest `requires` are acquired before relocation, and an app may borrow only a declared installed provider capability. Cleanup runs before `dlclose`; a failed quiescence retains mapped provider resources rather than forcing another boot launch.

`Apps/camera_utility.c` is an installable `0.1.1` application requiring `camera.capture@1`. It requests one bounded 800×600 JPEG, waits cooperatively, validates complete JPEG framing, and writes one new `/sd/camera-utility-NNNN.jpg` through the generic stream file API. It tries at most 9999 four-digit names and never overwrites a prior capture. The output path and byte count may be logged, but image bytes are never logged or published. This small utility uses the already installed camera provider; it does not own sensor registers, SCCB, LCD_CAM or GDMA.

`cam-camera-app-experiment` is a lab-only deployment path. It embeds the ordinary application `.rte.zip`, installs it through U1's single package manager, and seeds the selector only when absent. It does not embed or reflash a driver package. The normal headless profile reads an owner-supplied selector and installed packages without a boot-time installer. The CAM experiment does not implement general U4 provisioning. It is independent of the callback-backed Reader entry described above.
