# U1 — ELF load verification performance and temporary bypass

**Binding U1 performance requirement; specification only.** The owner reports SHA/MD5 verification of ELF files on every load and a roughly ten-minute wait for ordinary button-driven app navigation. This is a user-observed symptom, not a measured benchmark or proof that a particular algorithm accounts for all delay. U1 cannot be Work Complete while routine app launches, menus, installed-package inventory or provider discovery synchronously rehash all already-installed ELF bytes.

## Confirmed source-level causes (master, September 18, 2026)

- `src/native/NativeAppHost.cpp`: `verifiedManagedApp()` calls `verifyOrdinarySdDirectory()` during installed inventory, launch selection, version lookup and `runNativeApp()` canonical-path verification; `runNativeApp()` also calls `verifyAppPair()` for sidecars.
- `src/runtime/packages/PackageOrdinarySdAdapter.cpp` → `PackageOrdinaryManagedInstall.h` → `PackageOrdinaryStage.h`: directory verification reparses the canonical manifest, enumerates files and SHA-256 hashes **each declared entry**; it is called by the installed capability resolver as well as app paths.
- `src/runtime/packages/InstalledCapabilityResolver.cpp`: capability lookup scans `/Drivers`, `/Providers` and `/Services` and rehashes every candidate on each snapshot/query, creating an expensive multiplicative cost when called during dependency resolution or opening an app.
- `src/native/AppPackageInstaller.cpp`: `verifyAppPair()` reads/validates sidecar and streams SHA-256 over the entire ELF whenever a digest exists, even for an ordinary installed-file check; the staging/publication path also uses this code and MUST NOT lose its content-integrity check.

Perform a final call-site/reachability audit for any MD5 digest and for driver, provider, service, ELF loader and App Store code before claiming all hot-path hashing is removed. MD5 was reported by the owner but the above identified hot path is demonstrably SHA-256. Do not replace SHA-256 with MD5, which solves neither repeated I/O nor the underlying trust boundary.

## Temporary workaround requested now

**Temporarily bypass only expensive full-file SHA/MD5 computation on normal load, launch, inventory, ordinary availability and capability discovery of a previously committed installed generation. Preserve the verification code; make the bypass explicit and easy to revert.** Keep bounded metadata parsing, manifests/identity/version/ABI/import/permission checks, ELF magic/architecture, sizes, exact file inventory, package-use gate, generation/lease checks, and handling of absent/incomplete/staged/backup files. Fail closed on invalid structure. Never imply that metadata-only verification proves unchanged executable content; emit accurate diagnostic terminology if needed.

**Do not bypass** cryptographic checks for downloaded packages, first-time install, staged bytes/readback, installation commit and update, recovery of incomplete or uncertain transactions, explicit integrity verification, or privileged authorization. A normal launch must not silently downgrade to a legacy flat ELF when canonical package metadata fails. Do not remove hash functions, alter published digests, change app IDs/versions unnecessarily, add an always-accept hash fake, or disable ELF format/import validation. A temporary bypass weakens detection of post-install SD tampering; document that limitation honestly. If the current implementation cannot separate hot paths from transaction/recovery verifiers safely, first split the verification modes and then bypass only the installed hot-path mode.

## U1 permanent implementation

At installation/staging, verify exact executable bytes and digest once through the common four-kind transaction; commit an atomic, generation-bound local verification receipt tied to canonical package kind/ID/version, manifest digest, ELF length/content digest and committed generation. Define durable state, boot/recovery trust policy and invalidation for overwrite, replacement, interrupted transaction, missing media/remount, generation mismatch, suspect metadata, explicit verify request and any other way executable bytes can be changed outside the manager. Neither a cached digest of unverified bytes nor modtime/size alone proves integrity on writable SD. Decide whether retained installed bytes are immutable/protected or must be reverified at meaningful trust boundaries, then implement that policy without blocking each UI interaction. Preserve full check on install/update, validate loader ABI/import/permissions at launch, and avoid repeated full tree scans during capability resolution by using a coherent package inventory snapshot invalidated on manager mutation.

Acceptance: normal menu/app launch and driver capability lookup have bounded work that does not scale with total installed ELF byte volume; installing/updating an ELF still rejects mismatched digests and leaves last-good generation safe; stale/wrong generation or interrupted transaction cannot reuse a receipt; explicit full integrity verification remains available. Record before/after launch and inventory timings and any regression, using a realistic installed package set and honest checks. The user controls hardware qualification; no new milestone, UI redesign or intermediate manual test gate.
