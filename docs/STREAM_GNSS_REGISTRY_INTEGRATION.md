# GNSS stream / Unified Device Registry integration

**Status:** Live cooperative GNSS implementation candidate in draft PR #67, now including its dependent provider authorization work in the **same PR targeting `master`**. Not yet validated on physical GPS hardware or approved for release. The canonical architectural references are [RiscRTE Platform Specification](RISCRTE_PLATFORM_SPEC.md), [Stream GNSS Record Adapter](STREAM_GNSS_RECORD_ADAPTER.md), [Runtime Driver Architecture](RUNTIME_DRIVER_ARCHITECTURE.md), [Provider Authorization Integration](PROVIDER_AUTHORIZATION_INTEGRATION.md), and [Platform Capability Roadmap](PLATFORM_CAPABILITY_ROADMAP.md).

## One device registry, one stream registry

`RuntimeDevices::systemRegistry()` is the only production device registry. The existing `RuntimeStreams::Registry` in `src/native/NativeStreamBridge.cpp` is passed by reference into `LiveGnssSession`; no separate stream registry or GPS polling task is created. `LocationLeaseBinding` verifies actual, generation-qualified `location.position` Registry grants. A manifest `Dependency` lease cannot serve as physical provider authority. `GpsDriverRuntime::borrowLocationSource()` returns the driver-owned device handle and *borrowed* physical grant only on the owning task in the running execution context, while the ELF driver is active. This accessor is firmware-only and never transfers lease ownership.

The bridge serializes attach, subscription, record publish, record read, pipe pumping, disconnect and cleanup using its existing stream mutex. The installable GPS ELF's synchronous UART read executes on its claiming application task **outside** that mutex; only a copied `t5_gps_state_t` is submitted to the coordinator. If one subscriber's bounded queue is full, all-or-nothing publication retains one pending copied observation. `beforePoll()` retries that observation before allowing another hardware read; retry success also consumes the current poll. No-fix, stale observations and duplicate accepted fixes do not become fabricated valid records. Optional measurements are unverified by default; numeric zero does not establish field presence.

On driver stop, the GNSS binding is disconnected before module unload, UART release or release of the driver's source grant. The data-plane marks previously accepted records as drainable to a terminal `DISCONNECTED` result, releases subscriber device grants, and never rebinds stale device generations. **The public authorization bridge is stricter:** if the original consent grant is revoked, released or invalidated by device replacement, a subsequent raw stream access destroys that subscription and queue, returns `DENIED`, and cannot drain its previously accepted records. This is intentional; loss of hardware authority is not permission to continue revealing buffered location data.

## Separate consent and physical ownership

`T5LocationApi.h` defines semantic API v1: `t5_location_get_api(1)` exposes `subscribe(authorization, token, stream)`, `poll(authorization)` and `unsubscribe(token)`. A caller must obtain `location.position` READ through the trusted device API v3 `request()` flow (or a trusted existing grant). The semantic bridge verifies the *issued* permission, running context, exact device generation, READ right and capability name before starting hardware, after startup and again after subscribing. An altitude grant, raw hardware grant or manifest dependency is insufficient. App-supplied owner IDs and driver ELF pointers are never accepted.

The concrete issued consent handle is then passed to the shared native stream bridge and bound to the returned record handle through firmware-only `GnssStreamAuthority`. Generic `record_read`, `record_info`, byte read/write and stream metadata check the same consent before touching the queue. On revocation, the queue closes and clears with its subscription. Regranting location through a **new** handle does not restore the old stream; the app must subscribe anew. `close()` and semantic `unsubscribe()` both release the matching subscriber grant and clear the binding. The bridge denies `connect()` for a GNSS stream even while the grant is valid: copying location into an unprotected pipe destination would bypass later revocation. GNSS-to-file/recorder delegation requires explicit authorization propagation and sink purge/cancel rules first. Already read app memory cannot be retracted, and native ELF memory isolation is not provided by this mechanism.

The active GPS source grant remains owned by `GpsDriverRuntime`. Consent-derived handles are separate non-physical dependency-mode registry leases; each subscriber also obtains its own shared `location.position` registry grant. `ExecutionContext::GnssDriver` is a distinct cleanup resource from `DeviceLeases` so permission grants and GPS startup can coexist in either order. GPS cleanup precedes stream cleanup and module unload, and the borrowed source grant is released exactly once.

**Concurrency limitation:** Up to four independent typed-record data-plane subscriptions exist, but firmware currently launches one application ELF at a time and polls GPS cooperatively on the claiming task. This is not a background location service simultaneously delivering data to four independently running applications. The stream scheduler never calls the GPS ELF; GNSS pipes are currently denied. If multiple execution tasks later run independently, permission mutation and stream-access validation must share synchronization.

## Passive GNSS discovery

On ESP32 firmware, `src/native/NativeDeviceBridge.cpp` calls passive `GpsDriverRuntime::available()` discovery from inventory, observation and authorization operations. The first call scans immediately; later calls are throttled to a 10-second interval using wrap-safe `millis()` subtraction. This prevents repeatedly hashing the package as an app polls events. The scan publishes the GNSS descriptor and package availability to the **existing** Unified Device Registry without starting GPS, claiming UART, powering the receiver or granting permission. Missing packages appear as unavailable on a supported board; installation may take up to one discovery interval to appear. Host USB fixtures omit the ESP32 hook.

`Apps/gnss_stream_diagnostic.c` uses `T5DeviceApi`, `T5LocationApi` and record streams, not the legacy `T5GpsApi` getter. Discovery happens through device observation on demand, not an autonomous scan in the main loop. A background GNSS discovery/service worker remains follow-on work.

## Native diagnostic application

`Apps/gnss_stream_diagnostic.c` and its sibling manifest provide a real ELF consumer. It discovers the GPS registry device, requests explicit physical-button READ permission, starts/subscribes through the semantic location API, validates the exact read-only `location.fix.v1` schema, polls on the app task, and decodes the 52-byte little-endian record without casting it to a native struct. It displays fix count, latitude, longitude, satellites and fix age, and releases the subscription and authorization on normal exit. Its minimum firmware is 1.2.14, matching this API introduction.

## Tests and acceptance gates

`test/streams/location_production_registry_test.cpp` covers the internal production registry, grant validation and state revocation, backpressure/retry, queue drain and generation replacement. `test/resources/gnss_permission_lifecycle_test.cpp` covers permission-first and GPS-first cleanup. `test/streams/location_native_bridge_test.cpp` links the actual semantic ABI bridge against mocked GPS and stream functions, including revocation during startup and subscription. `test/resources/gnss_stream_authority_test.cpp` covers consent binding for already-issued streams, release/regrant, spoofed dependencies, unrelated permissions, revocation and device generation. The raw stream bridge itself is compiled in both firmware board builds. All host tests run in the normal CI scripts with sanitizers for the authority checks; CI does not substitute for physical hardware tests.

**Release gate:** Pass host suites, both firmware builds, native ELF and released app validations, installable GPS and USB CDC driver checks, and firmware artifact staging on the *final* head. Exercise an actual board and installed GPS package: discover without legacy GPS calls; consent approval and denial; no-fix suppression; repeated live fixes, schema/coordinates, backpressure/retry, device removal, revoke/read denial, app exit/reentry, power ownership and cleanup. A simulated or compiled path is not a hardware acceptance result. The PR remains draft until physical acceptance is recorded.
