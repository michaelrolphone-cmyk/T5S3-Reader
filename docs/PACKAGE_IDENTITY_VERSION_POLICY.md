# Stable package identity, versioning and replacement policy

**Status:** Normative, September 18, 2026. Applies to all ordinary `application`, `driver`, `service` and `provider` packages, all code agents, and the U1 integrated implementation. Read [RiscRTE Platform Specification](RISCRTE_PLATFORM_SPEC.md), [ordinary package format](RISC_PACKAGE_FORMAT.md), [Application Version Policy](APP_VERSION_POLICY.md), [U1 milestone](NEXT_HARDWARE_TEST_MILESTONE.md) and [Driver Platform Reuse Acceptance](DRIVER_PLATFORM_REUSE_ACCEPTANCE.md). This policy does not itself migrate published/installed packages; U1 MUST implement the CDC identity repair and prevention gates before the owner hardware-test handoff.

## Separate three independent concepts

1. **Package identity (`kind`, stable `id`):** the immutable logical product/updatable lineage, e.g. driver `usb-cdc-acm`. Installed inventory, upgrade detection, dependency planning, online/SD discovery, asset publication and uninstall identify this same lineage. A feature rewrite, new implementation, new API, new transport dependency or new major release is not by itself a new package identity.
2. **Package version (`version`):** strictly increasing numeric `MAJOR.MINOR.PATCH` on each independently distributed change in that same identity. Release/tag/filename/source-folder names and content digests do not replace it. Builders must read the manifest version; no hard-coded `0.1.0` allowlist. Updates compare numeric versions per stable ID; refuse same-ID/same-version different content, downgrades or immutable-release mutations.
3. **Compatibility (`driver_abi`, `architecture`, required/provided capability API versions, firmware/runtime floor and profile):** independently validated requirements. `driver_abi: 2` or capability API 2 does not mean `id: foo-v2` or version `2.0.0`. A package's major version MAY advance with breaking compatibility, but an ABI bump must still be represented explicitly and checked. A major update never bypasses compatibility, resource ownership or unload safety.

Never append `-v2`, `-v3`, `_new`, an ABI number, a firmware version, or a revision suffix to the package `id` merely to release an updated implementation. Do not issue an updated driver under a different ID to escape version checks. A genuinely separate device family, provider with separately installable functionality, or intentionally parallel product may have a distinct stable ID **only** when the author records why both should coexist and supplies distinct capability/probe/binding policy. A source directory or build target may retain an internal historical suffix temporarily, but emitted package ID, package directory, release asset prefix, catalog entry and displayed installation identity MUST agree with the canonical stable ID; remove obsolete source names after reference migration when safe.

Every distributable driver/service/provider change to ELF, behavior, payload, relevant metadata, ABI/capability declarations, profiles or build options MUST increment its own manifest `version` in the same PR. One bump suffices for one cumulative unreleased change set. If multiple packages change, bump each separately. A no-op/docs-only change need not bump. Compare the new version with both the merge-base version and the latest actually published version for the identity; never roll back a published version when branches diverge. The same policy applies to apps under [Application Version Policy](APP_VERSION_POLICY.md). Firmware version increases alone do not advance package versions.

## Verified existing defect: USB CDC-ACM

On master as audited September 18, 2026:

| Source manifest | Package ID | Version | Driver ABI | Required capability | Provided capability | Implementation |
| --- | --- | --- | --- | --- | --- | --- |
| `Drivers/usb_cdc/manifest.json` | `usb-cdc-acm` | `0.1.0` | 1 | `kernel.usb.host@1` | `usb.class.cdc_acm@1` | Legacy descriptor/protocol proxy; firmware executes physical USB work. |
| `Drivers/usb_cdc_v2/manifest.json` | `usb-cdc-acm-v2` | `0.1.0` | 2 | `usb.host@1` | `serial.port@1` | Functional replacement owns CDC class/session operations through the installed USB host provider. |

These are **different implementations/ABIs of the same logical CDC-ACM driver**, not two CDC hardware families or two correctly versioned releases. The `-v2` suffix is a mistaken identity fork; the matching `0.1.0` values do not encode an update relationship. Current `scripts/build_installed_usb_stack.py` hard-codes `usb-cdc-acm-v2` and rejects every version except `0.1.0`, so merely editing one manifest would break package generation and would not repair installed identities. This is a U1 blocker, not an intentional future multi-driver taxonomy.

## Required U1 CDC repair (one end-to-end migration)

1. Inventory both source implementations, their actual release artifacts, on-device installation paths/inventory records, dependency references, active handles, catalog/driver manager rows, version comparisons, tests and historical releases. Inspect which old IDs and versions have actually shipped; do not assume only the two source-manifest versions were distributed. Identify further `-vN` identities, but do not blindly collapse genuinely different driver families. Record a precise mapping of old identity -> canonical lineage and an immutable historical compatibility policy.
2. Designate **`usb-cdc-acm` as the stable canonical CDC package ID**. Retain the functional ABI-2 physical driver as the implementation; replace its emitted manifest ID with the canonical ID and a strictly higher version than every previously distributed canonical `usb-cdc-acm` version (and choose a fresh version for its new canonical distribution). Keep `driver_abi: 2`, `requires: usb.host@1`, `provides: serial.port@1` as distinct compatibility declarations. Rename the source directory/build target only after references and asset paths are consistently migrated; do not create another parallel `-v3` package.
3. Remove the legacy ABI-1 firmware-proxy CDC from normal builds, online publication and current catalog. Convert fixed build/export/online install references to manifest-derived generic publication, so the canonical ID and its version are read from one real manifest rather than a hard-coded 7-driver list/`0.1.0` check. Do not rely on `usb-provider-catalog.json` or a firmware USB fallback. Do not erase past Git tags/assets or delete user data simply to tidy release lists.
4. Handle users with an installed `usb-cdc-acm-v2` or `usb-cdc-acm` generation explicitly: inspect both identities and ABI/dependencies; make a bounded replacement/retirement plan using ordinary transaction, rollback and safe quiescence. Refuse to replace an active/unsafe-to-unload driver, preserve prior working generation on interrupted migration, prevent two implementations from binding one physical device, avoid treating the old and new IDs as two independent preferred updates, and preserve unrelated packages. If the existing ordinary manager cannot safely rename identities atomically, implement a validated migration step or a clearly diagnosable user-approved remove/reinstall plan, **not** silent deletion, privilege bypass, automatic unsafe force-unload or fake identity aliases that survive forever.
5. Online/SD/install inventory, Driver Manager, generic catalog, exact package manifest, release asset prefix, provider declaration and version must agree. Only one current CDC-ACM product entry appears for fresh installs; its update semantics work for already installed canonical lineage. A historical importer, if necessary, is strictly bounded to known identities/generations and does not make the old firmware proxy available as fallback.

## Automated prevention / U1 acceptance

At the actual production package generator/ordinary manager/release pipeline and in host tests, fail on: duplicate `(kind, stable ID, architecture/target, version)` with differing bytes/metadata; same stable lineage shipped as `-vN` solely for ABI/rewrite; an updated ELF or distributable manifest with unchanged package version; a version less than or equal to the latest published version for that lineage; hard-coded approved driver version such as `0.1.0`; conflicting canonical/legacy IDs simultaneously advertised for the same update lineage; source manifest / `.package.json` / provider metadata / generic catalog / release asset / displayed version disagreement; incompatible ABI/dependencies imported as an update without a safe migration. Use a *documented explicit separate-product exception* only for intentionally coinstallable products, never automatically strip arbitrary suffixes.

Tests MUST exercise: legacy ABI-1 -> ABI-2 migration or safe refusal; `usb-cdc-acm-v2` legacy installed state -> canonical state or safe diagnosed replacement; fresh canonical install; higher-version upgrade; same-version changed bytes rejection; downgrade and cross-ABI incompatibility refusal; in-use/quiesce refusal; interrupted migration rollback; catalog absent/offline installation; no duplicate CDC rows and no core USB fallback. Link the exact tested versions/artifact hashes to one release-equivalent build at a single commit. A spec-only update or CI format check does not satisfy these gates.

**Stop rule:** U1 is not software complete while the forked CDC package identity remains in current source/release/inventory pathways, the installed legacy route lacks a safe disposition, or the version/identity automated gates are absent. Do not postpone this to hardware-test feedback, a separate stacked PR, the owner or a speculative provisioning milestone. The developer migration is a software task within existing U1 scope, not a request for an early owner hardware test.
