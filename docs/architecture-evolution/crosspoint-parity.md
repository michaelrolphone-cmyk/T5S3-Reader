# CrossPoint comparison and application boundary

## Baseline and meaning of parity

This is a **source-grounded comparison**, not a declaration of full parity or a request to implement the latest upstream release wholesale.

Reader's [initial README](https://github.com/michaelrolphone-cmyk/T5S3-Reader/blob/b04806126c1ec2af967d4d4798d239ac6e5c6088/README.md) identifies `crosspoint-reader/crosspoint-reader` as upstream. For a reproducible current comparison this review uses upstream **release 1.6.5**, commit `93e98bb78702e29868a16a13b80c40e6b36ccdff`, against RiscRTE Reader `3300229d0a232b4e6047a7c93b2f518c033c3cfa`. The owner's intended parity revision and meaning of “their app” are not yet selected. The original fork baseline, current upstream release and a future deployable reader application are different things.

Upstream [README](https://github.com/crosspoint-reader/crosspoint-reader/blob/93e98bb78702e29868a16a13b80c40e6b36ccdff/README.md) and [scope](https://github.com/crosspoint-reader/crosspoint-reader/blob/93e98bb78702e29868a16a13b80c40e6b36ccdff/SCOPE.md) describe a reading product across C3/S3 e-readers, with hardware-dependent features. RiscRTE also deliberately supports games and workbench tools. Keep the reader's product policy replaceable rather than importing its product limits into the platform.

Track three independent outcomes:
1. **Behavior parity:** the selected upstream feature works with equivalent content/state/user interaction on the applicable device
2. **Application portability:** that reader behavior is assembled as apps/services over capabilities, not a wrapper into compiled product code
3. **Binary/build compatibility:** the actual artifact targets the supported CPU/ABI and host interface; source lineage is not an executable compatibility guarantee

## What to decide before a port experiment

Select the target revision/features and obtain or define the actual upstream app build interface. Identify persistent data that must remain compatible: books, reading progress/bookmarks where supported, library caches, fonts, sync configuration and settings. Classify each dependency as reader/product code, reusable service, physical driver or irreducible boot/runtime primitive.

Then choose one representative end-to-end reader path and a small set of differentiating features from the map. The desired result is a reproducible reader build plus a bounded capability/service contract and preserved user behavior. It is not a new core export for every upstream function. Maintain current reading and workbench functionality throughout; unmet parity belongs in this map, not behind an unqualified “compatible” label.

This review did not execute upstream or Reader parity tests, test hardware, contact upstream, or modify either implementation. Broader README claims remain unverified until relevant source and behavior are checked.
