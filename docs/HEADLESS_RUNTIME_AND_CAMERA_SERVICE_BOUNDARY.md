# UI-optional runtime, headless boot, and provisioned camera service — U1–U4 contract

**Status: binding specification, September 18, 2026; no implementation implied.** This refines [four-milestone execution order](FOUR_MILESTONE_STREAM_FIRST_EXECUTION_ORDER.md), [U3](NEXT_MILESTONE_T5_PRO_HARDWARE_DRIVER_MIGRATION.md), [U4](NEXT_MILESTONE_PROVISIONING_AND_ESP32_S3_CAM.md), and [deployment provisioning](DEPLOYMENT_PROVISIONING.md). It takes precedence over older wording that permits a file-only camera diagnostic as U4's final deliverable or assumes an interactive headless UI. It does NOT add U0/U5, turn the UI into an ELF, require moving all UI code out of firmware, require a new network stack, or impose an intermediate owner hardware-test gate. Observe [stream allocation](STREAM_PIPE_MILESTONE_ALLOCATION.md), [hardware boundary](HARDWARE_AGNOSTIC_DRIVER_BOUNDARY.md), [bounded work](COOPERATIVE_BOUNDED_OPERATIONS.md) and [implementation-first workflow](IMPLEMENTATION_FIRST_QUALIFICATION_WORKFLOW.md).

## Ownership and sequencing

- **U1:** generic execution contexts, stream/pipe endpoints, four-kind manager/inventory/installation, driver/service lifecycle and recovery MUST be callable and make progress independently of a graphical event loop or an active UI application. Do not undertake broad UI boot refactoring in U1 beyond what these U1 foundations require. This is a prerequisite architecture, not an assertion that headless board boot already works.
- **U2:** device-profile `system-core` eligibility is conditional: graphical Settings, springboard, navigation and display apps are **not** core requirements for a minimal/headless profile. Catalog, source/update and package lifecycle run without a screen. U2 does not implement first-run provisioning or the U3 boot split.
- **U3:** implement the minimum conditional UI bootstrap and execution separation that makes display/input/UI optional at *runtime*, even if their general presentation, scene, navigation and settings code is still compiled into the firmware. This is the first actual headless boot acceptance. Extract actual T5 Pro display/touch/etc hardware into ELFs separately.
- **U4:** use U3's UI-optional runtime and U1/U2 package machinery to provision verified ESP32-S3-CAM driver packages and an independently installed, configured camera-streaming **service**, start it without opening a graphical application, preserve service behavior across reboot and recover from driver/network absence.

## U3: UI is an optional consumer, not the OS main loop

Define a finite, observable boot sequence: generic CPU/port/bootstrap and storage recovery -> generic package inventory/manager and capability/provider activation for the selected profile -> generic scheduler/services/job infrastructure -> **conditionally** initialize graphical UI/scene and input only if the profile requests UI and a compatible `display.*` provider is available and initialized. An optional UI may be started later when a suitable display is installed and enabled, or cleanly stopped if display/touch vanish. Missing touch does not automatically block a working display if independent input/navigation remains supported; missing display means UI startup is skipped, not attempted indefinitely. An unavailable optional UI application cannot hold the scheduler, package manager, recovery, driver registration or service lifecycle hostage.

The generic task/scheduler must run in headless mode; it must not be a callback made only by `ActivityManager` navigation, frame refresh, button polling, springboard launch or a foreground app. Eliminate every unconditional display/framebuffer/font/icon/touch allocation or initialization before determining the profile and capability. Preserve the existing graphical firmware on T5 Pro; do NOT rewrite scene/navigation/UI into ELF or build a replacement headless GUI. A known UI initialization failure follows bounded error/cleanup and enters recoverable headless mode only when a non-UI profile permits it; on a UI-required profile report the missing dependency without faking success. Nothing should blindly dereference a display or schedule a rendering task on headless boot.

No camera-board driver, T5-specific peripheral package, SD card, screen, settings app, touch or first-run manifest is required for the U3 CAM idle boot. If no eligible service/app exists, generic scheduler executes a stable low-work idle, watchdog/uptime/memory remain healthy and no repeated UI/storage discovery loop occurs. Preserve a real port-supported serial/ROM/debug logging route for one-way diagnostics (boot/profile/driver absence/error/recovery) without inventing a USB-host/CDC hardware fallback. **No interactive serial shell, terminal UI, provisioning prompts, network portal or end-user control API is required in U3.** Serial becomes a possible future headless human interface; in U3 it is simply observational and recovery-compatible when the particular board physically supports it.

**U3 software completion evidence:** inspect the real init and loop/task reachability, conditional allocations, no-display/no-touch/no-SD failure paths, service/scheduler liveness, driverless CAM-compatible build and retained Pro graphical functionality; no known blocking source/build error. During explicitly owner-initiated physical qualification, flash actual CAM, observe boot and stable idle with zero peripheral packages, absence diagnostics and recovery; separately confirm fitted Pro + installed drivers still runs UI. Do not call compiled paths physical proof.

## U4: provisioning starts an actual headless camera stream service

The authorized, declarative CAM deployment profile identifies the actual verified board/sensor and source/version-pinned dependencies; enables only its required drivers/providers, camera capture capability, compatible reachable output/network transport where available, a camera-streaming `service` package, its bounded configuration and authorized startup policy. The provisioning transaction uses the **one** package engine; after staging/verification/install and permissions/configuration it starts the service through generic service lifecycle, checks actual camera and transport readiness, verifies the service is running and a remote/independent consumer can receive **multiple genuine successive frames**, records activation results in its ledger, and restores approved service auto-start on reboot. Do not mark a streaming deployment complete simply because packages installed or one file captured. Service startup is a declared and authorized intent, not a privilege implied by a manifest hash, system-core label or untrusted package metadata.

The service is independently distributed from U2's package source and must not be a firmware-compiled camera/web app. It resolves semantic `camera.*` frame input and a separately provided generic transport/network output through capability grants and U1 streams, with no hard-coded camera model, pin map or T5 display dependency. Select one concrete protocol/client/output transport from actual supported board capabilities at U4 kickoff, document its endpoint/configuration and prove that a separate client can receive a live sequence. A small bounded camera streaming service is in scope; a browser dashboard, full recorder, cloud platform, interactive serial provisioning UI or generalized streaming marketplace is not. A local file-only diagnostic may supplement acceptance, but cannot replace the working streaming service. Do not silently claim Wi-Fi, a usable IP address, credentials or an SD slot unless supported/provisioned on the actual CAM; where the chosen output is IP, provide the minimal reusable existing network capability/configuration path needed to make it reachable, without converting intrinsic ESP32-S3 Wi-Fi/BLE hardware to ELF as a new milestone.

Frame path: camera ELF owns sensor, capture, DMA and physical frame lifetime; the generic stream/endpoint contract carries versioned frame metadata (format, dimensions, frame length, source identity, timestamp/sequence) and bounded chunks or opaque generation-qualified owned buffers with explicit release. A 512-byte v2 record is not an entire image. The service honors output backpressure, memory/frame/throughput bounds, client disconnect, cancellation, capture errors, driver quiescence, generation revocation and safe cleanup; no raw ELF pointer survives unload. Prevent unauthenticated/unapproved camera activation or inadvertent unrestricted network exposure; select documented applicable authorization/access controls and avoid plaintext secret storage/logging. Failure of camera, transport, permissions or boot source is reported via noninteractive diagnostic state and normal retry/recovery policy, not a foreground UI modal or boot loop. The UI remains optional throughout.

**U4 completion/qualification distinction:** Work Complete requires implemented source/build integration, startup persistence, real client protocol/transport path and no known blocking software defect; owner-controlled Release Qualification then physically verifies provisioning, authorized streaming to a separate client, multiple real frames, reboot autostart, stop/restart, disconnect, missing/removed driver, transaction recovery and T5 Pro regression. Report hardware tests not actually performed as pending. Do not auto-merge, release, flash or require owner to use a serial command prompt.
