# UI-optional runtime and minimal headless CAM proof — U1–U4 contract

**Binding scope clarification, September 18, 2026; specification only.** Read [U3](NEXT_MILESTONE_T5_PRO_HARDWARE_DRIVER_MIGRATION.md), [U4](NEXT_MILESTONE_PROVISIONING_AND_ESP32_S3_CAM.md) and [four-milestone order](FOUR_MILESTONE_STREAM_FIRST_EXECUTION_ORDER.md). This replaces this document's earlier, overextended requirement for a continuous camera streaming service, external client, network setup and automatic service restart. **One real captured test image written to an actually available output is sufficient for U4 camera proof.** A later camera streaming service is an example of what the architecture enables, not a U4 completion gate. No U0/U5, UI-as-ELF project, interactive serial UI or intermediate owner hardware test.

## Milestone boundaries

- **U1:** generic package operations, provider/stream lifecycles and service scheduling must not be intrinsically dependent on an active GUI event loop. Finish streams first and use them for USB and package ingestion; do not restructure all boot/UI code now.
- **U2:** profiles must allow a minimal/headless device to omit graphical Settings, springboard, display and touch from its required/core package set. No first-run provisioning or headless boot proof in U2.
- **U3:** keep graphical UI/scene/navigation compiled into the firmware, but make its initialization and execution conditional on the selected profile and available display capability. Generic boot, package inventory/recovery, scheduler and service runtime must run with no display, touch, framebuffer, GUI app or UI tick. No installed T5/CAM board drivers means stable, recoverable, low-work idle on the owner's ESP32-S3-CAM. One-way serial/ROM/port diagnostics are sufficient if supported; no shell or interactive UI required. Preserve working T5 Pro UI when drivers are fitted.
- **U4:** use that same UI-optional runtime to provision actual verified ESP32-S3-CAM driver packages and execute a simple headless camera diagnostic that captures an **actual sensor frame and writes one test image** to a verified accessible file/output using generic camera and stream/storage capabilities. A file format suited to the real sensor and output is fine; specify how the owner retrieves or verifies it without assuming an SD slot, Wi-Fi or interactive serial interface. A minimal service may execute the diagnostic if convenient, but an always-on streaming service, remote viewer, server, network credential flow, multiple successive frames and autostart after reboot are **not required**.

## U3 UI absence contract

Boot: generic CPU/port/bootstrap and recoverable package storage -> inventory and profile/capability resolution -> generic scheduler/provider/service runtime -> optional graphical UI **only if requested and `display.*` is available**. Do not run hardware display/touch init, framebuffer/font/icon allocations, springboard or render/touch loop in a headless profile. A missing or failed optional UI cannot block core runtime, package recovery or idle; shutdown/removal of a display cannot kill unrelated services. The generic scheduler must not rely on `ActivityManager` navigation/frame polling to make progress. On actual CAM, no T5 peripheral, camera driver, optional SD, GUI or manifest is needed to boot, observe diagnostics and recover. Preserve minimal noninteractive port logs where physically supported. U3's owner-initiated qualification checks real driverless CAM boot/idle and T5 Pro UI separately; compilation alone is not physical proof.

## U4 minimal image contract

First establish the actual CAM revision, sensor, flash/PSRAM, pinout and available bootstrap/output hardware; no guessed sensor, SD card, network or media. Use U1's single bounded stream and package manager, U2 source/packages, U3's generic service/driver execution and headless profile. Provision the real camera ELF and any verified dependencies without display or manual serial commands. Driver owns probe/registers/power/capture/DMA and buffers, not a proxy to compiled firmware camera code. The diagnostic consumes semantic `camera.*` frame data through bounded chunks or an explicitly owned/released frame; it writes one actual frame to the available verified output without passing unloaded ELF pointers, leaking buffers or requiring a client connection. Source loss, capture failure, interrupted write, no output medium and lack of authorization fail recoverably; ordinary idle remains available. Keep first-run/reapply consent within a real owner-authorized deployment path, not a hypothetical GUI prompt or automatic permission from a manifest.

**U4 completion:** functional headless provisioning, installed hardware-owning CAM driver, reachable diagnostic/output path and known software defects addressed. Physical image capture, retrieval, reboot/recovery and Pro regression are checked only in owner-directed Release Qualification. Continuous streaming, network provisioning, remote client, camera dashboard and persistent camera-service auto-start are explicitly deferred unless the owner later requests them.
