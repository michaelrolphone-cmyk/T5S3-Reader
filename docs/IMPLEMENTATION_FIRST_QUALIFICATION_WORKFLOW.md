# Implementation-first milestone and owner-led qualification workflow

**Status: binding owner-directed execution policy, September 18, 2026.** Applies to U1 and subsequent RiscRTE implementation milestones. Read with [AGENTS.md](../AGENTS.md), [U1 continuation protocol](U1_CONTINUATION_AND_COMPLETION_PROTOCOL.md), [U1 status reporting](U1_STATUS_REPORTING.md) and [U1 milestone](NEXT_HARDWARE_TEST_MILESTONE.md). This document defines **how to execute and hand off** the existing product scope, not permission to omit features or change hardware/driver/package architecture. Where other specs require complete CI, exhaustive testing, a same-SHA qualification dossier or user hardware tests **before implementation is deemed complete**, this owner's newer explicit two-phase workflow overrides those procedural gates. Feature requirements, bounded-input safety, non-destructive migration, version correctness and known defects remain engineering obligations.

## The deliberate trade-off

**Favor code throughput and complete functional work blocks over continuous qualification.** The owner does not have time to micromanage source edits, approve routine workflows, test hardware after each subtask, or pay for elaborate short-lived tests of an evolving end-to-end architecture. Make implementation decisions independently within the specs; inspect existing code, implement actual end-to-end production paths, integrate components as they evolve, commit coherent checkpoints and move to the next unfinished task on each `continue`. Do not spend an entire turn on plans, status, speculative redesigns, line-by-line formal validation or CI polling when useful independent source work is available. Never equate a documentation commit with completing implementation.

Use targeted builds, unit/smoke tests and defect-driven checks when they accelerate debugging or protect **stable** invariants (e.g. ZIP bounds/traversal, safe transactional replacement, package identity/versioning, executable authorization, driver lifetime). Fix actual compilation/integration errors discovered during work. Do not introduce a sprawling one-milestone end-to-end test harness just to establish implementation completion; it can be brittle and constrain legitimate design changes. Test suites may be expanded deliberately during subsequent collaborative qualification. Do not delete useful existing tests or knowingly leave data-loss/privilege hazards unresolved under the banner of speed.

**CI is feedback, not a stop-work queue.** Do not wait for all CI jobs, branch-rule approvals or release publishing to advance independent implementation. Do not interpret a green unrelated workflow as proof of runtime operation; do not misreport an observed failure as PASS. An actionable failing build is a defect to repair, not a reason to ask the owner to operate CI every five minutes. GitHub quota handling follows the continuation protocol and must be evidence-based.

## Two distinct phases and exact completion signal

### Phase A — autonomous implementation

Starting from the current merged specification baseline, use ONE milestone implementation branch/PR targeting master. Complete **all requested functional code, cross-component wiring, applicable manifests/version increments, package/build path migration and material safety behavior** as one integrated work block. Keep a compact progress ledger, not a qualification bureaucracy. Do not ask for intermediate physical checks or freeze a complete release asset inventory after every commit.

**`Work Complete` means the requested IMPLEMENTATION BLOCK is finished**: all in-scope production features are actually present and connected, relevant source/build inconsistencies and known blocking defects have been addressed, and the owner has a coherent candidate to begin testing. It does **not** mean every behavior is exhaustively tested, CI unanimously green, hardware proven, release approved, or quality certified. Record what was built/checked, what was not run and any uncertainty in a brief handoff. Do not claim completion for specs-only changes, stub/proxy substitutes, missing functionality or a candidate known not to build/launch. If a meaningful build cannot be executed due to tooling or access, disclose that limit; do not fabricate its result. The first truthful Phase-A completion message includes a standalone bold **Work Complete** line and ends with **Implementation Complete Awaiting Qualification** (four words). The owner's ability to begin qualification later is not a reason to delay completion of implementation.

If the owner continues saying `continue` after implementation is finished but is unavailable for testing, perform useful independent source audits, focused tests, defect fixes and improvements of the completed work. Do not expand the milestone into unrelated functionality or manufacture a new mandatory test gate. An actual discovered blocking defect returns the implementation to IN PROGRESS; once fixed, report the updated state accurately.

### Phase B — collaborative qualification and release

**Only when the owner has time and asks to validate/test/qualify:** jointly run the real deployment/integration/hardware procedures, diagnose failures, patch the same milestone work, repeat the relevant checks and decide whether the candidate is qualified. Qualification can establish an exact tested revision, coherent release artifact set, final compatibility/version checks and release readiness **at this stage**. A passed compiler or host test is not a claim of physical success. **`Release Qualified` is not an agent's unilateral declaration:** report qualification only after the required verification is actually performed and the owner accepts it. Release/tag/merge/flash remain owner-authorized operations; then the next milestone begins from the accepted baseline.

Do not move Phase-B qualification gates backward into Phase A. In particular: comprehensive milestone-specific E2E suites, all-green CI as a global precondition, immutable artifact freezes at every interim commit, repeated hardware-test reminders and repeated requests for manual GitHub workflow approvals are explicitly disallowed as default Phase-A behavior. Preserve honest evidence and the ability to validate later.

## Minimal owner-facing communication

Briefly report code changed, actionable blocker/observed check and next work item. End every U1 work message with one bold 2–5-word state under [U1 status reporting](U1_STATUS_REPORTING.md). During implementation: **Implementation In Progress**. After finished implementation but before joint qualification: **Implementation Complete Awaiting Qualification**. During owner-led testing: **Qualification In Progress**. Only after demonstrated and owner-accepted qualification: **Release Qualified Awaiting Authorization**. A confirmed GitHub rate limit must be reported transparently and stops remote calls, not misrepresented as implementation completion.
