# U1–U4 execution order — streams first, four milestones only

**Normative sequencing and yield contract; September 18, 2026; specification only.** This document refines implementation order and stream-related acceptance in [U1](NEXT_HARDWARE_TEST_MILESTONE.md), [U2](NEXT_MILESTONE_INDEPENDENT_PACKAGE_ECOSYSTEM.md), [U3](NEXT_MILESTONE_T5_PRO_HARDWARE_DRIVER_MIGRATION.md) and [U4](NEXT_MILESTONE_PROVISIONING_AND_ESP32_S3_CAM.md). Read the [source-backed streams work allocation](STREAM_PIPE_MILESTONE_ALLOCATION.md), [UI-optional/headless and camera-stream service contract](HEADLESS_RUNTIME_AND_CAMERA_SERVICE_BOUNDARY.md), [Stream/Pipe Architecture](STREAM_PIPE_ARCHITECTURE.md), [hardware boundary](HARDWARE_AGNOSTIC_DRIVER_BOUNDARY.md) and [implementation-first three-step workflow](IMPLEMENTATION_FIRST_QUALIFICATION_WORKFLOW.md). If an older U1 workstream places USB/packages ahead of streams, **this dependency order takes precedence**. If an older U4 example permits only a frame-to-file diagnostic, **the service-stream acceptance below takes precedence**. No U0, no independent stream/GUI PR, release, owner test or qualification gate. All other product requirements and safety checks remain intact. No implementation or physical verification is implied by specification edits.

## U1 — generic streams first, then USB and package integration

**Entry:** [PR #86](https://github.com/michaelrolphone-cmyk/T5S3-Reader/pull/86) merges as a docs baseline and owner initiates one fresh U1 implementation PR from current `master`; inspect source, not assumptions.

**First workstream: finish the preexisting stream/pipe foundation before committing new USB driver or installer architecture.** Preserve v1 byte streams, v2 record streams, App Store HTTP transfer, `serial.port`, GNSS and existing callers. Add append-only versioned hardware-owning installed-ELF producer/sink endpoints in the single generic registry/capability resolver. Bind endpoint instances/generations, separate provider vs consumer execution contexts, permissions, cross-context open/connect/close, source loss, cancellation and safe unload. No USB/GNSS-specific stream/callback bridge in compiled normal firmware. Bound memory/queues/bytes/records/wall time, backpressure, real scheduler yields and in-flight I/O lifetime. Never hold the global stream mutex across potentially blocking provider or SD I/O. Protected pipe destinations require downstream authorization and revocation/purge, otherwise fail closed. Non-USB witness uses the same producer mechanism where relevant. No optional full transform/tee/merge/camera/display/LoRa development just to finish this foundation.

**Second workstream: USB on top of streams.** Physical controller/host/class/power/required I2C logic lives in real ELFs; those publish semantic `serial.port` and RX/TX byte streams. Serial Monitor and ESP ROM programmer consume streams with separate baud/framing/DTR/RTS controls, safe reconnect, no firmware USB I/O, special resolver branch or resident fallback. New compatible class driver requires no firmware edit.

**Third workstream: package ingestion on top of streams.** Four-kind manager and `.rte.zip` use one bounded online HTTP/archive and offline file/archive stream-to-stage path with existing verification, SHA-256, identity/version, dependency plans, ZIP bootstrap, rollback and App Store transfer preserved. No split fixed driver downloader, alternate installer, whole-archive allocation or USB catalog. Remove unwanted signing-only code independently without weakening necessary integrity.

**UI interface constraint for U1:** generic streams, package inventory/transaction, service/provider lifecycle and recovery must have no essential dependency on a displayed scene, foreground app or graphical event-loop callback. Do not broadly refactor the current firmware UI or claim headless board boot yet; the conditional UI boot split is a U3 requirement.

**U1 Work Complete:** working installed-ELF cross-context endpoint and safe unload; USB Serial Monitor and programmer use actual driver-produced streams; generic bounded ZIP ingestion; v1/v2 compatibility, focused tests and no known blocking source/build defects. One integrated owner hardware-test handoff follows code completion, never an intermediate streams gate. **Yield:** reusable hardware-blind stream/driver/package foundation.

## U2 — independent packages and headless-eligible profiles

**Entry:** accepted U1 and explicit U2 start. Owner's separate GitHub package repo, independent publishing, source management/update discovery, cross-source dependencies, provenance/UI and role/profile metadata reuse U1 package/stream interfaces. Catalog/ZIP reads and source refresh use generic bounded transfers, snapshot pinning, cancellation, progress and ordinary transaction path regardless of GitHub account. Do not create source-specific downloaders or installers; offline inventory and SD operations survive source outages.

**Headless policy only:** a minimal/headless profile does not require graphical Settings, springboard, display, touch or GUI installation screens for system-core eligibility; source/catalog and package lifecycle operate through non-graphical APIs. This is role/profile metadata and reusable APIs, not U3's boot restructuring or U4 first-run provisioning. Do not create an interactive serial substitute.

**U2 Work Complete:** owner's independent repo publishes/updates four kinds without firmware rebuild or source-specific stream adapter; profiles classify core/optional requirements for graphical and headless systems; source changes cannot silently redirect installs. **Yield:** independent release/update lifecycles and headless-compatible package selection.

## U3 — T5 peripherals plus UI-optional driverless CAM boot

**Entry:** accepted U2 and explicit owner U3 start. Each verified board-added T5 Pro peripheral becomes a hardware-owning ELF. Touch emits typed input records/events; LoRa atomic packet records plus RF controls; GNSS reuses merged `location.fix.v1` while eliminating compiled GNSS UART/rail/poll residue; SD runtime supplies generic bytes outside minimal bootstrap; telemetry uses typed records/events. Display exposes versioned surface/frame transfer, bounded chunks or owned/pinned buffers, safe DMA/PSRAM/refresh semantics—never fake full frames as 512-byte records or leave panel scanning in firmware. Drivers use U1 capabilities, permissions, endpoint loss, revocation, cooperative work and quiescence; only implement required optional stream topology extensions.

**UI boundary is mandatory in U3:** the firmware may keep its graphical UI/scene/navigation/Settings implementation compiled in, but boot and operating-system/service scheduler are independent of UI initialization, display/touch providers, foreground apps, and `ActivityManager` rendering/poll loops. Discover profile/capabilities first, launch UI only when profile requests it and usable display exists; missing/failed optional UI cannot block package inventory/recovery, drivers, services, sleep/idle, watchdog or diagnostics. Do not allocate display buffers/fonts/touch resources unconditionally; preserve full T5 Pro GUI. A headless CAM with no T5/CAM drivers, optional SD, UI app or provisioning manifest boots and remains stable, low-work and recoverable. Serial/ROM/port diagnostics are one-way observation only on a verified supported path: **no interactive CLI, replacement headless GUI or provisioning input required**. See [binding headless boundary](HEADLESS_RUNTIME_AND_CAMERA_SERVICE_BOUNDARY.md).

**U3 Work Complete:** real T5 Pro ELF hardware control, GUI still functional when providers exist, no required UI startup path, no-screen/no-driver CAM-compatible image builds and absence/idle/recovery implementation with no known blocking defects. Actual Pro operation and CAM flash/idle are verified only in owner-initiated Release Qualification. **Yield:** runtime that can operate graphically on T5 and boot cleanly without UI or drivers on CAM.

## U4 — provision CAM and automatically operate a camera streaming service

**Entry:** accepted U3 headless CAM baseline and explicit owner U4 start. Implement U4 first-run/approved-reapply manifest using U1/U2 one streaming package engine and verified bootstrappable medium/recovery route. Establish actual CAM board/sensor, implement board-specific camera and fitted peripheral ELFs, and install/authorize/configure an independent **camera streaming service** using versioned semantic frame capability plus a real, independently reachable output transport selected from verified supported hardware. Service consumes bounded metadata-rich camera frames (format, dimensions, length, timestamp/source/sequence, explicit PSRAM/DMA-safe buffer ownership, release and generation), supplies bounded stream chunks/frames to a client, handles backpressure, client disconnect, source revoke and cleanup. No raw ELF pointer retention, UI dependency, giant record queue, firmware-specific camera/web app or compulsory display.

Provisioning expresses the authorized service package, output/network prerequisites, safe configuration and autostart. After installation/activation it verifies the service's actual running/readiness state and a **real sequence of frames received by a separate headless client** at physical qualification; persists desired service autostart across reboot. A single frame-to-file diagnostic is optional supporting evidence, not the final streaming yield. If IP/Wi-Fi output is chosen, verify compatible existing port/network path and provision permitted connectivity without assuming Wi-Fi credentials magically exist or migrating intrinsic ESP32-S3 radios into ELFs. No general interactive serial UI, cloud platform, video dashboard or unapproved camera exposure. Failures preserve stable headless boot and observable diagnostics.

**U4 Work Complete:** implemented source/build integration of provisioning, real camera ELFs and independently installable auto-start streaming service, observable noninteractive startup/recovery, without known blocking software defects. Physical owner qualification then checks multiple real frames to a separate client, reboot autostart, driver removal, transport loss, recovery and both board profiles. **Yield:** a provisioned headless CAM that actually streams images while T5 Pro continues to use its own GUI/drivers on the same generic runtime architecture.

## Exclusions and change control

Four milestones only: no U0, separate streams release, full UI-as-ELF migration, interactive headless serial shell or mandatory screen for provisioning. The entire aspirational [Stream/Pipe Architecture](STREAM_PIPE_ARCHITECTURE.md) is not required as a blanket gate; optional transforms, tee/merge, replay, zero-copy pools, persistent topology and visualization are deferred unless a required consumer needs a narrow implementation. Boundedness, ownership, permissions, safe detach and graceful UI absence are mandatory wherever used. Only owner advances milestones, merges, publishes, flashes and initiates physical Release Qualification. No code or test success follows from editing this plan.
