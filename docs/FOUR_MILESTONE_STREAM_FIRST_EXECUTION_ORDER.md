# U1–U4 execution order — streams first; four milestones

**Normative sequencing; specification only.** Read [stream source audit/allocation](STREAM_PIPE_MILESTONE_ALLOCATION.md), [UI-optional headless boundary](HEADLESS_RUNTIME_AND_CAMERA_SERVICE_BOUNDARY.md), [hardware boundary](HARDWARE_AGNOSTIC_DRIVER_BOUNDARY.md) and each milestone below. This dependency order overrides older U1 A–F execution ordering; U4's one-image proof overrides earlier camera-streaming-service language. No U0, separate stream-release gate, interim hardware tests, UI-as-ELF conversion or automatic merge/release/flash. Actual code, builds and physical results are not established by these specs.

## U1 — finish streams first, then USB and packages

Starts only after owner merges PR #86 and initiates ONE new implementation PR from master. Inspect actual merged v1 byte/v2 record streams, pipes, App Store HTTP transfer, GNSS and `serial.port` implementations. **First implement generic hardware-owning installed-ELF byte/record producer and sink endpoints** in the single registry/capability system: execution-context ownership, generation, rights, cross-context open/connect, bounded buffer and deadlines, revocation, cancellation, safe quiescence and no blocking provider I/O under global stream mutex. Preserve existing stream ABI/callers; protected pipes must enforce downstream permission/purge or fail closed. Non-USB witness uses same mechanism where relevant. No full transform/tee/merge/camera/display/LoRa development now.

**Next:** physical USB/controller/host/class/power/I2C ELFs publish generic `serial.port` RX/TX streams; Serial Monitor and programmer consume them with independent baud/DTR/RTS control. Remove compiled USB data plane, device-selection and fallback. **Then:** same bounded streams feed four-kind manager and online/offline `.rte.zip` ingestion, verification, safe extraction/rollback; eliminate fixed driver downloads and special USB catalog, preserve prior App Store transfers. Other U1 work such as signing-only purge can proceed independently. Generic package recovery, streams and provider/service lifecycle must not intrinsically depend on a GUI callback; full conditional UI boot conversion remains U3. **Yield:** working generic driver/stream/package architecture without hardware-specific stream bridges.

## U2 — independent package sources, reusable streams and headless-eligible roles

After accepted U1 and owner advance: independent owner-controlled package GitHub repo/build/release, source management, updates, provenance, dependency planning and profile-aware system-vs-optional roles. Use U1 generic streams for catalog/ZIP transfer and the same transaction; no separate downloaders. Headless profiles need not select graphical Settings, springboard, display or touch as core. Do not implement first-run provisioning or GUI boot refactor in U2. **Yield:** independently shipped packages and profile-aware selection from generic sources.

## U3 — T5 Pro drivers and optional firmware UI

After accepted U2 and owner advance: actual fitted T5 Pro display/touch/LoRa/GNSS/SD/power/etc hardware moves into real installable ELFs using U1 generic capabilities, byte/record/event/frame contracts and lifecycle. E-paper display uses bounded chunk/owned-frame semantics; LoRa preserves packet boundaries. **UI stays compiled into firmware but initializes only on profiles with available display, and the generic scheduler/manager/services/idle do not depend on UI rendering or foreground app.** T5 Pro GUI continues to work with installed drivers. The actual ESP32-S3-CAM must flash/boot with no Pro or CAM peripheral drivers, no display/SD/UI requirement, stable observable headless idle and recovery. Optional one-way serial diagnostic output, no interactive console. No CAM drivers or provisioning in U3. **Yield:** GUI-capable Pro and stable driverless headless CAM using the same hardware-blind runtime/port architecture.

## U4 — provisioning and one real camera image

After accepted U3 and owner advance: implement declarative first-run/approved-reapply provisioning using the one ZIP package engine, actual verified board/profile and available bootstrap media, authorization and recoverable ledger. Install CAM-specific hardware-owning ELF drivers, activate generic `camera.*` capability, and run a small **headless one-frame capture diagnostic** using an actual output available on the owner's board. Write one real test image that can be retrieved or inspected. U1 stream/owned-frame rules keep memory, DMA, quiescence and file output safe. Existing GUI remains inactive on CAM; T5 Pro retains its GUI. Avoid assuming SD, network or particular sensor before actual board inventory. **Yield:** provisioned functional headless CAM proven by one image and a retained functional Pro.

**Not U4 gates:** always-on camera streaming service, multiple frames to an external client, network/Wi-Fi setup, service auto-start, browser dashboard, interactive serial shell or full UI-to-ELF extraction. These can be scoped separately if ever needed; a camera-streaming service remains an example future application, not a required proof. Tests and physical acceptance follow the owner-controlled three-step implementation workflow, never automatic milestone advancement.
