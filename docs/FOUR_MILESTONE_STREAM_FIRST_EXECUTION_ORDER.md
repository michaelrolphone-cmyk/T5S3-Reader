# U1–U4 execution order — streams first, four milestones only

**Normative sequencing and yield contract; September 18, 2026; specification only.** This document refines implementation order and stream-related acceptance in [U1](NEXT_HARDWARE_TEST_MILESTONE.md), [U2](NEXT_MILESTONE_INDEPENDENT_PACKAGE_ECOSYSTEM.md), [U3](NEXT_MILESTONE_T5_PRO_HARDWARE_DRIVER_MIGRATION.md) and [U4](NEXT_MILESTONE_PROVISIONING_AND_ESP32_S3_CAM.md). Read the [source-backed streams work allocation](STREAM_PIPE_MILESTONE_ALLOCATION.md), [Stream/Pipe Architecture](STREAM_PIPE_ARCHITECTURE.md), [hardware boundary](HARDWARE_AGNOSTIC_DRIVER_BOUNDARY.md) and [implementation-first three-step workflow](IMPLEMENTATION_FIRST_QUALIFICATION_WORKFLOW.md). If an older workstream sequence in the U1 plan places package-manager/USB feature work before the stream foundation, **this dependency order takes precedence for execution**. It neither adds a U0 nor requires an independent streams PR, release, owner test, or qualification gate. Other product requirements and safety checks of each milestone remain intact. No implementation/release/physical verification is implied by this specification.

## U1 — generic streams first, then USB and package integration

**Entry:** [PR #86](https://github.com/michaelrolphone-cmyk/T5S3-Reader/pull/86) is merged as a documentation baseline and the owner initiates the single new U1 implementation PR from current `master`. Recover real source and PR state; do not assume a spec is working code.

**Required first workstream: finish the preexisting stream/pipe foundation before committing the architecture of new USB driver or installer paths.** Inventory existing v1 byte streams, v2 record streams, App Store HTTP transfer, `serial.port` and GNSS work; preserve their existing ABI and callers. Then implement an append-only, versioned interface for hardware-owning installed ELF producer/sink endpoints that publishes ordinary byte and typed-record streams through the single generic stream registry and capability resolver. Bind endpoint instances/generations, independent provider versus consumer execution contexts, rights/permissions, cross-context open/connect/close, source loss, cancellation, disconnect and physical unload/quiescence. No USB/GNSS-specific stream or callback bridge in normal compiled firmware. Enforce bounded queues/memory, transfer size and wall time, backpressure, lifecycle-safe in-flight I/O, real scheduler yields and no potentially blocking provider or SD operation under the global stream mutex. Sensitive/protected data may enter a pipe only if downstream permission, retention and revocation/purge are enforced; otherwise fail explicitly closed. Provide a non-USB stream-producing witness using the same provider registration where applicable. Do NOT implement optional all-purpose transforms/tee/merge/camera/display/LoRa simply to close this foundation.

**Second workstream: USB on top of streams.** Physical USB/controller/host/class/power and required I2C logic resides in real ELFs. Those ELFs publish `serial.port` and RX/TX byte streams using the completed generic endpoint contract. Serial Monitor and ESP ROM programmer use those streams and an independently versioned baud/framing/DTR/RTS control plane, with safe disconnect/reconnect and no `NativeStreamBridge` USB I/O, USB-specific resolver branches or compiled driver fallback. A compatible new class driver must not require a firmware edit.

**Third workstream: package ingestion on top of streams.** Complete the four-kind package manager and `.rte.zip` format with one bounded generic online HTTP/archive and offline file/archive stream-to-stage path. Preserve independent manifest/content/ABI/import validation, SHA-256, canonical identity/version, dependency planning, ZIP bootstrap, transaction rollback, stored artifacts and existing functioning App Store transfer. No fixed four-asset USB downloader, alternate driver installer, whole-archive RAM load or hard-coded USB catalog. Audit/remove unwanted package-signing code while retaining necessary integrity controls; the signing purge may proceed independently while stream/USB implementation is underway.

**U1 Work Complete requires:** source-level functional installed-ELF stream attachment with cross-context grants and safe unloaded-driver lifetime; USB serial and programmer using driver-produced streams with zero firmware USB data plane; generic bounded online/offline package ZIP ingestion using the same stream mechanisms; compatibility for existing v1/v2 callers, focused failure/scheduler tests and no known blocking build/source defect. One integrated owner hardware-test handoff follows implementation completion; the owner's three-step workflow governs acceptance, not a new intermediate stream milestone.

**Yield:** reusable, hardware-blind driver/package/stream foundation ready to support multiple unrelated peripheral classes without adding transport-specific firmware streams.

## U2 — use the U1 data plane for independent publishing and update discovery

**Entry:** accepted U1 baseline and explicit owner U2 start. Implement the owner's independent package GitHub repository, package-only builds/releases, configured sources, independent update discovery, cross-source dependencies, provenance/UI and profile-aware system-vs-optional roles as specified in [U2](NEXT_MILESTONE_INDEPENDENT_PACKAGE_ECOSYSTEM.md). All catalog/ZIP reads, source refresh and archive downloads use U1's generic bounded stream reader, pipe progress, cancellation, source snapshot pinning and normal transaction path, regardless of GitHub account. No separate HTTP downloader, stream runtime, firmware release coupling or second cross-source installer. Preserve offline inventory/SD installation when sources fail. Do not build third-party developer onboarding.

**U2 Work Complete additionally requires:** the independently hosted package repository can publish and update all four kinds through the same stream/package path without a framework rebuild or source-specific stream adapter; ownership/source changes and failures cannot redirect installs silently. **Yield:** firmware and owner-maintained packages have independent release/update lifecycles.

## U3 — T5 Pro peripherals consume and publish generic data

**Entry:** accepted U2 and explicit owner U3 start. Migrate each verified board-added T5 Pro peripheral into hardware-owning ELF packages. Touch uses bounded typed input records or low-volume events; LoRa uses indivisible typed packet records with TX/RX metadata and separate RF control; GNSS reuses merged `location.fix.v1` stream logic but removes firmware GNSS UART/rail/poll residue; SD supplies generic bytes apart from minimal bootstrap; battery/RTC/charger observations use typed records where sustained and events for infrequent state changes. Display uses generic versioned surface/frame transfer with bounded chunks or pinned/owned buffers, DMA/PSRAM lifetime and refresh completion; do not force a frame into a 512-byte record or embed panel scanning in core. All providers use U1 capability/endpoint permission, loss/revocation, cooperative work and quiescence. A narrowly scoped transform or tee may be introduced only when a **required** working product path needs it; full optional topology is not a U3 prerequisite.

**U3 Work Complete additionally requires:** no panel/touch/LoRa/etc firmware physical I/O path; useful T5 Pro functionality survives driver conversion; absent T5 Pro and CAM drivers do not prevent the compatible generic image from booting stably, observably and recoverably headless on the owner's actual ESP32-S3-CAM. **Yield:** one board-agnostic runtime and a verified driverless second-board boot; U3 does not add CAM drivers/provisioning.

## U4 — provision CAM profile and deliver a real frame stream

**Entry:** accepted U3 headless CAM baseline and explicit owner U4 start. Implement the already-deferred first-run/authorized-reapply provisioning manifest using U1/U2's ordinary file/ZIP/source stream and one package manager, with an independent bootstrappable medium/recovery path. Identify the owner's actual ESP32-S3-CAM board/sensor and deliver hardware-owning camera and other verified board-peripheral ELFs. Provide a generic, metadata-rich, bounded camera frame transfer: frame format, dimensions, byte count, timestamp and source identity; PSRAM/DMA-safe buffers and explicit generation-qualified ownership/release; cancellation, backpressure/drop policy, quiescence and revocation. Choose chunked byte streams or versioned opaque owned-frame descriptors instead of giant v2 record queues or retained ELF pointers. Demonstrate one headless frame-to-existing file/stream consumer and that T5 Pro and CAM use the same generic runtime/CPU port ABI; use the identical binary only where bootloader/flash/memory compatibility permits, documenting any minimal port divergence.

**U4 Work Complete additionally requires:** recoverable profile-aware provisioning and actual driver-published CAM frames, with absence/removal semantics and no camera-specific firmware bridge. Physical two-board qualification requires real owner evidence only in Release Qualification. **Yield:** proven provisioned multi-device operation.

## Exclusions and change control

Keep four milestones: **no U0, no stand-alone stream qualification gate.** The entire aspirational [Stream/Pipe Architecture](STREAM_PIPE_ARCHITECTURE.md) is not mandatory by U1 or by U4: generalized transforms, fan-out/fan-in, replay, advanced zero-copy/pools, persistent topology and global visualizers are deferred unless necessary to a named milestone acceptance path. Fundamental boundedness, source/schema integrity, permission, cleanup, backpressure and safe driver detach are never deferred for paths that are required. Only the owner advances milestones, merges, publishes, flashes and initiates physical qualification. This plan updates dependency order and acceptance only; no code or test result has been established by authoring it.
