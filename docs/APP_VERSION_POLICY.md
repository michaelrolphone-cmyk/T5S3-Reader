# RiscRTE application version and release-identity policy

**Status:** Normative for all first-class applications, September 18, 2026. [Platform specification](RISCRTE_PLATFORM_SPEC.md) -> this policy -> [Native ELF applications](NATIVE_APPS.md), [ordinary package format](RISC_PACKAGE_FORMAT.md) and [U1 execution milestone](NEXT_HARDWARE_TEST_MILESTONE.md). Applies to every future app change, including work performed inside U1. This is an agent/spec requirement; adding this document alone does not implement a build-time guard or retrospectively correct already-published releases.

## Mandatory version rule

Every distributable change to a first-class app **MUST advance the app's own `version` field in its source `Apps/<app>.json` manifest** before the app change is presented as complete. This includes code fixes, UI or behavior changes, capability/API usage, packaged resources, dependencies/manifest metadata affecting the installed or launched app, and build-option changes that alter the distributed ELF. An app-only change does **not** require a firmware version bump unless firmware itself changes. Changing `min_firmware_version` is *never* a substitute for changing `version`; raise that minimum only when new firmware behavior/API is required. Do not edit unrelated app versions or increment every app simply because a new firmware release is cut.

Use numeric `MAJOR.MINOR.PATCH` as validated by `scripts/app_manifest.py` and the runtime (three decimal components, each at most 65535). The new version MUST be strictly greater under the repository's numeric version comparator than both (a) the app's version at the PR's merge-base/last published source and (b) any later version already distributed for that same app identity. Normal bug fixes and small changes may increase PATCH; additive functionality may increase MINOR; incompatible behavior/API expectations may increase MAJOR, subject to actual compatibility checks. The critical invariant is strictly increasing versions; do not reinterpret these suggestions as a separate feature or an excuse for broad churn.

One release-worthy app update may contain multiple internal commits, so one appropriately increased app version for that cumulative update suffices. Subsequent independent app updates/releases require another increase. If a PR changes several apps, advance **each affected app's own manifest**. Do not defer version edits to the owner, merge, release workflow, catalog generator or a later PR. If no distributed app bytes or behavior/metadata change, such as a documentation-only edit outside `Apps/`, no app bump is needed. If uncertain whether the produced ELF/published manifest changes, build/compare rather than silently reusing a version.

## Package and artifact consistency

A published app identity is `(kind=application, stable app ID, version, architecture/ABI)`. Once that identity is released, its ELF and distributable manifest/resources MUST remain immutable. Do not overwrite/clobber a published app artifact or reissue changed content under the same app version, even when a GitHub release tag or firmware version differs. A digest detects changed bytes but is not a replacement for versioning. If fixing an already-published artifact, advance its version and publish a new identity. Never silently downgrade installed users or use `min_firmware_version`, release tag, timestamp or SHA as a counterfeit app-version increment.

The source manifest version is the single authoritative input. The individual release sidecar, aggregate app catalog, generic package manifest/catalog, installed inventory, App Store update comparison and release notes MUST all report that same version. Builders may stamp hashes/sizes but MUST NOT independently invent, reset or overwrite the app version. Verify the ELF/sidecar name, identity, version and hash agree, and pin all assets to the same immutable release snapshot. Keep legacy adapter metadata consistent with the canonical package rather than creating competing versions.

A firmware/API change that requires app changes is not complete until the modified apps have independently advanced versions and the correct `min_firmware_version` where required. For a manifest-only change affecting actual distributed metadata, advance the app version too; preserve correct launch requirements. Do not raise firmware minimum for an app that remains compatible solely to force a perceived update.

## Mandatory agent/review checklist

Before editing an app, inspect `Apps/<app>.json`, the current target branch and latest published app identity. Record old -> new version for each changed app in the PR/checkpoint. Update source and manifest in the **same PR**, ideally the same logical change, before declaring a task complete. Build with `scripts/build_all_apps.py` or the applicable native-app builder and inspect emitted ELF+JSON and catalogs for version consistency. Report tests accurately: an unimplemented version-reuse guard is NOT a passing test.

Review/CI policy to implement in the existing build/release validation (without creating new manual approvals or a separate workflow): compare each changed app source, distributable resource, relevant manifest and app-specific build inputs against the target/released baseline; reject non-increasing app versions; reject two different published payloads using one app identity/version; reject source/sidecar/catalog version disagreement. A test must demonstrate a changed app with unchanged version fails and an appropriately bumped version passes. This automatic enforcement is a requested follow-up implementation requirement, not a claim already delivered by this documentation commit. It should not block independent U1 coding while CI is running; correct discovered version failures before software-complete handoff/publication.

## Current implementation and enforcement gap

`Apps/*.json` already have `version` separate from `min_firmware_version`; `scripts/app_manifest.py` checks only the version's shape and bounds, and `scripts/build_all_apps.py` stamps hashes and generates a catalog. Those current validators do **not by themselves prove a version increased relative to changed app code or an earlier release**. Until the automated comparison is implemented and verified, agents MUST perform and record that check manually for every affected app. Do not label documentation compliance as automated enforcement.
