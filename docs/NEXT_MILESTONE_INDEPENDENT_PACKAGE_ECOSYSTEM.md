**Status: NEXT MILESTONE AFTER U1; SPECIFICATION ONLY.** Owner-directed scope, September 18, 2026. This document does not authorize implementation during U1, delay U1 completion, add requirements to the U1 PR, or initiate U2 before the owner advances milestones. Read [RiscRTE Platform Specification](RISCRTE_PLATFORM_SPEC.md), [U1](NEXT_HARDWARE_TEST_MILESTONE.md), [ordinary package format](RISC_PACKAGE_FORMAT.md), [bundled ZIP layout](BUNDLED_PACKAGE_ARCHIVE_AND_INSTALL_LAYOUT.md), [package identity/version policy](PACKAGE_IDENTITY_VERSION_POLICY.md), [three-step implementation workflow](IMPLEMENTATION_FIRST_QUALIFICATION_WORKFLOW.md), [cooperative bounded operations](COOPERATIVE_BOUNDED_OPERATIONS.md) and [releasing](RELEASING.md). Start U2 from the completed, owner-accepted U1 baseline only when directed, on a fresh milestone branch/PR targeting master.

## Objective and first deployment

**First make it possible for the owner to maintain a SEPARATE GitHub package repository for this project, independently of the RiscRTE framework and its firmware releases.** Build, publish, discover, update and manage the owner's packages from that separate repository without a firmware rebuild/tag/release. The package repo's precise account/name is not prescribed; it need not exist at specification time. Existing framework-hosted packages remain compatible and can migrate to the separate source without silently changing installed identity or deleting historical releases.

Use the same generic public-GitHub source mechanism for different `owner/repository` accounts so later third-party sources can be referenced without a firmware change. **U2 does NOT solicit, onboard or accept public third-party submissions, create a developer template/submission process, or launch a third-party directory.** An external source's metadata and provenance must already be representable and displayed accurately, but a public inclusion/review program is a later explicitly authorized milestone. This is source and package infrastructure first, ecosystem invitation later.

Retain U1's ONE ordinary manager for `application`, `driver`, `service` and `provider`, one `.rte.zip` archive per `(kind,id,version,target)`, extracted per-ID roots, transaction/recovery, integrity/ABI/import/authorization checks and hardware-blind runtime. Package-specific signing/P-256 is not reintroduced. The owner-directed workflow is **Work Complete -> Improving Code -> Release Qualification**; CI is useful feedback, not an excuse to stop independent implementation.

## 1. Firmware/package build and publication separation

- Firmware release jobs publish firmware, boot and recovery artifacts only; no implicit rebuild/republish of every package. Retain necessary firmware compatibility filenames, request behavior and legacy resolution. A package-only change does not increment the firmware version or require a firmware tag.
- Support independent build commands and GitHub Actions for one named stable package, a selected set, and all changed packages, optionally filtered by architecture/target. Build from actual package manifests and the U1 deterministic ZIP packer, including resources and dependencies. Detect package source/resource/manifest and shared SDK/ABI inputs; rebuild only affected packages, not the whole firmware. Explicit dispatch works without source changes. Avoid fan-out, approval loops and orphaned competing workflows.
- **Support an owner-controlled package repository separate from the framework repository as the primary U2 use case.** Its build/publish path must work from that repository's sources with a documented shared toolchain/SDK version or reusable build action/command, without assuming access to the framework repository's mutable workspace or compiling firmware. Prefer building/publishing in the package repository itself; GitHub's repository-scoped default token must not be assumed able to publish into a different repository. If a cross-repository publish path is offered, its permissions must be explicit and optional rather than a prerequisite for independent package builds.
- Package publications have their own immutable GitHub release/tag cadence; publish exactly one U1-format archive per identity/version/target plus suitable source-index metadata. Match manifest, archive, hash, catalog and origin records. Refuse identity/version reuse with changed bytes, regressions, duplicates or incompatible target claims. `min_firmware_version` remains a compatibility floor, not a reason to republish unrelated packages.
- Remove package steps from firmware release workflows only after their replacement can generate compatible artifacts. Audit dead workflows and eliminate mutable `.pio`/`dist` artifact interference. Preserve old releases, installed ZIPs and URLs via bounded legacy source resolution. Provide concise independent build/publish instructions for firmware and packages; never silently publish on a build or PR.

## 2. Source registry and owner-repository integration

- Extend U1's generic source configuration/catalog, not executable authority or the package installer. A configured public GitHub source records canonical account/repository, its catalog or immutable release location, enabled/disabled state, scope/policy, last successful refresh and diagnostic/availability state. Do not hard-code the owner's future package-repository name or require firmware changes to add one.
- A listed package resolves one immutable repository release ID/tag and one exact archive asset with bounded size, SHA-256, target, `(kind,id,version)` and source identity. Never assemble assets by separately querying mutable `latest`, follow unapproved cross-host redirects, replace unavailable assets from a different account, or infer publisher authenticity from an archive-supplied hash. Use HTTPS/GitHub repository validation, bounded parsing/downloads, timeouts, progress and genuine scheduler yields under [cooperative operations](COOPERATIVE_BOUNDED_OPERATIONS.md).
- Provide ordinary Package Manager source controls: list configured sources, add the owner's separate repository, enable/disable, refresh, inspect last error, and remove a source **without erasing installed packages**. Source refresh failure must not block offline inventory, launch, uninstall or SD installation. Disable/remove affects future discovery/update sourcing, not the provenance of existing installs.
- Preserve source continuity through repository relocation/rename, deletion and transfer. Installed inventory records the source repository and immutable release reference; show a clear unavailable/moved/changed-source state rather than silently rebinding. A move to another repository/account or change of ownership requires an explicit reviewed source-migration action, with existing install state and rollback intact. Preserve identity/version lineage when the owner moves framework-hosted packages into the separate package repository.
- Accept references to different GitHub accounts through the same source-record schema, but **do not implement a third-party request inbox, PR submission contract, publisher onboarding guide/template, automatic catalog approval or invitation workflow in U2**. Explicit owner-configured cross-account source support is sufficient. General registries, private-repository credentials and mirrors remain out of scope.

## 3. Independent update discovery and cross-source dependency planning

- Discover available package versions by refreshing enabled package source catalogs, **independent of the firmware updater and firmware releases**. Show installed/current/available versions, compatible vs incompatible updates with concrete firmware/runtime/architecture/ABI/capability reasons, source, and the difference between an optional update and a required dependency. Allow selective install/update; do not implicitly update every package or firmware because any catalog changed.
- Preserve U1's canonical `(kind,id)` update lineage, numeric semver and immutable-content rule. An installed package remains bound to its recorded source for ordinary updates; do not treat an arbitrary same-ID package from another repository as its successor. Detect duplicates and competing same-ID providers, same ID/version with conflicting hashes, version regressions, changed source ownership and differing target/ABI. No source may impersonate an official package through display metadata. Changes of source/owner must be explicit and diagnosable.
- Extend the **existing U1 dependency resolver** to select available packages across the configured, enabled sources under bounded, deterministic source/identity policy. Resolve dependency versions, capabilities and target compatibility; detect conflicts/cycles and missing or disabled-source dependencies before installation. Show the full planned source and version for each dependency and any required user decision. Reuse the ONE ordinary plan/preflight/transaction/rollback engine: never create a separate cross-repository installer, marketplace dependency engine or firmware special case.
- Update discovery and dependency planning must remain usable if one source is offline: retain verified installed inventory and last known catalog information with freshness/unavailable indicators; do not claim stale listings represent current releases or bypass integrity/version checks. Downloads pin exact immutable assets, use U1 archive verification and preserve last-good whole-directory generations on failure.

## 4. Publisher, authorship and detailed package information

- Version and bound catalog/manifest/inventory metadata to distinguish **claimed display author**, claimed publisher, actual configured GitHub `owner/repository` and release reference observed from source/API data, catalog-maintainer classification, and installed origin. Record origin through update/rollback and expose any proposed source change. Never label self-asserted authorship as verified ownership or assume a curated listing is an endorsement, permission grant or authentication of code.
- Package detail and install/update confirmation show: title/description/icon where present, package kind, system/optional role, author/publisher claim, actual source repository with link, release/version/target, license identifier/link where provided, minimum firmware/runtime compatibility and reason for incompatibility, dependencies, declared capabilities, installed/available version, update state and source status. Unknown/unverified fields are marked accordingly, not fabricated. Follow trusted-link/open URL policy; do not turn a package-supplied URL into an unrestricted downloader.
- Provide clear `RiscRTE core`, `Owner package repository`, `External source` and `Unknown/legacy` origin indications as applicable, independent from the package's system role. A package in the owner's external repository does not become firmware-resident; a package from a different GitHub account does not become official/core solely through its manifest. Keep source inspection available offline from recorded installed metadata.

## 5. System-core vs optional consumer and device-profile baseline

- Retain U1's four package **kinds**. Define a separate versioned **role** (`system-core`, `optional-consumer`, plus a narrowly justified optional-system classification if needed) and separate source/publisher classification. Kind answers what the package does, role why it participates in a device's baseline, source where it came from; do not infer any of these from directory name or default installation.
- Introduce a **lightweight declarative device profile/baseline** using the existing generic capability/dependency model. It describes required capabilities, applicable core packages, optional system components, resource requirements and profile revision. This is package selection/management metadata, NOT first-run SD provisioning or a new activation engine. Do not hard-code display/GPS/USB board tables into the runtime: profiles/providers declare compatible capabilities. Headless/minimal profiles omit the display-dependent Settings UI while retaining whatever baseline capabilities they actually require.
- Distinguish `core for this profile`, `available system component`, `required by dependency` and `optional consumer` in Package Manager. E.g. Settings can be a core system application on a display profile, Mahjong and Serial Monitor are optional consumer applications; core services/providers remain independently installed packages, not necessarily firmware code.
- Group/filter System/Core and Optional, retain kind/source filters, and show installed state, profile applicability, dependency chain and impact of removal. Core is **not universally installed, privileged, or unremovable**. Permit safe core deselection/removal when the selected profile and active dependencies allow it. Refuse destructive removal of required or in-use packages or the last boot/recovery route; otherwise offer an explicit, bounded coordinated dependency/removal plan through the ordinary manager.
- Official system-core designation comes from owner-maintained profile/catalog policy, never an external manifest's self-declared flag. Classification is descriptive management policy, not capability permission or automatic trust. Preserve existing installations and support migration from packages that predate role/origin metadata with explicit `unknown/legacy` state.

## 6. Implementation order and work-completion boundary

1. At kickoff inspect completed U1 source, actual manifests, release workflows, current package UI and profile support; preserve the shared manager and U1 archive semantics rather than rebuilding them.
2. Make the owner-controlled separate package repository a functional build/publish source, split firmware and package workflows and replace obsolete release tasks. Preserve published history and the independent version/compatibility model.
3. Add source configuration/management and immutable GitHub release resolution. Implement package-only version/update discovery and cross-source dependency resolution using the existing manager. Keep offline behavior, source continuity and transaction recovery intact.
4. Extend manifests/catalog/installed inventory and Package Manager UI for authorship, detailed package metadata, origin and role. Add lightweight device-profile baseline and safe system-package management without implementing provisioning.
5. Perform focused builds/smoke checks and durable invariant tests for actual defects and stable behaviors: independent package build, repository move/missing release, wrong hash/target, duplicate identity, incompatible updates, cross-source dependency conflicts, source disable, headless applicability and safe uninstall. Follow the bounded/cooperative operation code-completion rule. Do not introduce a broad milestone-specific end-to-end suite, wait for all-green CI before continuing unrelated coding, demand intermediate hardware checks or publish automatically.

**U2 Work Complete:** independent package-repository builds/publications no longer require firmware releases; an owner-selected repository can be configured as a source; package-only compatible updates and cross-source dependencies work through the same U1 manager; origin/authorship/license/compatibility information and system/optional roles appear in Package Manager; headless profiles can omit irrelevant UI; existing packages/updates survive absent or moved sources without unsafe substitution; no known blocking source/build defect remains. Report actual checks and unknowns, then **Improving Code** on subsequent `continue` until the owner explicitly initiates **Release Qualification**. Owner authorizes actual publishing/merging/flashing.

**Deferred:** third-party invitations and submission/review program, developer template/onboarding workflow, public marketplace, reputation or package-signature infrastructure, first-run SD provisioning and credential setup, additional hardware-family migrations, general non-GitHub registries, private GitHub authentication, billing, mirroring and blanket installation of every core-marked package. Generic different-account GitHub source compatibility **is included**, but recruiting or accepting outside packages is not.
