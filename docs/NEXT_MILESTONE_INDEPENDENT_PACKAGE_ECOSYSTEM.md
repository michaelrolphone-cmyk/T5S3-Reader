# U2 — Independent package publishing, external sources and system roles

**Status: NEXT MILESTONE AFTER U1; SPECIFICATION ONLY.** Owner-directed scope, September 18, 2026. This document does not authorize U2 implementation during U1, delay U1 completion, create a second U1 PR, or require qualification before the owner advances milestones. Read [RiscRTE Platform Specification](RISCRTE_PLATFORM_SPEC.md), [U1](NEXT_HARDWARE_TEST_MILESTONE.md), [ordinary package format](RISC_PACKAGE_FORMAT.md), [bundled ZIP layout](BUNDLED_PACKAGE_ARCHIVE_AND_INSTALL_LAYOUT.md), [package identity/version policy](PACKAGE_IDENTITY_VERSION_POLICY.md), [three-step implementation workflow](IMPLEMENTATION_FIRST_QUALIFICATION_WORKFLOW.md), and [releasing](RELEASING.md). U2 starts from the completed/owner-accepted U1 baseline when the owner authorizes it, in a fresh milestone branch and PR targeting master.

## Objective

Separate package build, publication and update cadence from RiscRTE firmware releases; allow independently published packages in other GitHub accounts to request catalog inclusion; present verifiable package origin/authorship and an explicit distinction between core system components and optional consumer packages. Preserve U1's one `.rte.zip` archive per `(kind,id,version,target)`, one generic four-kind manager, isolated installed roots, dependency/ABI/architecture admission, transactional update/recovery and hardware-blind capability architecture. Package-specific signing/P-256 is not reintroduced by this milestone.

## 1. Decouple build and publication

- Firmware releases build, validate and publish firmware/boot/recovery artifacts only; they do not implicitly rebuild or republish every unchanged app, driver, provider or service. Existing compatibility filenames and firmware release-request behavior remain functional where still needed for firmware.
- Package builds can be explicitly requested independently of firmware, individually by stable package identity or for a selected set/all changed packages, with an optional target architecture. A package source change need not increment firmware's version or require a firmware tag. Unchanged packages need not be rebuilt or republished.
- Create a package-specific GitHub Actions build/publish path using the U1 canonical manifest-derived builder and reproducible ZIP packer. Trigger builds for package source/resource/manifest/shared SDK dependency changes and by explicit dispatch; avoid workflow fan-out, approval loops and unrelated firmware work. The owner/developer retains control of publishing; builds/PRs do not silently create releases.
- Package releases use independently versioned immutable GitHub release/tag identities and one archive per identity/version/target; keep manifest, ZIP, catalog listing, emitted hashes and provenance metadata coherent. Reject reuse of a published identity/version with changed bytes, duplicate names/assets and package-version regressions. A shared SDK/ABI change invalidates or rebuilds only affected packages; `min_firmware_version` is compatibility metadata, not a package version or reason to republish unrelated packages.
- Remove obsolete package publishing and catalog-generation steps from firmware release jobs only after replacing their functionality. Audit orphaned/overlapping workflows, prevent mutable `.pio` or `dist` cross-job artifact custody problems, and document concise independent commands for building and publishing firmware versus packages. Legacy firmware releases and previously installed ZIPs must remain resolvable; do not rewrite or delete historical release assets.

## 2. External GitHub package sources and catalog inclusion

- Extend the generic catalog **source configuration / listing manifest**, not ZIP executable authority, to reference package releases hosted at another GitHub repository/account. A source record identifies canonical GitHub `owner/repository`, immutable release tag or release ID, exact release asset name, architecture/target, expected size and SHA-256, stable `(kind,id,version)`, and optional release/manifest URLs. Resolve one immutable snapshot; do not combine independently fetched `latest` manifest/asset bytes or follow arbitrary redirects to unrelated hosts.
- Provide a documented third-party submission mechanism: a developer supplies a public repository/release and a proposed source/listing manifest or pull request. The maintainer can review and approve inclusion in the catalog **without copying the package into a RiscRTE firmware release or rebuilding the developer's code by default**. Approved listing updates are independent of firmware publication. A referenced external release being changed, missing or incompatible is reported as unavailable/inconsistent; do not silently fall back to another account, tag or package.
- Use bounded source/index downloads and parsed manifests, retry/time limits and genuine scheduler cooperation per [cooperative operations rule](COOPERATIVE_BOUNDED_OPERATIONS.md). Enforce HTTPS/GitHub host/repository validation, bounded URL and manifest fields and archive/hash verification; avoid arbitrary URL injection and remote paths. Public GitHub releases are the initial required external transport. Private-repository authentication, generalized third-party registries, mirroring, billing and automated developer onboarding are outside this milestone unless explicitly requested.
- Preserve canonical package identity and update lineage across sources. Reject duplicate `(kind,id,version,target)` entries with conflicting bytes, disallow a third-party listing impersonating an existing official identity, and require an explicit source/owner migration policy for repository transfers/renames or loss of access. Catalog inclusion is discoverability, not an authenticity proof, permission grant or guarantee that the remote maintainer is trustworthy. SHA-256 proves downloaded-byte consistency against the selected listing; it does not prove publisher identity.

## 3. Provenance and authorship shown in Package Manager

Add bounded, versioned catalog/manifest metadata with distinct fields for **display author/publisher (claimed metadata)**, canonical source `owner/repository` (verified from the selected release URL/API record as available), source URL, immutable release/tag, package version and target, and **catalog inclusion/maintainer classification**. Record source identity in installed inventory so users can inspect origin offline; keep it through update/rollback and make source changes visible rather than overwriting origin silently. Do not present an unverified self-declared author as a verified GitHub owner.

Display publisher/author, actual source repository and an unambiguous `RiscRTE core` versus `Third-party` versus other configured origin indicator on package detail and install/update confirmation; offer a source link when available. A package published under another GitHub account remains visibly third-party even when listed in the curated catalog. Do not infer official endorsement or privilege from a display name, repository spelling, copied metadata or curated inclusion. Where metadata cannot be verified, label it as unverified/unknown rather than guessing. Source provenance is independent of runtime authorization, ELF import/API permission checks and dependency admission.

## 4. Core system role versus optional consumer role

Maintain the existing four `kind` values (`application`, `driver`, `service`, `provider`). Add a **separate, versioned role/classification** such as `system-core` and `optional-consumer`, with room for explicitly justified optional system components if the actual dependency model needs them. `kind` answers *what executes*; role answers *why it is offered / how essential it is to a configured device*; source/publisher answers *where it came from*. Do not infer these from filenames, directories, installed-by-default state or publisher alone.

Examples: Settings is a `system-core` application for a device profile needing local settings UI; Mahjong is an `optional-consumer` application; Serial Monitor is an `optional-consumer` tool despite consuming driver/service capabilities. Core providers or services may supply essential baseline functionality without being firmware-compiled. A display-dependent Settings app is neither mandatory nor automatically installed on a headless ESP32. **Core means essential within a selected device profile or its baseline capability plan, NOT universal or irremovable.**

- Have explicit profile/capability requirements determine applicable core packages and installation selections; allow minimal/headless profiles to omit display/UI packages. A device's chosen core baseline and dependency requirements, not arbitrary catalog grouping, govern whether a core component is needed for current configured functionality.
- Present separate `System`/`Core` and `Optional` groupings or filters in Package Manager, showing role, whether applicable/required by current profile, installed state, dependencies and impact of uninstall. Keep apps, services, drivers and providers available in their appropriate kind filters without producing a second installer.
- Do not protect every `system-core` package with an unconditional uninstall ban or make every core component firmware-resident. Allow optional core selection and removal **when safe**; if another installed package or active runtime capability requires it, explain the dependency and use ordinary quiescence/refusal or an explicitly approved coordinated removal plan. Avoid bricking the device by removing the only boot/recovery path. A core component's title/icon/role must never confer hardware or privileged rights.
- Official-core classification is controlled by the RiscRTE-maintained catalog/profile policy, not by an external package's self-declared `core` flag. Third-party packages may declare their technical role or capabilities but cannot become official core solely through a submitted manifest. Profile metadata remains versioned, explicit and hardware-agnostic; board-specific device selection lives in profiles/providers, not core firmware device tables.

## 5. Implementation order and completion boundary

1. At U2 kickoff inspect completed U1 code, package schema, releases, workflows, existing package-manager UI and actual headless/profile support; reconcile this document to real API boundaries without rebuilding the common installer.
2. Split firmware and package build/release workflows, add independent per-package/all-changed build and publication with stable identities, immutable outputs and backward-compatible release resolution. Remove dead/duplicate CI only after replacement and reference audit.
3. Implement GitHub cross-account source listing/resolution and curator-controlled inclusion, immutable asset fetching, conflict/identity checks and bounded/cooperative handling through U1's ordinary catalog/download/ZIP installer.
4. Extend manifests/catalog/inventory and Package Manager UI for authorship, actual source/provenance and core/optional classification, including headless profile applicability and safe core removal. Keep architecture generic for all four package kinds.
5. Use focused build/smoke and durable invariant tests for changed source/release resolution, identity collision, bad external asset/hash, source disappearance and role/uninstall rules; fix observed defects. Do not create a comprehensive short-lived end-to-end test suite, block independent coding on all-green CI or request intermediate hardware testing. Deliver a coherent implemented block as **Work Complete**; following `continue` means **Improving Code** until the owner explicitly starts **Release Qualification**. No automatic merging, publishing, flashing or release qualification.

**U2 Work Complete condition:** independent firmware and package build/publication paths exist; adding/updating a package does not need a firmware release or firmware rebuild; current and external GitHub packages use the same generic manager and U1 ZIP format; external entries show meaningful verified-source-versus-claimed-author distinction; core versus consumer roles are independently modeled and displayed; headless profiles can omit UI core components; existing installs remain safe; known blocking code/build defects are addressed. Record actual checks and limitations without claiming owner qualification.

**Explicitly deferred:** implementing U1 changes here, first-run SD provisioning workflow, full marketplace/reputation/signature infrastructure, cross-host registries beyond public GitHub, automatic third-party trust delegation, private repository auth, payments and auto-installing all packages marked core.
