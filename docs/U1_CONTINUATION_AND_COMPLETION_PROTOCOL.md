# U1 continue-driven implementation and handoff protocol

**Normative agent workflow; revised September 18, 2026.** Read [AGENTS.md](../AGENTS.md), [master spec](RISCRTE_PLATFORM_SPEC.md), [U1 milestone](NEXT_HARDWARE_TEST_MILESTONE.md), and [glanceable reporting](U1_STATUS_REPORTING.md). **PR #86 is the specification PR, intended to be merged to master before implementation. It is NOT the next implementation PR.** The owner's latest explicit workflow instructions supersede older directions to implement on PR #86 or refuse to merge it as documentation only.

## 1. Startup in a fresh context

Check whether [spec PR #86](https://github.com/michaelrolphone-cmyk/T5S3-Reader/pull/86) has merged. If merged, start from CURRENT `master`, create ONE new named U1 implementation branch and a PR targeting `master`, then work there. If not merged, identify that as the branch handoff condition rather than treating the documentation PR as the implementation destination; preserve any actual code already present. Do not stack dependent PRs or ask the owner to recreate context. Read current source, U1's linked specs and the actual branch state before acting; do not equate documented targets with implemented behavior.

Maintain `docs/U1_IMPLEMENTATION_LEDGER.md` on the **implementation** branch after starting real code work. Keep only a compact durable record of completed/remaining gates, commits, consequential test/build findings, package version changes, blockers and next source task. Update at meaningful checkpoints; do not spend an entire turn generating status documents. Recover work from source, commits and the ledger if the context restarts.

## 2. Meaning of every `continue`

Implement the next highest-value unfinished U1 code task now, on the SAME implementation branch/PR. Inspect, change, commit and perform proportionate validation. Keep working on independent tasks while CI runs or a nonessential check is broken; never idle or transfer routine build approvals, source edits or intermediate hardware tests to the owner. Address a CI failure when it provides actionable evidence relevant to the changed code; CI is a feedback mechanism, NOT a prerequisite to continuing other work and NOT a requirement to build elaborate new CI infrastructure as a substitute for finishing U1.

Priority remains completion of the authorized functionality: true provider-owned USB plus reusable non-USB driver foundation, generic `serial.port`, unified four-kind package lifecycle, `.rte.zip` bundle distribution, per-package installed directories and ZIP bootstrap/service, safe old-install and CDC-ID migration, signing-specific code purge, release/build compatibility and independent package versioning. First-run SD provisioning is deferred. Work through dependencies and fix demonstrated defects, not endless spec rewrites or speculative refactors.

**Testing during development:** Run the smallest useful build, host/unit or smoke check that can verify the code being changed, especially stable parsers, ZIP extraction bounds, version/identity invariants, migration rollback and lifetime safety. Repair meaningful failures. Do NOT build a comprehensive end-to-end test suite merely to satisfy this milestone, freeze rapidly evolving flows in brittle tests, require every current CI workflow to pass before proceeding, or mandate maintaining temporary milestone-only tests forever. Integration failures are expected to be discovered and repaired when integrating and later testing; that does not justify omitting focused safety/correctness checks. Do not repeatedly rehearse the eventual physical testing boundary in normal progress reports.

Each response: briefly state actual changed files/commit, real validation outcomes where relevant, the remaining actionable step or genuine blocker. End with the standalone bold 2–5-word status required by [U1 Status Reporting](U1_STATUS_REPORTING.md). Avoid ETA or promises of asynchronous work.

## 3. Software completion: accurate, not ceremonial

Reserve the standalone bold line **Work Complete** for when all REQUIRED U1 implementation deliverables are present, wired together in production paths, inspected and free of known blocking defects. Perform appropriate release-equivalent build/smoke checks that are available and useful to establish a coherent, installable candidate. Record exactly what was actually verified and any unrun/failed checks; do not turn missing CI status into success, but neither make a pending/unrelated CI check a blanket veto on substantive progress or create an artificial CI qualification bureaucracy. Do not invent an all-encompassing test suite or insist on an immutable artifact inventory for every intermediate commit. A demonstrably broken build, missing required feature or known blocking integration defect prevents a truthful completion claim.

At first genuinely finished software handoff, put the exact standalone line **Work Complete** earlier in the response, identify the implementation commit/PR and what was checked, and end with **Software Ready For Testing**. Prepare a concise single hardware test procedure at that handoff only; do not claim physical test results or repeat physical-test disclaimers during ordinary implementation. Owner alone decides merge/release/flash/test. If a later defect invalidates readiness, withdraw the assessment and repair before reconfirming.

## 4. Meaning of `continue` after completion

Continue productive QA on the SAME implementation PR: review code and interfaces, test concrete edge cases, strengthen reusable regression coverage, inspect ZIP extraction, migration/recovery, driver unload/IRQ/DMA lifetime, RAM use and diagnostics, and repair verified problems. Prefer targeted persistent tests on stable invariants over a fragile milestone-specific end-to-end harness; avoid unnecessary refactors and deferred scope. After a correction, perform proportionate revalidation. If no defensible independent work remains, report the verified coverage concisely without inventing defects. Never auto-merge or publish.

## 5. GitHub API rate limits and access failures

Distinguish actual GitHub primary/secondary rate limiting (HTTP 403/429 explicitly indicating a rate limit, x-ratelimit-remaining 0, Retry-After or reset headers) from permission/auth, 404/409, 5xx, network and connector errors. If confirmed, STOP API retries and polling, state explicitly `GitHub API rate limit reached; GitHub-dependent work is paused until the limit lifts`, give the last verified commit and reset time ONLY if provided. Continue only independent work available from reliable local code; otherwise GitHub-dependent work resumes on a later owner `continue` after recovery. If cause is unknown, say `GitHub access failure; reason not confirmed` and give the observed error; never fabricate a quota reset or successful commit. On reconnection re-read branch HEAD before writing. The final status must accurately say **GitHub Quota Blocking Work** or **GitHub Access Unavailable**.

## 6. Nonnegotiable boundaries

No hardware-specific functionality hidden in core/proxy drivers, special USB catalogs, unversioned changed packages, `foo-v2` identity forks, split-file normal publication, unsigned archive mistakenly treated as authenticated, new signing system, or premature provisioning. Preserve existing installed state and recoverability. Do not ask for intermediate hardware tests, freeze on CI, manufacture completion, merge/release/flash without permission, or confuse PR #86's specs with implementation work. The user's explicit nonblocking iteration model governs how the U1 requirements are executed.
