# U1 continue-driven implementation protocol

**Normative; September 18, 2026.** Read [root AGENTS.md](../AGENTS.md), [three-step implementation-first workflow](IMPLEMENTATION_FIRST_QUALIFICATION_WORKFLOW.md), [U1 milestone](NEXT_HARDWARE_TEST_MILESTONE.md), [stream milestone audit/allocation](STREAM_PIPE_MILESTONE_ALLOCATION.md) and [glanceable reporting](U1_STATUS_REPORTING.md). The owner deliberately favors completed code blocks over incremental qualification. Earlier text demanding all-green CI, comprehensive milestone end-to-end testing, same-commit qualification artifacts or hardware results before saying implementation is finished does not govern this workflow. Product scope, safe extraction/rollback, identity/version correctness and honest status remain mandatory.

## 1. Start a fresh implementation context

[PR #86](https://github.com/michaelrolphone-cmyk/T5S3-Reader/pull/86) is the **specification-only baseline** and is intended to merge into master, not the destination for production implementation. Confirm whether it has merged. After merge, create ONE fresh milestone implementation branch from current master and ONE PR targeting master. Continue in that PR; do not stack dependent PRs. If #86 has not merged, report that specific handoff condition without assuming master has the specs. Read current source/commits and binding specs; do not infer implemented code from a plan or past chat narration.

Maintain a concise `docs/U1_IMPLEMENTATION_LEDGER.md` in the new implementation branch: finished/unfinished production tasks, consequential commits, package version increments, real build findings, blockers and next source action. Update at meaningful checkpoints, not in lieu of writing code. Recover real state from git and source when chat context restarts.

## 2. Before Work Complete: `continue` means IMPLEMENT

On every user `continue`, inspect and implement the next high-value unfinished task on the SAME milestone branch/PR; commit coherent code and run proportionate useful checks. Continue independent code while CI runs, fails on an unrelated check or is unavailable. Address demonstrated relevant build/integration failures, but do not require routine workflow approvals or hardware testing after every change. Avoid status-only turns, endless spec edits, redundant redesign and brittle comprehensive milestone-wide test infrastructure.

Finish the entire authorized production block: provider-owned physical USB/controller/host/class/power and required I²C, generic `serial.port`, cross-family non-USB witness, four-kind common package lifecycle, `.rte.zip` bundles and per-kind/ID installed roots, ZIP bootstrap and reusable service, legacy/CDC identity migration, signing-only purge, generic release/catalog compatibility and independent package versioning. The future SD provisioning workflow remains deferred.

**Mandatory stream integration within that same U1 block:** use [the source-audited Stream/Pipe Milestone Allocation](STREAM_PIPE_MILESTONE_ALLOCATION.md). Preserve already-merged byte v1/record v2/App Store/GNSS work, but complete a generic installed-provider-owned byte/record endpoint and cross-context permission/lifetime binding; use installed `serial.port` ELF RX/TX for Serial Monitor and programmer instead of firmware USB bridge; route the common online/SD ZIP ingress through bounded, cancellable shared streams; prevent a global stream mutex from spanning unbounded provider I/O; and protect downstream copies/revocation for permitted sensitive pipes. These are foundations **necessary to avoid rewriting U2–U4 consumers**, not permission to implement all transforms, tee, merge, zero-copy, camera, display or LoRa now. A firmware-only `RuntimeStreams::Provider` callback table with USB-specific `NativeStreamBridge` implementation does not meet Work Complete.

Use targeted tests for stable ZIP/path/bounds, transactional integrity, capability/import authorization, version/identity and unsafe module lifetime cases when useful. Do not misrepresent failed/unrun checks as passing. Work through actual integration defects rather than requiring the owner to qualify incomplete subfeatures. Until all required production functionality is implemented and no known blocking defects remain, the final status is **Implementation In Progress** (or a truthful blocker-specific 2–5-word label).

## 3. First step: **Work Complete**

When the requested code block is fully implemented and wired together, with known blocking source/build defects addressed, announce the exact standalone bold final line **Work Complete**. In the few sentences above it identify the implementation PR/commit, actual builds/targeted checks and any checks not run. This is an **IMPLEMENTATION-completion signal** only; it does not assert that the owner tested hardware, all CI passed, release assets are frozen, or a release is qualified. Do not keep coding indefinitely simply because the owner has not had time to test. Conversely never use the phrase for a docs-only change, a missing mandatory feature or a known broken/unlaunchable candidate. Only the owner decides merge, tag, release, flash and physical testing.

## 4. Second step: **Improving Code** while waiting

When user says `continue` after Work Complete and has NOT explicitly initiated Release Qualification, perform a real independent audit, improvement, focused test, defect fix or maintainability/performance work on the SAME implementation PR. Favor ZIP extraction/recovery, provider lifetime, package migration, release-path consistency, resource usage and useful diagnostics. Do not invent scope, demand testing, freeze artifacts, auto-merge/release or simply restate status. Every such response ends with **Improving Code**. If a blocking defect is found that invalidates completion, state it, return to implementation and fix it; re-announce **Work Complete** when restored.

## 5. Third step: **Release Qualification** only when invited

Advance ONLY on the owner's explicit request to begin Release Qualification. Work together on actual device and integration tests, investigate failures, patch code and repeat relevant checks. Establish exact accepted revisions/artifacts at this stage, not every intermediate commit. Do not claim tests succeeded when they were not run or imply owner acceptance before it happens. Qualification is the third workflow step, not an automatic effect of code completion; a release-qualified outcome requires actual evidence and owner acceptance, not another autonomous workflow state. All merge/tag/release/flash actions still require explicit owner authorization. While working in this step, end messages **Release Qualification**.

## 6. GitHub quota and access failure

Distinguish confirmed rate limits (explicit GitHub 403/429 rate limit, exhausted rate headers or Retry-After) from auth/permissions, 404/409, transport/connector problems or 5xx. On a confirmed limit, stop retries/polling, explicitly state `GitHub API rate limit reached; GitHub-dependent work is paused until the limit lifts`, identify last confirmed SHA and a reset timestamp only if actually given. Continue only genuinely independent local work from a reliable snapshot; otherwise resume on a later owner `continue` once available. If cause is unknown, state `GitHub access failure; reason not confirmed` with observed error. Never invent reset timing or successful commits; reread HEAD before writing after recovery. Blocker labels may temporarily replace the workflow label for truthful glanceable reporting.

## 7. Reporting and prohibitions

Keep replies to a few sentences: substantive code change, actual relevant check/blocker, next task. The very last line is one bold 2–5-word truthful state under [U1 Status Reporting](U1_STATUS_REPORTING.md), nothing after it. No proxy ELF hiding hardware in firmware, USB-specific catalog, changed package without version bump, renamed `foo-v2` as version substitute, split-file normal packages, renewed P-256 signing, premature SD provisioning, unsupported PASS, intermediate owner hardware-test demands, or auto-merge/release. Product correctness is required; exhaustive qualification belongs to the explicitly owner-initiated third step.

## 8. Explicitly planned next milestone: U2

[U2 — Independent Package Publishing, External Sources and System Roles](NEXT_MILESTONE_INDEPENDENT_PACKAGE_ECOSYSTEM.md) is the owner's specified NEXT milestone after U1. It decouples app/driver/service/provider GitHub builds and releases from firmware, supports other GitHub accounts as catalog package sources with authorship/origin transparency, and distinguishes profile-appropriate core system packages from optional consumer packages. **U2 is not part of U1, is not a Work Complete gate, and must not start during the Improving Code step.** After owner-directed U1 Release Qualification and an explicit instruction to begin U2, start a new milestone implementation branch from the accepted baseline. Preserve U1's generic package interfaces without prematurely implementing external catalogs or role policies. Apply the [stream milestone allocation](STREAM_PIPE_MILESTONE_ALLOCATION.md) when implementing U2, U3 and U4; later board/camera data paths must use the U1 endpoint foundation instead of inventing transport-specific firmware streams.
