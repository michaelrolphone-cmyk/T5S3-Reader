# U1 continue-driven execution, evidence, completion and quota protocol

**Status:** Mandatory operating instructions for any implementation agent working on [U1](NEXT_HARDWARE_TEST_MILESTONE.md) in [PR #86](https://github.com/michaelrolphone-cmyk/T5S3-Reader/pull/86). Read [the platform specification](RISCRTE_PLATFORM_SPEC.md), the applicable child specs, [repository AGENTS.md](../AGENTS.md) and this protocol before beginning. These are operating rules, not a claim that implementation is finished. The owner intends to initiate a fresh chat, issue an initial instruction to implement U1, and then use the single-word instruction **`continue`** repeatedly. Never require the owner to act as a build operator or restate already documented requirements.

**MANDATORY USER-VISIBLE FORMAT:** [U1 Glanceable Progress Reporting](U1_STATUS_REPORTING.md) governs EVERY U1 work/workflow response, including the first implementation instruction, every `continue`, completion, post-completion QA, CI failure and GitHub outage. Keep the user report brief and factual; the FINAL LINE MUST be a standalone **bold, 2–5-word current-state label** with no text after it. Reserve **Work Complete** for verified software completion as specified below; on that first completion message, put its exact standalone bold line earlier in the response and END with **Software Ready For Testing**. Do not use a completed status while software gates are unmet. Read and obey the linked reporting specification in full.

## 1. New-context startup and rehydration

On an initial U1 implementation request, connect to the existing repository and **the existing draft PR #86 and its actual head**. Read this document, the current PR description and changed-file list, `AGENTS.md`, `docs/RISCRTE_PLATFORM_SPEC.md`, `docs/NEXT_HARDWARE_TEST_MILESTONE.md`, and binding child specifications. Compare the PR branch to master and incorporate relevant master changes without discarding branch work. Read implementation source, tests, scripts, actual releases and CI evidence before choosing the next task. The branch name beginning `docs/` does not mean this is a documentation-only PR. Do not open a new dependent PR, restart prior delivered work from an obsolete spec, or presume a past assistant's narrative proves an actual code change. At time of writing, U1's new docs, policies, agent guidance and PR acceptance requirements have been committed; USB migration, ZIP packaging, ZIP service, physical driver acceptance and several code-side validators are **not yet implemented or verified**. Refresh this statement against the latest actual branch state rather than continuing to repeat it after source progresses.

Maintain `docs/U1_IMPLEMENTATION_LEDGER.md` on the PR branch as the **durable, evidence-based handoff between chats**. Create it when starting production implementation; record exact HEAD/master refs, current code checkpoint, completed versus unfinished specification gates, files changed, true test/build/CI status with SHA and URLs, any blockers, versions and next actionable task. Update it at meaningful source checkpoints and at the end of each turn. Do not mark a requirement PASS from a written plan, generated artifact name or pending CI. If a previous context ended unexpectedly, reconstruct progress from Git history, branch diff, tests and this ledger. Ledger is evidence and navigation, not a new milestone or an excuse to spend a full turn merely updating planning.

## 2. Meaning of `continue` while software is incomplete

Treat `continue` as an instruction to **resume doing implementation work now on the same U1 PR**. Determine the highest-priority unfinished acceptance item, inspect the relevant current code, edit/commit code and tests, and validate as far as the available environment permits. Work in coherent source-level units. Fix a concrete integration or CI defect when it is evidenced; otherwise move to an independent source task while CI runs. Never spend a turn simply restating a roadmap, generating another spec, waiting for GitHub Actions, asking the owner for intermediate hardware tests, requesting routine manual workflow approvals or opening stacked dependent PRs. Don't merge, publish, tag, flash or change the owner's hardware without explicit authorization.

The agent MUST continue toward **all** binding gates, not stop at an individually working USB provider or package download: full USB ownership extraction; cross-family driver witness and portability gap audit; ordinary four-kind unified manager and catalog; one `.rte.zip` distribution archive per package; per-ID installed directories and ZIP bootstrap/service; safe legacy/CDC identity migration; package-specific signing purge; monotonic app/driver/service/provider versions and automated guards; release-equivalent build, archive-integrity and host/static tests; and one integrated owner hardware-test procedure. The separate first-run SD deployment provisioning workflow remains deferred. When tests fail, record exact evidence and repair; do not claim completion and transfer routine debugging to the owner.

Keep turn reports brief and concrete: commits/paths changed, tests actually run and results, current milestone gate state, next source task. Do not provide a synthetic ETA, ask the owner to wait while background work proceeds, or promise that changes will happen outside the current request. Each user `continue` is a new explicit request to carry out additional work in that response. Always END each report with the bold, 2–5-word label required by [U1 Status Reporting](U1_STATUS_REPORTING.md).

## 3. Strict software-completion gate and exact user-visible signal

The phrase **`Work Complete`** (exact capitalization, rendered in bold) is **reserved for the first response in which ALL U1 SOFTWARE-READY gates actually pass**, and for subsequent responses that reconfirm the verified completed state. Before using it, audit every binding document's stop rule, prove the production source changes exist, run and report applicable reproducible builds, host/integration/archive tests and static boundary/identity/signing/catalog audits at the **same final commit**, inspect relevant CI results, and verify coherent firmware/app/driver/service/package asset identities, versions and hashes. Generate a single complete hardware-test sheet. Every uncovered defect, failed check or unimplemented mandatory gate means **NOT COMPLETE**; never use the phrase as a progress heading, hypothetical declaration or consolation for documentation-only work. A frozen pending CI or missing relevant build evidence is not PASS; disclose an actual environment blocker and keep completion unclaimed.

When those software gates are met, the response MUST contain the standalone exact line:

**Work Complete**

Immediately distinguish the scope: `U1 software milestone: complete at <commit SHA>. Physical hardware acceptance: PENDING OWNER TEST.` Summarize verified artifacts/tests, outstanding physical-only items and the one procedure; don't conflate READY FOR HARDWARE TEST with an observed working USB connection. Do not hold the software-completion signal hostage to a user-run board test because U1 is explicitly a software-ready handoff. Conversely do not claim full hardware validation or a release until those actions actually happen. The very last line is **Software Ready For Testing**, as mandated by the separate reporting format; do not place a link or explanatory text after it.

If implementation reveals a newly discovered mandatory defect before signaling completion, fix it and rerun impacted tests; do not change requirements arbitrarily to declare success. If a later audit exposes a regression in a previously reported completed milestone, state plainly that the previous software-ready assessment is no longer valid, switch back to repair and verification, and only reconfirm completion after rerunning affected gates.

## 4. Meaning of `continue` after the software milestone is complete

Once software completion is evidenced, further user `continue` does **not** mean pause, repeat the same status, auto-merge/release, or expand into deferred projects. Begin a focused post-completion QA cycle against the same PR: independently review source diff/ownership boundaries and dependencies, examine package ZIP parser and extraction safety, resource isolation, versioning, installed-data migration and rollback, provider lifetime/IRQ/DMA safety, CI/test gaps, memory/stack/performance on ESP32-S3, diagnostics and release provenance. Add useful negative, edge, fault-injection and integration tests; run them and fix verified defects. Prefer objective correctness, maintainability and bounded resource improvements that reduce risk for the one owner hardware test. Preserve established behavior and avoid speculative refactors or unrelated feature creep; defer enhancements requiring new product decisions.

Each post-completion `continue` MUST perform a nontrivial useful audit/test/fix task if available, report what was actually reviewed, tests and new commits if any, and either reconfirm **Work Complete** after applicable checks or clearly withdraw the completion state if an actual blocker is discovered. Do not repeatedly claim fresh work without a diff or test result. If exhaustive available inspection finds no defensible additional work, say so with the review coverage and exact remaining physical-test dependency; never fabricate defects or silently alter scope just to remain busy. End with a truthful 2–5-word bold status label even during post-completion auditing.

## 5. GitHub API quota and connectivity failures

If a GitHub connector request fails, distinguish **evidenced quota/rate limiting** (for example HTTP `403`/`429` explicitly naming rate limits, `x-ratelimit-remaining: 0`, `x-ratelimit-reset`, `retry-after`, or an explicit GitHub secondary/abuse-rate-limit response) from unrelated authentication/permission errors (`401`, some `403`), missing resources (`404`), conflicts (`409`), transient `5xx`, transport failures and connector authorization issues. Never assert quota exhaustion solely because a connector says `unable to connect`; inspect the available status/response/headers. If unsure, report `GitHub access failure; reason not confirmed`, include the observed error and do not invent a reset time.

For a **confirmed** rate limit, immediately stop GitHub API polling, repeated retries, automated workflow triggers and writes. Report prominently: `GitHub API rate limit reached; GitHub-dependent work is paused until the limit lifts.` Identify whether primary or secondary if shown, any actual GitHub reset timestamp or `Retry-After` provided (with timezone), and the exact commit/operation last known complete. If the service does not provide a reset value, state that it is unavailable. Do not promise background resumption or ask the owner to keep retrying; continue only genuinely independent local work when reliable source snapshots/tooling are available, otherwise stop GitHub-dependent work explicitly and resume on a later owner `continue` after quota recovery. Respect any stated reset/Retry-After and avoid attempts that aggravate a secondary limit. On reconnection, check the remote branch/current SHA before writing and reconcile any intervening changes.

Quota transparency does not justify declaring incomplete work `Work Complete` or claiming a GitHub commit succeeded when the response did not confirm it. If the blocker is NOT quota, state the actual evidence and best available recovery path rather than telling the owner to await a quota reset without proof. Always finish the message with **GitHub Quota Blocking Work** only for confirmed quota, or **GitHub Access Unavailable** when the reason is unknown.

## 6. Prohibited substitutes and completion boundaries

No repeated 'please test now' halfway through; no proxy drivers, firmware USB special cases or fixed hardware catalogs; no duplicate `foo-v2` package identities or skipped version bumps; no split ELF/manifest normal distribution, separate archive installer or dangerous extraction; no new package signing; no newly implemented SD provisioning; no stale status reports dressed as implementation; no auto-merge/release; no unsupported PASS or hardware-test claim. Keep all work on the existing PR and its recoverable ledger until the user explicitly directs otherwise.
