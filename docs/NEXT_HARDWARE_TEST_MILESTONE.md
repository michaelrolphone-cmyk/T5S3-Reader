# Next hardware-test milestone: unified packages and complete USB extraction

**Status:** Normative execution and acceptance plan, September 18, 2026. **Milestone ID:** U1. **Scope:** one integrated, hardware-test-ready unit of work; not permission to merge, publish, flash or claim physical success. Read [RISCRTE_PLATFORM_SPEC.md](RISCRTE_PLATFORM_SPEC.md), [HARDWARE_AGNOSTIC_DRIVER_BOUNDARY.md](HARDWARE_AGNOSTIC_DRIVER_BOUNDARY.md), [temporary I²C bootstrap and cutover](I2C_BOOTSTRAP_CUTOVER.md) and [PACKAGE_MANAGER_SCOPE_CONTRACT.md](PACKAGE_MANAGER_SCOPE_CONTRACT.md) first. The [four-milestone execution order](FOUR_MILESTONE_STREAM_FIRST_EXECUTION_ORDER.md) controls implementation priority, and the temporary I²C exception overrides this document's historical full-I²C-in-U1 requirement. This plan resolves the current-work status and ordering of the [Unified Package Manager MVP](UNIFIED_PACKAGE_MANAGER_MVP.md), [RISC package format](RISC_PACKAGE_FORMAT.md), [USB migration status](USB_ELF_MIGRATION_STATUS.md), [runtime implementation](RUNTIME_DRIVER_IMPLEMENTATION.md), [driver architecture](RUNTIME_DRIVER_ARCHITECTURE.md) and [provider graph](PROVIDER_GRAPH_ADMISSION_LIFETIME.md). Target architecture in those documents remains binding subject to the explicit temporary bus exception. Where old MVP/status text says PRs #76/#78/#79 are drafts, physical ELFs are unpublished, or App Store/Driver Manager have not been integrated, those are superseded historical snapshots, not current work orders.

## 1. Explicit change contract

**User objective.** Complete one unified package-management system, purge unwanted *package-authentication/signing* scope creep from the active repository, and finish genuine hardware ownership extraction so no operational USB implementation, discovery, chipset/provider selection, USB sessions, USB stream or USB-specific bridge remains in normal firmware. Remove the special coupling to `usb-provider-catalog.json`. Prepare **one finished software unit** that the owner can install and test on hardware after implementation, rather than requiring intermittent physical tests before continuing.

**Required:** preserve verified ordinary unsigned package installation; complete four-kind application/driver/service/provider management, online and offline, in one engine; remove package-signing-specific sources, tools, gates and stale requirements after auditing their references; publish/discover packages through a generic source-agnostic catalog adapter, with no named USB catalog requirement; have installed USB controller/host/class/power ELFs do all real device work; allow only the versioned, bounded temporary firmware I²C **bus primitive** when needed for their power/expander ELF dependencies; use generic provider publication/resolution, permission, streams and lifecycle; remove and demonstrate absence of firmware USB behavior/fallback; supply reproducible tests and a single physical test sheet. **Complete I²C-controller extraction is U3, not U1.**

**Excluded/deferred:** P-256, signed RISC-PKG, trust roots, signer/key management, signed receipts/provenance, revocation, cryptographic NVS floors, secure boot, package publisher authentication, replacement signing systems, unrelated new hardware families, arbitrary new networking/security infrastructure, unrelated UI redesign, a general multi-architecture binary loader, broad platform rewrite and release automation redesign. No new required service or provider implementation simply to exercise a package kind: use minimal test packages. Four existing package kinds remain; do not redesign the taxonomy in this milestone. SHA-256 content-integrity checks, size/ELF/ABI/import validation, transactional replacement, generic runtime authorization, TLS already needed by networking, and hardware-safe quiescence are **not** signing scope creep and must survive. [ELF load verification performance](U1_ELF_LOAD_VERIFICATION_PERFORMANCE.md) separately controls bypass of expensive repeated hashing on already-committed installed generations, without compromising install/transaction integrity.

**Dependencies and authorization:** existing generic OS/CPU privileged ABI, package transaction, installed provider graph and independently installed physical ELFs are necessary to the two requested goals. A catalogue is only a source/discovery convenience, never loader authority, provider selection policy or hardware driver. The runtime must remain hardware-blind; the owner-authorized firmware I²C bus adapter is isolated in the port layer and is temporary, not permanent hardware knowledge in the generic runtime. There are no mandatory new signing, key, board-specific USB firmware or manual workflow approvals.

## 3. Definition of the single deliverable

**U1 READY FOR OWNER HARDWARE TEST** means all workstreams A–F below are implemented together on one PR branch targeting `master`, full production/release-equivalent firmware and module builds plus relevant source/host tests have been run and recorded, the static ownership/coupling audits have no unexplained hits **except documented temporary firmware I²C bus-only calls**, the package/update/driver chain is coherent, and the user receives one versioned firmware+application+driver asset set and one test procedure. No owner interaction or board test is an intermediate gate. Physical USB success is explicitly **PENDING OWNER TEST** until actually performed. No PR merge, tag, release, firmware flash or arbitrary workflow/manual-approval request is implied.

Successful CI is **not a prerequisite for starting the next code workstream**. Run available local, host, dependency and compiler checks as changes progress; push in coherent commits, inspect relevant CI opportunistically while developing independent code/tests/docs, fix failures when evidence arrives, and leave the branch/PR and milestone ledger in a recoverable state at every prompt boundary. Never block a prompt waiting for GitHub Actions; never claim a pending/failed check passed. Before *handoff*, supply the actual latest check state and successful relevant build/test evidence or disclose blockers precisely. Continue implementation across prompts until the whole U1 definition is met; an internal checkpoint is not a handoff.

### Workstream A — inventory, tests and ownership map (internal checkpoint)

1. Record exact `master` and U1 branch commit, existing owner test reports and current build/test baselines. Audit full compilation/link reachability and incoming references, not just filename searches. List every file, definition, CMake/PlatformIO inclusion, ABI export, app, test, workflow and release asset that owns or mentions USB, I²C bootstrap, package-signing features or the canonical USB catalog. Classify each as core hardware code (remove), adapter (migrate), driver ELF (retain), **explicitly authorized transitional I²C bus-only port API (retain until U3; document caller/removal)**, generic SDK definition, boot/recovery-only, test, signed-only (purge), or unrelated crypto (retain). Add a dated audit ledger to this spec/PR.
2. Inventory actual ordinary `Kind`/manifest and SDK functions, app and driver online/offline source adapters, installed inventory, active module use-gate, crash recovery, the release exporter and build scripts. Identify a minimal reusable host fixture for each of the four package kinds. Freeze speculative feature additions.
3. Identify actual USB debug/boot/flash transport dependency before deleting anything. A boot-only or ROM flashing interface may remain solely in an isolated platform port/recovery image; it must not export production USB capabilities, keep normal host hardware active or function as a hidden fallback. Do not damage boot or logging to satisfy a text grep. Inspect the actual I²C power/rail graph before deleting a bus dependency that is required for boot or USB VBUS safety.

### Workstream B — finish the *generic* manager and remove USB-catalog coupling

1. Establish one canonical ordinary package manifest/input accepted by the existing common inspection, preflight, transaction, recover, inventory and uninstall implementation. Retain existing manifests and ELF/payload format where workable. Both SD (`/Packages/Inbox/<id>`) and downloaded inputs adapt to the same engine; no separate App Store/driver transaction, privileged admission, permissions or recovery policy. Conversion of legacy ELF+JSON is a compatibility **source adapter**; it may not be another independent installer.
2. Implement a bounded generic `package-catalog.json` **source index**, or a format-neutral catalog endpoint with equivalent behavior, generated from ordinary package manifests for all four kinds. This is a discovery/locator view only: ID, kind, version, architecture/runtime compatibility, capabilities/requirements, immutable release identity or base URL, bounded filenames, lengths and SHA-256. It does not define a second package format or grant trust/hardware access. Build the index from actual produced assets and checked manifests; reject missing, duplicate, stale, conflicting or inconsistent entries before publishing. No hard-coded seven-package count, fixed USB file set, driver-specific global catalog or hard-coded USB capability mapping. Other future packages enter the index from manifest/build metadata, not changes to firmware.
3. Pin catalog and downloads to the same immutable GitHub release tag/asset set or versioned source snapshot, **not independent `/releases/latest/download/` requests** that can cross a release boundary. Check each fetched size/digest and revalidate against the actual `.package.json` and staged ELF through the common engine. A catalog digest establishes *consistency only*, never a verified signer. URLs/paths must be bounded, normalized and restricted to the configured source; no arbitrary manifest-provided download URLs or traversal.
4. Replace `NativeDriverManagerBridge.cpp`'s `kCanonicalProviderCatalogUrl`, `loadCanonicalDriverCatalog`, special overlay/priority merging and `NativeOnlineDriverInstall.h`'s fixed `kNames`/latest URL with a common catalog/source adapter and generic dependency planner. App Store, Driver Manager and Package Manager may display filtered views, but all call the same inventory/online/offline/install/update/uninstall API. Dependency plans must include the full provider graph, detect missing/cyclic/ambiguous capability requirements, refuse downgrade/in-use replacement, preserve existing installs on partial failures, and supply specific diagnostics. Package Manager gains installed inventory and online discovery/actions for **all four kinds**, not only SD inbox browsing. Do not install or activate hardware merely by opening a catalog.
5. Package installers and inventory must work with **zero catalog file** when operating offline or examining installed packages. Missing, corrupt, stale or unavailable online catalog means a clear online discovery failure; it cannot prevent locally installed drivers from activating, existing packages from being listed/uninstalled, or SD installs. A new driver package in a supported architecture/ABI must install without being in a baked firmware list or the old USB catalog. Drivers own physical suitability/probe and capability advertisement; catalog does not select chipsets.
6. Update `scripts/build_installed_usb_stack.py`, `scripts/export_canonical_driver_release.py`, `.github/workflows/release.yml` and related tests to publish ordinary generic package assets/index. Remove production emission, publishing, fetching and parsing of `usb-provider-catalog.json`. Use legacy driver-catalog/flat `.t5driver.*` import only where needed for existing GPS/older releases, with a finite explicit removal condition after parity; never a fallback physical firmware provider. Historical immutable releases can retain their old asset; current source/release cannot depend on it. Add a repository test that fails on reintroduced production references to the old catalog and ensures publishing a new unrelated driver requires no source edits in firmware or the exporter.

**B acceptance:** online + offline discovery/install/update/inventory/uninstall for app, driver, service and provider test fixtures share the same transaction; existing working App Store/Driver Manager behavior remains; offline operation succeeds with catalog missing; a new manifest-only driver appears in online release index; removal of `usb-provider-catalog.json` from build/release does not affect supported USB stack installation; interrupted/corrupt/mixed-release assets reject cleanly, preserving previous generation.

### Workstream C — purge unrequested signing code, without weakening necessary checks

1. Build a dependency/reachability table before deleting. Candidates include `PackageArchive*` signed framing/verification/staging/extraction if signing-only; `PackageDeviceCrypto.*`, `PackageTrustPolicy.h`, `PackageDeviceSecurityFloor.*`, `PackageSignedProvenance.h`, `PackageSignedTransaction.h`, signing-specific `PackageDeviceInspection/Stage/Extract/Directory/Publication/Installer` portions; `PackageSecurityFloor.h`, P-256 writer/signing scripts such as `scripts/build_risc_package.py`, signed experiment tests and fixtures, signing-only CI targets and deferred signed-format docs. Classify every exact path as DELETE, EXTRACT GENERIC or KEEP with callers/tests. Do not blindly remove a useful ordinary parser, copy, hash, safe-path, transaction, rollback, importer or private ELF-byte ownership function because it resides in a file named `Signed`.
2. Move independently useful code to neutral existing package modules with unchanged or improved tests, rewire build/link/callers, then **delete** signed-only source, headers, signing test tools/fixtures, release dependencies and experimental signed-format documentation from the active repository. Git history retains old experiments; do not hide an unused signed subsystem in an `experimental/` directory or leave a future feature switch. Remove signing assertions/requirements from all active spec/agent/README/API guidance. This purge is explicitly requested, unlike the older keep-or-archive option.
3. Preserve SHA-256 file-content comparison, bounded parsing/path/ELF/ABI/relocation and import checks, independent privileged-policy authorization, normal package version checks, mapped-generation pins, rollback/recovery, and general network TLS or OS crypto unrelated to package signing. A hash supplied by untrusted metadata is **not** publisher authentication or the authority to import privileged symbols. Normal installed-file hot paths follow the temporary bypass and permanent caching requirements in [ELF load verification performance](U1_ELF_LOAD_VERIFICATION_PERFORMANCE.md); staging/update/recovery and explicit checks still validate contents.
4. Handle previously installed signed-only packages conservatively: inspect read-only and preserve unknown data; accept them only if they independently satisfy ordinary manifest/contents rules, otherwise report unsupported/needs migration. Never delete user-installed data or silently grant permissions to maintain compatibility. No speculative signed-package migration framework in U1.
5. Add negative scans of production source, build/release actions and tests for P-256, trust roots/signers, `.risc-auth`, signed-receipt/floor APIs and old signed archive production paths, with a documented allowlist only for unrelated system cryptography, historical git history or a plainly worded explanatory note. Compilation and ordinary offline/online regression must still pass with signing sources physically absent.

**C acceptance:** no package-signing implementations/tooling/docs remain in active tree; normal package workflows neither link nor reference them; unsigned ordinary package install and real driver admission still enforce all independent integrity, privilege and lifecycle checks; signed-only input fails safely without corrupting installed data.

### Workstream D — move the *remaining USB behavior* into ELFs and generic APIs

1. Use `Drivers/usb_controller_esp32s3`, `usb_host_v2`, `usb_cdc_v2`, `usb_cp210x_v2`, `i2c_esp32s3_v2`, `board_power_t5s3_v2` and `platform_clock_v1` as the existing driver and dependency starting point. Their manifest-provided capabilities/dependencies and board/profile data drive activation. Keep the 46-symbol generic OS/CPU ABI as generic primitive support; no replacement ESP-IDF USB host/transfer/PHY implementation in firmware or a privileged `kernel.usb` shim. **Unlike USB host/class behavior, the I²C controller is a permitted temporary port-layer bus primitive: U1 does not require `i2c_esp32s3_v2` to take over runtime bus ownership when that causes a root-bus/power dependency cycle.** Do not claim the bus fully converted until U3.
2. Move **all logic presently in** `src/native/NativeUsbBridge.cpp`—host polling, fetching/interpreting descriptors, VID 0x10C4/CP210x choice, hard-coded `usb-*-v2` IDs, selection order, class/session state, USB read/write/configuration/line controls, USB-specific lifecycle and `BOARD_T5S3_PRO` feature guard—into the host/class/provider side as appropriate. Convert Serial Monitor to request a generic `serial.port@1` capability, obtain a provider-published instance via generic registry/resolver and use a provider-produced generic byte stream plus a versioned provider capability for serial configuration/control. A compatibility `T5UsbApi` may exist only in an independently installed adapter ELF/app if unavoidable; *no USB-aware implementation or adapter remains in the compiled framework*. Keep functionality and current UI controls including baud, DTR/RTS and manual selection.
3. Move provider probe and per-device class selection to actual driver ELFs: the host ELF owns enumeration, topology/device tokens, hotplug, interface/endpoint claims and controller access; CDC ELF inspects USB descriptors; CP210x ELF validates supported VID/PID/profile rather than vendor-VID-only selection. A new serial class driver binds via its installed manifest/probe, without touching core, board build flags, Serial Monitor or central USB lists. Ambiguous matching must fail with a visible choice/diagnostic or provider-defined deterministic policy, never firmware-specific guessed priority.
4. Replace `UsbSerialProjection.h`, firmware `NativeUsbDeviceRegistry`, USB polling in `ActivityManager::loop`, `nativeDeviceDiscoveryTick`, `NativeSerialPortBridge` USB session/physical reservations, direct USB logic in `NativeStreamBridge`, fixed `UsbCdcDriverRuntime` loader and other reached firmware USB code with **provider-originated, bounded, generation-safe generic** device publication, execution-context grants, lifecycle and stream callbacks. Physical contention, USB power/role arbitration, recovery and safe teardown stay in providers. Keep the transport-neutral device registry and software leases; it must not parse VID/PID/USB epochs or reserve USB devices as physical hardware.
5. Implement a genuinely functional, driver-origin `serial.port` capability: installed USB providers publish serial instances and RX/TX streams; Serial Monitor and ROM programmer use the generic consumer API for byte I/O and versioned baud/DTR/RTS control, without a firmware USB fallback. Disconnected streams return a real error and reconnect only after the provider announces a new generation; cancellation/unload revokes old handles without use-after-unmap. The I²C port adapter is an allowed upstream power/expander bus dependency only, not the USB data plane.
6. Audit and remove USB-specific firmware code/imports from production-reachable core and tests that incorrectly require old behavior. Keep boot-only debug/ROM interfaces separate, mark immutable historical code as legacy, and maintain one-way diagnostics when needed. New class drivers require no core/board build edits.

**D acceptance:** physical USB implementation and class selection are in driver ELFs, Serial Monitor and programmer use driver-published generic serial streams, board power control is performed by a power ELF through a bounded temporary I²C bus transfer when needed, and no USB hardware/host/class path remains in normal firmware. A failed or missing power/I²C dependency fails safely; no duplicate controllers, unbounded transaction or hidden USB fallback. An I²C-controller ELF may be packaged/tested in U1, but its exclusive normal-bus ownership and removal of the transitional firmware API are U3, **not** U1 acceptance.

### Workstream F — integrated software and owner hardware-test handoff

## 4. Definition of done / milestone stop rule

Mark U1 **SOFTWARE COMPLETE — READY FOR ONE HARDWARE TEST** only when all are true:

- One manager API and transaction handles four kinds from SD and a general online source; installed inventory, version/update/uninstall/recovery work without an online catalog and do not require signature tooling. App Store/Driver Manager/Package Manager are views over it; legacy compatibility is bounded and documented.
- No production build, release/export step, runtime source, provider selection or installation relies on `usb-provider-catalog.json`; generic catalog is generated from actual manifests and is not an authorization or activation source. New compatible provider registration needs no firmware patch.
- Unwanted P-256/signed archive/trust/provenance/floor implementation and tests/tools are **deleted from the active repo**, with independently needed validation retained and tested; no rebranded signer substitute.
- All operational USB, USB device projection, VID/PID/class selection, direct USB stream/session/host/power logic and fixed USB driver routes are outside compiled normal framework and inside installable ELFs or explicitly isolated boot-only port exceptions. No silent fallback exists. Generic code knows only opaque capabilities, grants, versioned interfaces, streams, events and lifecycles. **The separately recorded temporary firmware I²C bus primitive is allowed solely for power/expander ELF bootstrap and bounded transactions until U3; it is not permission to keep any firmware USB implementation.**
- The I²C dependency graph is noncyclic for the active U1 setup; one controller owns the bus at any time, calls are bounded/authorized, unsafe failures are handled, and the removal path in U3 is recorded. Do not demand an exclusively active I²C ELF yet.
- U1 stream provider foundation, generic serial and ZIP intake work are implemented per the stream-first execution order. Installed ELF launch/inventory no longer repeatedly hash complete ELF files, and transactional integrity remains per [performance spec](U1_ELF_LOAD_VERIFICATION_PERFORMANCE.md).
- Source/link audits, realistic failure/absence tests, firmware+ELF builds and artifact-custody checks have recorded results at the same commit. No known build failure is called successful and no owner hardware test is claimed. A failing CI run is addressed without abandoning next independent work; remaining external CI uncertainty is disclosed.
- A single runnable hardware acceptance sheet and asset manifest is delivered; no partial implementation milestone has been pushed onto the owner to test.

If any condition fails, U1 remains **IN PROGRESS** with a concrete remaining-work ledger, and the next prompt continues on the same branch. Do not split interdependent U1 work across stacked PRs, auto-merge, tag, publish or require repeated manual GitHub Actions approvals. Once U1 is actually complete, a subsequent milestone may move the **next** hardware family (GNSS/UART or network, per explicit priority) out of firmware with the same install-only, no-fallback criterion. **U3 specifically completes I²C bus extraction and T5 Pro hardware migration; U4 handles one camera image.** U1 alone does not establish that one ESP32-S3 firmware binary runs unmodified on every ESP SoC: CPU/ABI/bootstrap differences require a distinct port. It does establish that *new USB devices and compatible providers* require ELF/profile installation, not a board-specific core rebuild.
